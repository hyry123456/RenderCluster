## 阴影性能回归修复（Cluster 4.32ms → 目标接近 SRP 3.12ms）

Profiler 对比（同场景同位置）：
- SRP：Shadows **0.450ms** / Main Camera 0.378ms / 帧 3.119ms
- Cluster：Shadows **1.724ms** / Main Camera 0.569ms / 帧 4.319ms
⇒ **整帧只差 1.2ms，全部来自阴影 pass**。GBuffer(cluster) 只比 SRP 贵 0.19ms，可接受。

三个根因 + 修法：
1. **每个顶点 3 次有依赖的缓冲读取**：`_Visible → _Indices → _Positions`。
   → `_Positions` 改成**按「簇 × 384（角点序）」平铺**（同簇共用顶点也重复存），
     VS 变成 `_Positions[簇号*384 + corner]`，只 **1 次**流式读取；`_Indices` 整个删除。
     显存净变化≈0（省掉 idxBuf 47MB + drawIdxBuf 47MB，换来 posBuf 50→141MB）。
2. **静态单位索引缓冲本身是纯浪费**：每个索引只用一次 ⇒ 顶点缓存零复用，却仍要 4B/顶点 读一遍。

## 阴影追平 SRP：改回索引绘制（推翻上一版的"删索引"结论）

上一版把阴影改成「非索引 + 簇×384 角点全展开 + VS 里查 _Visible」是**方向性错误**，实测 1.7ms vs SRP 0.45ms。
根因：
1. 128 三角形的簇唯一顶点只有 ~90 个，展开成 384 等于把顶点复制 4 份 ⇒ VS 白跑 4 倍；
2. 非索引绘制让 GPU 后变换顶点缓存完全失效，收不回这 4 倍；
3. VS 里 `_Visible` → `_Positions` 是两级依赖读取（gather 延迟）。

正解（2026-10-27 定案）：
- **`CommandBuffer.DrawProceduralIndirect(indexBuffer, ...)` 在 Unity 2022.3 存在**（映射 D3D11
  DrawIndexedInstancedIndirect，args = 5 个 uint：indexCount/instanceCount/startIndex/baseVertex/startInstance）。
  不带 indexBuffer 的那个重载才是非索引（4 个 uint），两者别混。
- 索引缓冲用 **`GraphicsBuffer.Target.Index | Target.Raw`**：D3D11 不允许 Index 同时是 Structured，
  但允许同时是 Raw ⇒ compute 用 `RWByteAddressBuffer` 写、draw 直接当 index buffer 读，**单缓冲零拷贝**。
- 数据：`_Positions` = 每实例的 mesh 顶点各一份（簇内去重，不再按 384 展开）；
  `_ClusterVerts[簇×384]` = 静态的全局顶点号表；`_ClusterSlot[级联×簇]` = 可见槽位（不可见 0xFFFFFFFF）；
  `_DrawIdx[级联×簇×384]` = 每帧 compute 重排出的索引。
- 4 个 dispatch：Reset / CullAll / **BuildIndices** / BuildArgs。
  BuildIndices dispatch 用 **(384/64=6, 簇数, 级联) 三维**：x 维恒定不撞 D3D11 单维 65535 上限，
  且同簇 384 线程读同一个 `_ClusterSlot` 地址；级联走 **id.z 线程维度**而不是 uniform（绕开
  "CommandBuffer 内逐 dispatch 变的 uniform 会被最后一次设置覆盖"这个老坑）。
- VS 简化成 `pos = _Positions[SV_VertexID]` —— **只有一次顺序读取**，无查表。
- `_ClusterSlot` 不可见时必须写 INVALID_SLOT 覆盖上帧残留（省掉对整张表的 Reset）。

顺手：`_Visible` 在阴影侧已完全删除（GBuffer 侧仍用自己那份，互不影响）。
内存代价：`_DrawIdx` ≈ 级联数 × 簇数 × 384 × 4B（4 级联 / 3.4k 簇 ≈ 21MB）。

## 阴影提速第一刀：Cull Off → Cull Back（口径对齐 SRP）

**发现**：`ClusterPBR.shader` 的 ShadowCaster pass（第 106 行 Pass，LightMode="ShadowCaster"）**没写 Cull 指令**
⇒ 默认 `Cull Back`；而 `ClusterShadow.shader` 写的是 `Cull Off`。
⇒ SRP 路径一直单面投影，Cluster 路径把每个投射物的背面又画了一遍（**光栅化 ×2**）。
这是 Cluster 阴影 1.77ms vs SRP 0.45ms 的主要嫌疑之一（阴影 pass 是光栅化/fill-rate bound，
432K 三角形 × 4 级联，背面多出来的部分在阴影图里完全不参与最终深度）。

已改 `ClusterShadow.shader` 为 `Cull Back`。若场景出现必须双面投影的单面片（旗帜/布/卡片植被）再改回。

**用户问「相邻簇能否合并合批提速」——不能，也已经没必要**：
现在 4 个级联 = 4 次 `DrawProceduralIndirect`，每次把该级联【所有可见簇】一次画完，
不存在「一个簇一次 draw」。把附近簇合并成大块只会降低剔除精度（画更多三角形），
draw call 数不会变（本来就是 4）。

**「抹平差异」的含义**（给用户解释用）：
SRP 的顶点来自 GPU 的 Input Assembler —— 固定功能单元，按 vertex buffer + index buffer
拉数据，有专用预取器和带宽通路；Cluster 是在 VS 里用 shader 指令去 StructuredBuffer 里
"读"顶点，走通用 load 通路。要让 Cluster 也走 IA，要把顶点放进真正的 Mesh vertex buffer
（`SetVertexBufferParams` + `SetVertexBufferData`，索引用 `indexBufferTarget = Index|Raw`
让 compute 写，再 `DrawMeshInstancedIndirect`）—— 风险较大，未实施。

**下一步验证**：切到 SRP，看 Profiler 里 Shadows 的顶点数。
若 SRP 顶点数远小于 Cluster 的（簇数 × 384 × 级联），说明 per-object 剔除剔掉了大量物体，
「同样渲染条件」的前提就不成立，得先把两边几何量对齐再谈优化。

## GBuffer 交给 Cluster（用户最终目标：只有动态物体走 SRP）

- `ClusterAssembleAsset.clusterGBuffer` 默认 true，`assemble.asset` 里同步改成 `clusterGBuffer: 1`。
  `clusterMode = Cluster` + `clusterGBuffer = true` ⇒ GBuffer / RVT Feedback / 阴影全部走簇，
  动态物体（有动画/移动的 Transform）自动留在 SRP。
- **顺手优化（逻辑等价，纯减负载）**：`_Visible` 从 `uint` 改成 `uint2 = (簇下标, 材质槽位)`，
  由 CullAll 在剔除时一并从 `_ClusterInfo[c].y` 写出。
  ⇒ 绘制侧 `ClusterFetch` 的取数链从
     `_Visible → _ClusterInfo → _Indices → 属性`（4 级串行）
     缩成 `_Visible → _Indices → 属性`（3 级串行）。
  shader 里 `_ClusterInfo` 声明与材质绑定都删掉了（compute 还需要它）。
  ⚠️ `_Indices[clusterID*384 + corner]` 与原来的 `_Indices[info.x + corner]` 等价，
  因为 `info.x` 恒等于 `簇序号 * 384`。

### 已知的 GBuffer 路径开销结构（下一步优化的靶子）
- `ClusterGBufferRenderer` 用的是**非索引** `DrawProceduralIndirect`（4 个 uint args，
  `vertexCount = 可见簇数 × 384`）⇒ **每簇 384 个角点全部各跑一次 VS**，索引缓冲只在
  VS 里当查表用，没参与顶点缓存复用。
- GBuffer + RVT Feedback **各画一遍**（但 Feedback 的间接绘制不计入 Statistics 的 Batches）。
- VS 里还要读 `_ClusterToWorld` / `_ClusterNormal` 各 3 行（同一个簇 384 顶点读同一地址，L1 命中）+ 2 次矩阵乘。
- 要真正追平 SRP：把顶点按「每实例、世界空间」烘焙（pos/nrm/tan/uv + matIdx 打进顶点），
  索引缓冲存全局顶点号走**真索引绘制**，VS 只剩一次读 —— 这就是之前说的「抹平差异」。

## GBuffer 顶点改为「世界空间预烘焙」—— VS 从 15 次缓冲读降到 3 次

实测 GBuffer 走 Cluster 后 316.6 FPS vs GBuffer 走 SRP 373.6 FPS（慢 15%）。
用户判断正确：**VS 里每顶点的十几次缓冲读取全部压给 GPU，是慢的主因**。

重构（`ClusterGBufferRenderer` + `ClusterGBufferInput.hlsl` + `ClusterGBufferPass.hlsl`）：

**顶点格式**：每顶点 64B，4 个 float4，**全部预烘焙到世界空间**
```
a = (posWS.x, posWS.y, posWS.z, nrmWS.x)
b = (nrmWS.y, nrmWS.z, tanWS.x, tanWS.y)
c = (tanWS.z, tanSign, baseUV.x, baseUV.y)   ← UV 已乘 _MainTex_ST
d = (detailUV.x, detailUV.y, 0, 0)           ← 已乘 _DetailMap_ST
```
烘焙期算完：世界变换、法线逆转置矩阵、Gram-Schmidt 正交化、两个 ST。
⇒ VS 只剩 `_Visible[slot]`(uint2) → `_Indices[簇*384+corner]` → `_Vertices[gi]` **三次读取**。

**删掉的资源**：`_Positions` / `_Normals` / `_Tangents` / `_UVs` / `_ClusterToWorld` / `_ClusterNormal`
（每簇 128B × 2 的矩阵缓冲完全不需要了）。`_ClusterInfo` 上一轮已从绘制侧删除，只留 compute 用。

**代价**：顶点不再跨实例共享 —— 同一个 mesh 的每个摆放各存一份（原来按唯一 mesh 一份）。
属于「拿显存换 GPU 时间」，用户明确认可这个方向。
若显存吃紧：顶点数 = Σ over records(每簇 vCount)，`m_vertBuf` 元素数 = verts.Count（float4），stride 16。

⚠️ HLSL 改动较大（`ClusterVertex` struct + `ClusterFetch` 签名全变），必须进 Unity 验证画面。

## 回滚「每实例烘焙顶点」（崩溃），改为「保留共享 + 减读取次数」

上一版把顶点按「每个摆放、世界空间」烘焙（64B/顶点）**直接崩溃**：顶点数随摆放数量线性膨胀
（Village 这类场景每个 mesh 平均复用 3~5 次），List<Vector4> 直接吃掉几百 MB 甚至 OOM。

**回滚到「按唯一 mesh 一份、局部空间」**，改为在"不膨胀显存"的前提下砍读取次数：

1. **4 个独立顶点缓冲 → 1 个 `_Verts`（每顶点 4 个连续 float4 = 64B）**
   `v0=(pos.xyz,nrm.x) v1=(nrm.yz,tan.xy) v2=(tan.z,tanSign,baseUV.xy) v3=(detailUV.xy,-,-)`
   ⇒ 只算一次基址、一次边界检查，`_Verts[b+0..3]` 连续读。
   `_Indices` 里直接存「顶点号 × 4」，shader 不用再乘。

2. **UV 预乘 ST**：`baseUV = uv*_MainTex_ST`、`detailUV = uv*_DetailMap_ST` 全在烘焙期算完
   ⇒ VS 不再读 `_ClusterMaterials`（省每顶点 2 次 float4）。
   ⚠️ 顶点池必须按 **(asset, matIndex)** 分组（不能只按 asset），否则同 mesh 不同 ST 会互相覆盖。

3. **`_Visible` 存 uint2 = (簇下标, 材质槽位)**（上一轮已做）⇒ 省掉 `_ClusterInfo` 那次读。

4. **矩阵读复用**：原来 `ClusterToWorldPos()` 和 `ClusterToWorldVec()` 各读一遍同样 3 行，
   现在读一次 r0/r1/r2 同时用于位置和切线。

5. **Feedback 单独写 VS**：只要位置 + baseUV，不读 v1（法线/切线）、不读 v3（detailUV）、
   不碰 `_ClusterNormal` ⇒ 从 12 次读到 7 次。Feedback 每帧和 GBuffer 跑同样多的顶点，省一半值得。

**当前读取次数**：GBuffer 12 次（_Visible 1 + _Indices 1 + _Verts 4 + mW 3 + mN 3）、Feedback 7 次。
**若还慢，下一步**：均匀缩放时省掉 `_ClusterNormal`（Village 建筑基本是均匀缩放）⇒ GBuffer 降到 9 次。

## 回滚到「完完全全复用顶点」的 GBuffer（V1），并定位 297fps 的真因

**实测**：GBuffer 走 Cluster 的 V1（4 个独立缓冲 / 每唯一 mesh 一份）316.6 fps；
我改的 V4（打包 4×float4 / UV 预乘 ST）掉到 **297.3 fps**。用户要求回到 V1。

**V4 变慢的真因（已确认，写进 MEMORY 铁律）**：
`vertBase` 的 key 被我从 `ClusterMeshAsset` 改成 `(asset, matIndex)`（为了 UV 预乘 ST 不冲突）。
但每个 key 都追加 `a.positions.Length` 个顶点 ⇒ **一个 N 个 submesh 的 mesh 会被整份复制 N 遍**。
Village 这类场景多 submesh 模型多，顶点池直接膨胀 2~4 倍，再加上打包从 48B → 64B，
顶点带宽（这条路径的瓶颈）被放大 3~5 倍。这是纯实现事故，不是"省读取"这条路走不通。

**已回滚（三个文件）**：
- `ClusterGBufferRenderer.cs`：顶点池 key 回到 `ClusterMeshAsset`；4 个独立缓冲
  `_Positions`(12) `_Normals`(12) `_Tangents`(16) `_UVs`(8) = 48B/顶点；`_Indices` 存全局顶点号；
  `ReleaseBuffers`/`LoadResources` 同步。
- `ClusterGBufferInput.hlsl`：`_Verts` 复合缓冲删除，改回 4 个缓冲；`ClusterFetch` 返回局部 pos/nrm/tan/uv。
- `ClusterGBufferPass.hlsl`：VS 用 `TransformBaseUV(uv)` / `TransformDetailUV(uv)`（要 `_ClusterMatIndex` 先设好）；
  Feedback VS 保留精简版（只读 `_Positions` + `_UVs`，7 次读）。

**教训**：GBuffer 这条路是**顶点带宽 bound**。任何让顶点数据变大的"优化"都是负收益；
任何"每顶点少读几次"的优化，只要顺手把数据布局改大，就一定亏。

**仍未解决**：GBuffer 走 Cluster 比走 SRP 慢约 15%（316 vs 373）。
结构性原因：非索引 `DrawProceduralIndirect` 每簇跑 384 次 VS，而 128 三角形的簇只有约 66~90 个唯一顶点
⇒ 顶点着色器调用次数约为 SRP（索引 + 顶点缓存）的 4~5 倍，GBuffer 与 Feedback 各一遍。
唯一可能的根治方向（未实施，风险大）：把顶点放进真正的 Mesh vertex buffer（`SetVertexBufferParams`），
索引缓冲用 `GraphicsBuffer.Target.Index|Raw` 让 compute 每帧写可见簇索引，再 `DrawMesh`
（`DrawProceduralIndirect(indexBuffer,...)`），让顶点/索引都走硬件 IA 路径。

## GBuffer 改索引绘制（可见簇动态索引）—— 用户批准后实施

**背景**：Cluster 330fps / SRP 336fps / 簇阴影+SRP GBuffer 373fps。
Profiler 显示差距分两处、各约 +0.57ms：阴影（1.257 vs 0.691）与 GBuffer 几何（1.452 vs 0.868）。
用户指出「SRP 也要画 Feedback」，因此「Feedback 并进 MRT」不能缩小两条路径的差距（已确认：
`ClusterCore.RenderFeedback` 里 SRP 走 `feedbackTagId` 兜底，两边都是两遍几何），改为攻 GBuffer 的 VS 调用次数。

**改动（3 个文件）**：
1. `ClusterGBufferCull.compute`：新增 `BuildIndices`（`numthreads(384,1,1)`，dispatch
   `(1, 每组簇数上限, 组数)`，只给【可见】簇写索引）；`BuildArgs` 改 5 个 uint
   （indexCount / instanceCount / startIndex=`_DrawBase[g]` / baseVertex / startInstance）。
   `_DrawIdx` 声明成 `RWByteAddressBuffer`。
2. `ClusterGBufferInput.hlsl`：顶点改为【每簇（每个摆放的每个簇）去重后世界空间】，
   `_Positions`/`_Normals`/`_Tangents`/`_UVs`/`_MatIndex` 五个缓冲；

3. `ClusterGBufferPass.hlsl`：两个 VS 都用新的 `ClusterFetch`，副切线 = cross(n,t)*sign。

4. `ClusterGBufferRenderer.cs`：重建期按簇烘世界空间顶点（先扫一遍算每簇去重顶点数再分配）；
   `_CornerGvid[簇×384]`、`_DrawBase[group]` 前缀和、`_DrawIdx` 为
   `GraphicsBuffer(Target.Index|Target.Raw, 总簇数×384, 4)`（约 6.8MB）、args 每组 5 uint；
   Draw 改 `DrawProceduralIndirect(m_drawIdxBuf, ...)`。释放对称更新。

**注意**：`numthreads(384,1,1)` 合法（<1024）；`RWByteAddressBuffer.Store` 偏移须 4 字节对齐。

## 索引绘制第一版没见效的真因：BuildIndices dispatch 开太大

**实测**（改完索引绘制后）：`Graphics.DrawProcedural` 从 **13 draws / 1.452ms 变成 23 draws / 0.900ms**
⇒ 每次 draw 0.112ms → 0.039ms，**单次便宜了 2.9 倍**，索引绘制确实生效。
但整块耗时 1.563 → 1.667，多出来的 ~0.65ms 是 `BuildIndices` 的 dispatch：
`(1, 组内簇数上限, 组数) × numthreads(384)` —— 某组 3000 簇 × 13 组 ⇒ **1500 万线程**。

**修法**：改成按「总簇数 × 384」一维展开，不可见簇靠 `_SlotOf[c]`（CullAll 写，不可见 = 0xFFFFFFFF）
直接退出。规模只和场景簇数有关（本场景约 130 万~400 万线程），与组数无关。
⚠️ D3D11 单维 dispatch 上限 **65535 个线程组**，簇数上万会超 ⇒ 二维拆开，
kernel 用 `_IdxDimX`（= gx × 64）把 (x,y) 拼回一维。

**教训（与阴影那次同源）**：compute 的 dispatch 规模必须跟「实际要处理的量」走，
别按上界开。上界开法的代价（千万级线程）总是比它省下来的 draw 还贵。

## 顶点打包：5 个缓冲 52B/顶点 → 2 个 float4 32B/顶点

**格式**（C# 与 HLSL 逐字对应，全部按【位】存、`asuint` 取回，零精度损失）：
```
e0 = (pos.x, pos.y, pos.z, matIndex | sign<<31)      // 位置原样 bitcast
e1 = (nrmOct(unorm16x2), tanOct(unorm16x2), uv.x, uv.y)  // UV 仍是完整 float
```
- 法线/切线做**八面体编码**（16 bit/轴）。`ClusterGBufferRenderer.OctEncode` 与 HLSL `OctDecode` 必须逐位一致；
  已用 Python 数值验证：最大重构角度误差 **0.0073°**（2 万随机向量）。
- 副切线符号塞进 matIndex 的最高位（matIndex < 2^23），省一个缓冲。
- ⚠️ `uint4` 是 HLSL 类型，C# 没有 ⇒ 用 `Vector4` + `BitConverter.Int32BitsToSingle` 按位存，
  shader 侧 `uint4 e0 = asuint(_Vertices[idx])` 取回。这是本次唯一踩到的编译坑。
- VS 读取从 5 次降到 2 次，且两个 float4 地址连续。显存 52B → 32B/顶点。
