## 排查：级联阴影「缺一块」（用户报告 cascade 1 有不该被剔除的东西）

### 一、先证明剔除的几何口径是精确的（重要结论，别再往这个方向返工）
平行光的级联是**正交投影，且投影方向 = 光线方向**。正交投影沿光方向不改变光空间 x/y，
所以「簇包围球在光空间 x/y 盒子外」⇔「它投出的阴影也落在盒子外」。
⇒ 6 平面剔除（实际只有 4 个 x/y 平面生效，见下）对平行光级联是**精确**的，
**不可能在盒子内部挖出洞**。盒子内部的阴影缺块一定来自别处。

副产物结论（值得记住）：
- `GeometryUtility.CalculateFrustumPlanes` 是 Gribb-Hartmann，两个 z 平面在
  **reversed-Z** 下都退化成恒真（z∈[0,w] 时 z>=-w 与 z<=+w 恒成立）
  ⇒ 深度方向完全不剔，只在 x/y 剔。这是"安全"的（多画不少画），不是 bug。
- `minTexels` 是**唯一**与相机无关的尺寸型剔除，且 projScale = tileSize*0.5*|proj.m11|，
  实测量级下（2048 tile / 60m 级联 ≈ 34 texel/m）半径 0.05m 以上都不会被剔 ⇒ 基本不起作用。

### 二、真正修掉的 bug：镜像实例（负缩放）的绕序
Unity 内建渲染器对 **det < 0 的 MeshRenderer 会自动翻 culling**，所以 SRP 路径正常；
而我们的 `DrawProceduralIndirect` 没有这层逻辑 ⇒ **Cull Back 会把镜像实例的几何/阴影整块剔掉**。
- 症状完全吻合用户描述：「该是完整的一个东西，却缺了一块」，且**只在 Cluster 路径出现**。
- 修法（烘焙期、运行时零成本）：
  - `ClusterShadowRenderer.Rebuild`：`det < 0` 时索引写 `i0,i2,i1`；
  - `ClusterGBufferRenderer.Rebuild`：同样翻 `_CornerGvid`，并把副切线符号取反
    （反射下 `cross(Rn,Rt) = -R·cross(n,t)`，真实副切线是 `R·b` ⇒ 符号必须反）。

## 追加：排除 Cull Back，锁定「正交级联的 z 范围裁剪」

用户实测：`clusterShadowTwoSided = 1` 之后仍然缺块；且**只有贴近水车时**才断，拉远就完整，太阳没动。
⇒ `Cull Back` 与双面无关（用户的推理正确：剔除模式只跟光方向有关，与相机距离无关）。

**修正我之前的一个错误证明**：我此前断言「级联剔除对平行光是精确的、盒内不可能缺块」——
这只证明了 **x/y**。**沿光轴的 z 范围完全没算**。

正交阴影投影的 z 范围只是 cullingSphere 附近的一条「板」：
投射物 x/y 在盒内、但沿光轴超出这条板 ⇒ **被光栅化器整块裁掉**，
而它落下的阴影在盒内 ⇒ 阴影凭空缺一块。板厚 ∝ 级联尺寸 ⇒「贴近就缺、拉远就好」。
太阳角度低（本场景影子很长）时投射物沿光轴铺得远，最容易触发；水车顶部支臂离地高，正好中招。

**已加修复开关**（默认 1 = 行为完全不变）：
- `ClusterAssembleAsset.clusterShadowDepthPad`（1~8）→ `ClusterShadowRenderer.PadOrthoDepth`
- 实现：正交下 `z_ndc = m22·z + m23`，中心 `= -m23/m22`；`m22 /= pad; m23 /= pad`
  ⇒ 中心不变、斜率变小 ⇒ z 范围扩大 pad 倍。
- **关键**：在 `Shadows.cs` 拿到 `projectionMatrix` 后立刻替换，这样
  「图集采样矩阵 `ConvertToAtlasMatrix(proj*view)`」「cluster 渲染 `worldToClip`」
  「`SetViewProjectionMatrices`（cutout 用）」三处天然一致，不会出现两侧深度约定不符。
- 代价：深度精度按 pad 倍下降（pad=2 ≈ 少 1 bit）+ 极小概率 acne。

**待用户验证**：pad=2（不行再 4）。
- 补上了 ⇒ 确认是 z 裁剪，可以把 pad 定在能覆盖的最小值，或改成"按投射物沿光轴的展开量自适应"。
- 完全没反应 ⇒ 不是 z 裁剪，再把 `clusterForceAll` 打开区分「剔除 vs 绘制/登记」。

## 定案：正交级联深度范围必须由【簇集合自建】（pad=2 实测修复）

**用户的判断正确**：Unity 的级联正交矩阵**只按 `ShadowSplitData.cullingSphere` 拟合**，
沿光轴厚度 ≈ 2×球半径，**完全不看场景里有什么**（不是"看场景里没物体就设小"，而是它压根不看场景）。
Unity 自己唯一的补救是 `light.shadowNearPlane`（`nearPlaneOffset`），只给**近侧**加余量。
我们的投射物是自建的簇集合 ⇒ Unity 不知道分布 ⇒ 必须自家把厚度撑开。

**已实现自动模式**（默认开，`clusterShadowAutoDepth = true`）：
```csharp
need = |dot(sceneSphereCenter - cascadeSphereCenter, light.forward)| + sceneSphereRadius;
have = splitData.cullingSphere.w;              // 原板半厚
pad  = clamp(max(manualPad, need / have), 1, 64);
projectionMatrix = ClusterShadowRenderer.PadOrthoDepth(projectionMatrix, pad);
```
- `sceneSphere` 在 `Rebuild` 里由全部簇的 bounds 求 AABB → 球，`TryGetSceneBounds()` 暴露。
- 必须用 `light.forward`（= 光行进方向），只看 |投影|，符号无所谓。
- **为什么撑大不会引入 acne**：工程的阴影偏置是 `surfaceWS.position + normalBias`，
  normalBias = `surfaceWS.normal * directional.normalBias * _CascadeData[i].y`，**世界空间、投影前应用**
  ⇒ 与 z 范围无关。深度只是按 pad 倍变粗，D32 下几百米仍是亚毫米级。

**教训（写进 MEMORY）**：任何「自建投射物集合」的阴影路径都必须自建三个量：
x/y 盒子、**沿光轴深度范围**、以及偏移量。少一个就会在某个相机距离下凭空缺块。

## 修：Cluster 阴影 `PadOrthoDepth` 偏侧（近侧仍被裁 ⇒ 近级联阴影缺块/全错）

用户实测 Cluster 模式阴影"全错"而 SRP 正常。查 `Shadows.cs`：pad 在 Cluster 模式才套（`if(useCluster)`），
且渲染侧(`cluster.Draw` 的 worldToClip) / 采样侧(`dirShadowMatrices=ConvertToAtlasMatrix(paddedProj*view)`) / cutout(`SetViewProjectionMatrices(m_cascadeProj)`)
**三处都用同一 padded 矩阵 ⇒ 不是渲染/采样错位**，问题在 padding 本身。

**旧实现** `m22/=pad; m23/=pad`：正交 `ndc=m22·z+m23`，同除 pad 等价于"围绕 **ndc=0 边**"展开 ⇒ 只把**远离光的一侧**拓宽 pad 倍；
簇球是沿光轴**双侧**超出原板的球，朝光近侧超出部分照样被光栅化器裁掉 ⇒ 近处级联阴影缺块（"贴近才缺、拉远就好"只解决了一半，现暴露成"全错"）。

**修正**：`m22/=pad; m23=(m23+0.5*(pad-1))/pad` ⇒ 板中心(ndc=0.5)不动、z 范围对称 ×pad，近/远两侧都覆盖（旧实现覆盖的超集，只可能修好）。
C# 编译 180 文件 0 错 0 警告。README「沿光轴深度范围自建」段已同步。待用户进 Unity 验证 Cluster 阴影是否恢复。

## 修：Cluster 阴影把「父级被禁用」的山也登记进阴影（有山影却看不到山）

用户报告场景里看不到山，却有一道山影。`Terrain` 父级被禁用，其下 `terrain_far_01 / terrain_near_01`
带 `ClusterObject`、mesh 就是山。

**根因**：`ClusterShadowRenderer.ScanScene()` 用 `FindObjectsInactive.Include`（故意含 disabled，
给 LOD 各级打 bit29），但筛选只查 `mr.enabled`（组件自身开关）。父级被禁用时子物体
`MeshRenderer.enabled` 仍是 `true`、`activeInHierarchy == false` ⇒ 漏过跳过判断，被登记进 cluster 阴影缓冲。
而 GBuffer 路径靠 `OnEnable` 登记（禁用层级不触发 OnEnable）⇒ 山不显示却投山影。

**修法**：在 `ScanScene` 循环内 `!mr.enabled` 之前加一条 `if (!mr.gameObject.activeInHierarchy) continue;`，
把整条层级被禁用的物体（含山）从阴影登记排掉。GBuffer 路径无需改（OnEnable 已正确跳过）。
此改可逆：`Terrain` 重新启用后 `activeInHierarchy` 变 true，山影自然恢复。

**顺手修编译错误**：`Editor/ListClusterObjects.cs` 第 26/28/32 行误用 `MeshRenderer.sharedMesh`
（该属性不存在，mesh 在 `MeshFilter.sharedMesh`）。改为先 `GetComponent<MeshFilter>()` 再取 `mf.sharedMesh`。

**待用户验证**：① 禁用 `Terrain` 后山影是否消失；② `ListClusterObjects.cs` 已编译通过（Unity 侧）。

- raw 远大于 actual ⇒ 以前在白撑，C 有效；
- raw ≤ 上限 ⇒ pad 本就不大，C 帮不上（此时大头在 cull / 草 pass）。

## 【重要】B 方案（草阴影实例化）实测失败并已回滚 —— 结论：切换不是瓶颈

用户实测：把草阴影从 SRP `context.DrawShadows` 搬到 cluster 的 DIPS 通道（`ClusterGrassShadowRenderer`
+ `ClusterGrassShadow.shader` + `ClusterGrassShadowCull.compute`）后，**没变快、反而更慢**。

已回滚（2026-10-28）：
- `Shadows.cs` 恢复 cutout 的 SRP `context.DrawShadows` 分支（保留 bit29 mask 收紧 + 存/还原）。
- `Shadows.cs` / `DefferPipeline.cs` 移除全部 `ClusterGrassShadowRenderer` 调用与 Dispose。
- 三个新文件**保留但零调用点**，类头已标注「已停用，别接回去」。

**为什么失败（本质原因，别再往这个方向返工）**：
1. 「cluster 间接绘制 → SRP DrawShadows」的路径切换**不是成本来源**。SRP 内部同样要把
   SRPBatcher 的 batch flush 成实例化 draw，两边的"切换"本质相同。用户这个判断是对的。
2. 那 0.325ms 是 SRP 用**硬件顶点缓冲 + 顶点后变换缓存**画草几何的**真实工作量**。
   改成过程式顶点（SV_VertexID 查 _Positions/_UVs/_InstanceMatrices/_Visible）后，
   每顶点多 4 次 structured buffer 读 + 丢失顶点缓存复用 ⇒ 更贵。

**真正的 Cluster 阴影差距（3 条结构性，与切换无关）**：
| 差异 | Cluster | SRP |
|---|---|---|
| 索引展开 BuildIndices | 每帧铺「可见簇×384 顶点号」，几百万次散射写 | **不需要**，直接用原始 index buffer |
| 剔除粒度 | 簇包围球（32³ 块）命中就整簇画 ⇒ 多送三角形 | 逐 renderer/逐 LOD，精确 |
| z 板 pad | 沿光轴撑大（修缺块的代价）⇒ 近侧图元不再被裁 | 不 pad，紧贴 cullingSphere |

**历史数据早就说明簇阴影是负收益**：固定相机 纯SRP 337 / **簇阴影+SRP GBuffer 374** / 全簇 350 fps。
即：簇化 GBuffer +11%（真收益），再叠簇阴影 −6.4%（亏）。
⇒ **下一步方向：Cluster 模式只接管 GBuffer / RVT Feedback，阴影整体交回 SRP**，
预期回收 ~1.1ms（1.87ms → 0.77ms）。待用户确认接入方式（加开关 or 直接改语义）。

## 阴影额外支出定位：pad 用全场景包围球撑每个级联（实测 56×，已改精确算法）

**实测日志（本次痛点）**：
```
级联 0 pad: raw=56.83× actual=16.00×（触顶）
级联 1 pad: raw=16.76× actual=16.00×（触顶）
级联 2 pad: raw= 9.95×
级联 3 pad: raw= 6.13×
```
**根因**：`Shadows.cs` 的 pad 公式
```
need = |dot(全场景球心 − 级联球心, 光向)| + 全场景半径
pad  = need / 级联球半径
```
用【全场景包围球半径 sr】当每个级联的余量 ⇒ 等于要求每个级联覆盖整场景沿光轴的跨度。
级联 0 球半径最小 ⇒ pad 最大（56×）⇒ 光栅化器彻底不裁近侧，整场景三角形都要走完
setup+raster 才被深度测试丢掉。**这就是「场景内容变多 ⇒ 阴影变慢」的传导链**：
物体更多更分散 ⇒ sr 更大 ⇒ pad 更大。

**正确口径**：平行光级联是正交投影且投影方向 = 光线方向 ⇒ 沿光轴不改变光空间 x/y。
所以一个簇的阴影只可能落进「光空间 x/y 与其相交」的那个级联；其余簇沿光轴再远也无关。
⇒ 只统计 x/y 相交的簇，取它们沿光轴的 [minZ,maxZ]，pad = 刚好盖住这段的倍数。

**改动**：
- `ClusterShadowRenderer`：
  - 新增 `m_cpuBounds`（Rebuild 时的簇包围球 CPU 副本）与 `ComputeDepthPad(...)`。
  - 缓存：key = (该级联剔除球, 光方向)，球移 >1m 或光转 >1° 才重算
    ⇒ **静止场景零 CPU 开销**（否则每帧数千簇×4 级联的变换约 0.5ms）。
  - 加 10% 余量（缓存不保证每帧精确）；`Clamp(1,16)`。
  - 删 `m_sceneCenter/m_sceneRadius/TryGetSceneBounds`（不再需要，省一次 O(簇数) 遍历）。
  - **顺手修真 bug**：`clusterCount = allIdx.Count / 384` 向下取整 ⇒ 末簇不满 128 三角形时
    clusterCount < 簇数 ⇒ `boundsBuf` 分配偏小（SetData 失败/截断）+ 尾簇被漏掉。
    改为 `clusterCount = allBounds.Count`，并补 0 索引补齐（退化三角形，不产生深度）。
- `Shadows.cs`：pad 改调 `ComputeDepthPad(i, light.forward, viewMatrix, cullingSphere, projectionMatrix)`，
  保留 `clusterShadowMaxDepthPad` 作保险上限。

**深度约定（关键，别再搞错）**：`PadOrthoDepth` 的 `newM23=(m23+0.5(pad-1))/pad`
只在 **ndc ∈ [0,1]（D3D）** 下等价于「围绕板中心(0.5)对称扩张 pad 倍」，
而该式正是实测修好缺块的那版 ⇒ 反解 z 范围必须用 `(0-m23)/m22` 和 `(1-m23)/m22`。
用 [-1,1] 反解会把厚度算成 2 倍 ⇒ pad 偏小 ⇒ 缺块。

**待 Unity 验证**：① pad 日志应从 56/16.8/9.9/6.1 掉到 1~2；
② 阴影是否缺块（重点看远侧/贴近）；③ 阴影 pass 耗时与帧率。

## 精简：BuildIndices 改为「每簇一个线程组」+ 缓冲按实际级联数分配

### 1. BuildIndices 组数 ÷6（GBuffer 与阴影两侧）
旧：`numthreads(64,1,1)` + 一维展开 `idx = id.y*_IdxDimX + id.x`
⇒ 组数 = ceil(簇数×384/64) = **簇数×6**。31854 簇 ⇒ 19.1 万个线程组（GBuffer 侧簇数更多，还要翻）。
新：`numthreads(384,1,1)`，dispatch = `(1, min(簇数,65535), ceil(簇数/65535))`
⇒ 组数 = **簇数**。同簇 384 线程读同一个 `_SlotOf[...]` 地址 ⇒ 硬件广播。
线程总数不变（仍是 簇数×384），省的是**线程组调度开销**。

改动：
- `ClusterShadowCull.compute` / `ClusterGBufferCull.compute`：`_IdxDimX` → `_IdxDimY`，kernel 改 384 线程/组。
- `ClusterShadowRenderer.cs` / `ClusterGBufferRenderer.cs`：dispatch 改 `(1, idxDimY, idxDimZ)`。

⚠️ `numthreads` 必须 == `_TrisPerCluster*3`（当前 128×3=384）。改 TrisPerCluster 要同步改两处 compute。

### 2. `MaxCascades` 8 → 4（实际只用 4）
`ShadowSetting.Directional.cascadeCount` 是 `[Range(1,4)]`，默认 4。
但阴影缓冲按 `MaxCascades=8` 分配 ⇒ **`_DrawIdx` 白占一倍**：
`8×31854×384×4B = 391MB` → 改 4 后 **196MB**。`slotBuf`/`visibleBuf`/`planesBuf` 同理减半。
⚠️ 必须与 `cascadeCount` 上限一致；否则 `AddCascade` 会静默丢弃新增级联（`if (cascadeCount >= MaxCascades) return;`）。

### 本轮不做的（已评估）
- **DispatchComputeIndirect 按可见数派发**：不可靠。4 个级联的可见簇累加后可能**比总簇数还多**
  （每级联可见 50% ⇒ 2 倍），只有可见率很低时才划算。放弃。
- **Cull Off/小簇剔除恢复**：量级太小。
- **硬件 IA 路径**（SetVertexBufferParams + DrawMeshInstancedIndirect）：能消掉阴影 draw 那 0.55ms
  与 SRP 的差，但属架构级改动，风险高，暂不动。

**状态**：C# 181 文件 0 错 0 警告。**HLSL 改动必须进 Unity 验证**：
① 阴影是否正常（尤其镜像实例/绕序）；② GBuffer 是否黑屏（索引铺错会整片黑）；
③ 看 GPU Usage 堆叠图的 ShadowDepth 档前后对比。

## ★ 阴影 pad 的真正元凶：一个半径 672m 的平面被当成投射物

诊断日志（`ComputeDepthPad` 里新加的「最撑板的簇」打印）一击命中：
```
级联 0 pad=16.00×（x/y 命中 1030 簇 / 共 31858）
最撑板的簇：世界中心 (0.0,-1.7,50.0)，半径 672.68m
            需深 729.3m（原板半厚 12.4m ⇒ 58.8×），投影约 31804 texel
```
⇒ 场景里有个**半径 672m、中心在地面高度**的物体（用户口中"最底下的 Plane"）被登记进了 cluster 阴影。
它的簇包围球横跨整个场景，`ComputeDepthPad` 为了让这个球落进级联，把 z 板撑到 58.8×。
**z 板一撑大，光栅化器就不再裁近侧 ⇒ 阴影 pass 全部三角形走完 setup+raster 才被深度丢弃。**

**修法**（已实现）：`ScanScene` 用 `mr.bounds.extents` 的最大分量做半径，
超过 `MaxCasterRadius = 200m` 的 MeshRenderer **不进 cluster 阴影**，并打警告（限前 4 个）。
- 这类物体本身就是接收面（地面），投影无意义。
- 若确实需要（起伏地形投山影），调大 `MaxCasterRadius` 或让它走 SRP 阴影。
- Rebuild 日志新增 `超大 N` 计数。

**待验证**：pad 应掉到 1~2、`Shadows` 应明显下降；确认地面/地形没有出现"该有的影子没了"。

## 关于「阴影级联 z 剔除」的物理限制（结论，别再试）
正交投影沿光轴不改变 x/y ⇒ **x/y 在盒内的簇，其影子一定落在盒内**，z 再远也必须画。
所以阴影侧**不存在"安全的 z 剔除"**，简单按 z 砍一定缺块（这正是当初引入 pad 的原因）。
唯一可行的替代是「紧板 + 宽板双 pass」，但先把超大投射物排除后大概率不需要了。

## Hi-Z 遮挡剔除（未实施，已设计方案）
- 只对**相机 GBuffer** 有意义；阴影从光源看，遮挡剔除不适用。
- 不需要额外 RT：对上一帧 depth 降采样成 mip chain（≈1.33× 单张深度）。
- **降采样必须取「最远深度」**（保守），取最近会过度剔除 ⇒ 漏画。
- 复用上一帧 ⇒ 相机快速移动时，上一帧屏幕外、本帧刚进画面的簇会被误剔；
  补偿：对「上一帧视锥外的簇」强制不剔（或强制可见）。
