## Cluster 全屏性能剖析（Cluster 3.917ms vs SRP 2.991ms，差 ~0.93ms）

用户截图（GPU ms）：
- **Cluster**：Main Camera 1.94 / Shadows 0.875~1.083(6 次 DrawProcedural) /

- **SRP**：RenderLoop.ScheduleDraw 1.454（全部几何）/ Shadows 1.044 / Main Camera 0.476（blit/光照）。

结论：
- 簇 GBuffer 片元与 SRP 完全共用、VS 只 5 次缓冲读 ⇒ **慢不是逐片元重，而是绘制无排序的过度绘制**

  BuildIndices 0.14 还贵）。这是最典型的浪费。

## 已做优化（C# 编译通过 .workbuddy/compile_check.py；HLSL 需进 Unity 验证）

1. **GBuffer：`BuildArgs` 合并进 `BuildIndices`**（ClusterGBufferCull.compute + ClusterGBufferRenderer.cs）
   - BuildIndices 开头：`idx < _GroupCount` 的线程顺带写 `_Args`（5 个 uint）。
   - 删掉 C# 里 kArgs 的 FindKernel + dispatch；`_Args/_Counter/_DrawBase` 本就绑到 kIdx，顺序安全。
   - 整帧 compute 4 → **3 个 dispatch**，省 ~0.15ms。
2. **阴影：`BuildArgs` 合并进 `BuildIndices`**（ClusterShadowCull.compute + ClusterShadowRenderer.cs）
   - 关键点：原 BuildIndices 读 `_Args[k*5+2]` 判静态段；改成**由 `_Counter` 现算 `base`**
     （`full ? 0 : oneCopy*(k+1)`），从而同一 dispatch 内「写 args」与「算 base」无读写竞争。
   - 删掉 kArgs dispatch（及 cGroups）。
   - 阴影 cull 4 → **3 个 dispatch**（CopyStatic 本就只在重建后跑一次），省 ~0.15ms。
3. **CPU**：两处 `foreach(kernel){ SetInt(...) }` 的全局常量提出循环（SetInt 是全局、不区分 kernel，
   原来重复设 4 遍）。纯 CPU/GC 清理。
- 预期合计省 ~0.3ms ⇒ ~3.6ms，仍高于 SRP ~0.6ms。

### 本次剖析的最终认识（重要，供以后大场景判断）
- **簇 GBuffer 在 GPU 上是小幅负优化**（本场景约 +0.33ms 绘制 +0.29ms 剔除）：根因是「每 128 三角形拆簇 ⇒ 边界顶点复制」

- **簇阴影比 SRP 慢约 0.79ms**（Hi-Z 关时的实测）：同样 4 级、同样几何，但静态簇光绘制就 1.127ms > SRP 全量 0.905ms，
  原因同上（顶点路径更贵）。SRP 阴影的 42 次 draw 靠实例化+硬件顶点，已是该场景的最优路径。
- **簇真正的用武之地**：海量物体（CPU draw 提交 O(N) 成瓶颈，簇恒定 4 次 draw = O(1)）+ 严重遮挡（Hi-Z 有效）。
  小场景 / 中等物体数下，SRP 的硬件路径更优。这是「规模问题」不是绝对快慢。
- 已落地且保留的优化：GBuffer/阴影各自把 `BuildArgs` 合并进 `BuildIndices`（各省 ~0.15ms、4→3 dispatch）；
  簇 GBuffer 深度预 pass（1.449→1.172ms）；两处 `foreach(kernel){SetInt}` 常量提出循环。

## 灯光系统（Tiled Deferred）评估 + 面光源接入

### 现状结论：设计是合理的
链路：GBuffer → 全屏光照 pass。方向光 ≤4 每像素全算；其他光（点/聚/面）≤`_MAX_OTHER_LIGHT_COUNT`，
`ClusterLight.compute` 按 **16×16 像素 tile** 取深度 min/max，逐灯做「视图空间深度区间 + tile 锥 AABB」测试，
原子追加进 groupshared，每 tile 最多输出 `MAX_LIGHT_COUNT_PER_TILE = 32` 盏；光照 pass 只遍历该 tile 的灯。
= 标准 Tiled Deferred Light Culling，没有结构性错误。

### 本次修掉的 3 个真 bug（都不是性能问题，是正确性）
1. **`lightIndex = groupIndex` 把灯数硬绑在 256 线程数上**：超过 256 盏的灯永远不参与剔除（静默丢光）。
   改为标准跨步循环 `for (i = groupIndex; i < count; i += THREAD_COUNT)`，灯少时只跑一圈、灯多自动多圈。
   旧代码里 `uint passCnt = ceil(count/256)` 是**算了但从没用**的死代码。
2. **groupshared 越界写**：`tileVisibleLightIndices[offset] = lightIndex` 没有 clamp，
   tile 内灯数 > 数组容量时会踩坏别的 groupshared 变量。现加 `if (offset < MAX) `。
   同时把数组从 256 降到 32（= 实际输出上限），groupshared 从 1KB → 128B，提占用率。
3. **tile 计数没 clamp 就写进 args**：`indices` 只写了前 32 盏，若 args 存了 >32 的计数，
   光照 pass 会读到**相邻 tile 的灯索引** ⇒ 光照串台。现写 args 时 `min(count, 32)`，Lighting.hlsl 再防御性 clamp 一次。

### 上限策略（回答「相机内超过 256 怎么办」）
- 业界做法：① 全局灯列表本身就是 StructuredBuffer，线程数不该成为灯数上限（跨步循环，已做）；
  ② 真超上限时按**重要度裁剪**（保留最强的），而不是按遍历顺序截断。
- `_MAX_OTHER_LIGHT_COUNT` 256 → **1024**（1024×112B = 112KB，显存可忽略）。灯少时零成本，
  因为它只是 buffer 大小，剔除循环跑的是实际 `_OtherLightCount` 圈数。
- 溢出时按 `luminance(finalColor) × range²` 降序保留前 1024，丢最弱的；只在真超限时排序（`List.Sort` + 静态比较器，无 GC），
  且只在丢弃数量变化时打一次 LogWarning。旧代码是「遍历顺序前 256」，丢掉的可能恰恰是最亮的。

### 面光源（方案 A：MRP 代表点近似，已实现）
- `OtherLight` 结构 **+2 个 float4**：`lightAreaRight` / `lightAreaUp`（轴向量已乘半宽/半高，`.w` = 半宽/半高）。
  **判定约定：`lightAreaRight.w > 0` ⇔ 面光源。** 三处必须逐字一致：`Lighting.cs` / `Light.hlsl` / `ClusterLight.compute`。
- C# `SetupRectangleLight`：`localToWorldMatrix` 的 col0/1/2 归一化（去缩放）当 right/up/forward，
  发光面法线 = `-forward`；`light.areaSize` 取半宽半高；`range = max(range, 半对角线)` 让 tile 剔除直接复用点光球测试。
- shader `AreaLightRepresentativePoint`：着色点投到发光面 → 钳制进矩形 → 最近点当点光。
  `softR = (halfW+halfH)/2`，`1/d²` 抹平为 `1/(d² + softR²/2)`（面积光柔化的最省事近似）；
  `sideAttenuation = saturate(dot(areaNormal, 着色点→中心) × 3)` 只照正前方、边缘软过渡。
- **限制**：高光仍是点光形状（要真矩形高光必须 LTC+LUT）；**面光源不投影**（area shadow 太贵，`lightShadowData` 给零）；
  `GetOtherLightByPosition` / `_SSS` 版本没加面光分支（会退化成中心点光），体积光路线要用时再补。
- ⚠️ 点光/聚光**必须显式清零** `lightAreaRight/Up`：`NativeArray` 是 `UninitializedMemory`，
  不清会残留上一帧面光的轴向量 ⇒ 被误判成面光源。

### 明确「不做」的（用户决定）
- **每 tile 32 盏的「最强 N 排序」不做**：32 够用，且溢出几乎不发生，排序（groupshared bitonic）是纯浪费。
- **3D 簇（tile × 深度切片）不做**：灯少时收益为零，纯加复杂度。
- **体积光**：用户「以后可能加」，先记着 —— 那时才需要 `GetOtherLightByPosition` 的面光分支 + 3D 切片。

### 面光源补充：Gizmo + 「不投影」显式化
- `AreaLightSource` 加 Gizmo：**矩阵用 `TRS(pos, rot, scale=1)`**（不是 `localToWorldMatrix`），
  因为 width/height 是世界米数、shader 侧也用归一化的 `t.right/t.up` ⇒ Gizmo 与实际渲染口径一致，不吃缩放。
  未选中画线框（一眼区分场景里哪些是面光源），选中画半透明面 + 发光方向箭头（局部 -Z）+ 四角引出线 + range 球。
- **面光源不投影这件事是显式的**：`SetupPointLight` 面光分支直接 `return`，不调 `ReserveOtherShadows` ⇒
  不占 `maxShadowedOtherLightCount(16)` 里点光要用的 6 个 cube tile，`RenderPointShadows` 的 6 次 DrawShadows 完全不跑。
  （阴影是「谁 reserve 谁才画」：`RenderOtherShadows` 只遍历 `shadowedOtherLights`。）
- 为什么不做「1 面覆盖半球」的便宜阴影：Unity 的 `DrawShadows` 只吃
  `ComputeSpotShadowMatricesAndCullingPrimitives` / `ComputePointShadowMatricesAndCullingPrimitives` 给的 splitData，
  没有面光源这种投影；自定义 fov≈170° 的 perspective 走不通，只能自建剔除+自绘，成本远大于收益。
  ⇒ 真需要阴影时，另放一盏 Spot / Point 当「阴影代理灯」。
- `AreaLightSource.OnEnable` 检测 `light.shadows != None` 打一次警告（告知设置被忽略）；
  `OnValidate` 检测 light 类型不是 Point 时警告（面光只在 Point 下生效）。

### 坑：`State comes from an incompatible keyword space`（ImageFilters::Blit）
现象：Game 视图每帧报 assert，Expected = `CustomRP/Defferer/DefferCamera`(15 keyword)，
Actual = `Hidden/Internal-Loading`(4 个 stereo)，堆栈顶是 `ImageFilters::Blit` → `LocalKeywordState::Union`。
成因：CommandBuffer 里挂了 DefferCamera 的 15 个 global keyword（`_USE_CLUSTER`/`_DIRECTIONAL_PCF*`/
`_OTHER_PCF*`/`_CASCADE_BLEND_*`/`_MY_LIGHTING`），此时若有一次「用 `Hidden/Internal-Loading` 做的内部
blit」（Unity 用来 **load 相机目标/RenderTexture 的已有内容**），Union 两个不兼容的 keyword 空间 ⇒ 断言。
**根因（最终定位）**：`ImageFilters::Blit` 就是 **`CommandBuffer.Blit` 的实现**（不是 Unity 的 present）。
当源纹理「不可直接采样」时，Unity 会先插一次 `Hidden/Internal-Loading` 的内部拷贝：
- `BuiltinRenderTextureType.CameraTarget` = 正在写入的相机目标 ⇒ 要 resolve；
- **`null` 的语义是「把当前 render target 拷到 dst」** ⇒ 同样要 load（所以改 null 没用！）；
- 当前 MRT 的附件（如 `GBufferIds[0]`）同理。
而 `Hidden/Internal-Loading` 的 local keyword space 只有 4 个 stereo keyword，
与 DefferCamera 的 15 个不兼容 ⇒ `LocalKeywordState::Union` 断言。
（`_ACCURACY_NORMAL`/`_MY_LIGHTING` 在 C# 里从未被设置，与 keyword 开没开无关。）
**最终方案**：`DrawGBufferFinal` 用一个 **1×1 临时 RT 当占位源**：
`GetTemporaryRT(dummy,1,1) → Blit(dummy, dst, material, _GBufferDraw) → ReleaseTemporaryRT`。
源颜色根本不用（片元只读 GBuffer；`_SourceTexture_TexelSize` 恒 0）。
另外两处 `SetRenderTarget(CameraTarget)` 无参重载（= Load）也改成显式 `DontCare, Store`。
2. `Cleanup()` 的 `SetRenderTarget(CameraTarget)` → 显式 `DontCare, Store`（无参重载 = Load ⇒ 触发内部 load blit）。
3. `MipsDebug` 调试路径同 2。
**其余已知的无材质 Blit（未改，仅在 AO/SSR 开启时才会执行）**：
`AmbientOcclusion.cs:61 buffer.Blit(colorTexId, TempBufferId)`；`SSR/StochasticScreenSpaceReflection.cs:356/409
buffer.Blit(GBufferDepthId, SSR_HierarchicalDepth_RT)`。若还报，优先关 AO/SSR 验证。

### 另一个坑：HLSL `min(uint, int)` 是 "ambiguous function call"
`min(tileVisibleLightCount, MAX_LIGHT_COUNT_PER_TILE)`（uint vs int 字面量）会编译失败（X3061），
因为 `min` 有 int/uint/float 多个重载，两边类型不一致时多个候选都能靠隐式转换通过。
⇒ 必须显式转型：`min((int)buf[i], 32)` 或 `min(u, (uint)32)`。
**连带症状**：`DefferCamera` 编译失败 ⇒ material 失效 ⇒ `buffer.Blit(..., material, ...)` 退成
`Hidden/Internal-Loading` ⇒ 顺带报上面那个 keyword 断言（表面看像 Blit 问题，真凶是编译失败）。

### 面光源方向语义（踩坑，务必记住）
`OtherLight.lightDirectionsAndMasks.xyz` 在本管线里存的是 **【指向光源的方向】= -发射方向**：
- `SetupSpotLight` 原代码就是 `-visibleLight.localToWorldMatrix.GetColumn(2)`；
- 原因：shader 里 `light.direction` 是「表面→光源」，锥形衰减算 `dot(spotDirection, light.direction)`，
  所以 `spotDirection` 必须与「表面→光源」同向。

而面光源 MRP 需要的是 **【发光面朝外的法线】= +发射方向**，两者**差一个负号**。
❌ 第一版直接把 `lightDirectionsAndMasks.xyz` 当 `areaNormal` 用 ⇒
`AreaLightRepresentativePoint` 里 `planeDist = dot(surfacePos - center, areaNormal)` 恒为负
⇒ 永远 `return center` ⇒ 面光源退化成一个中心点光源，观感就是「射灯/点光」。
✅ 修法：`float3 toLightAxis = normalize(otL.lightDirectionsAndMasks.xyz); float3 areaNormal = -toLightAxis;`
   - MRP 与 `sideAttenuation` 用 `areaNormal`（发射方向）；
   - `otherShadowData.spotDirectionWS` 用 `toLightAxis`（与 Spot 同口径，normal bias 的
     `dot(surfaceToLight, lightPlane)` 才是正距离）。
   - `side = dot(areaNormal, normalize(surfaceWS.position - lightPosition))`（「表面-中心」，不是「中心-表面」）。

### Unity 的 Spot 锥沿 +forward
`transform.forward`（+Z）就是光射出方向。Gizmo 里箭头/锥体必须画在 +Z；
第一版画在 -Z，与场景里的 Spot 锥正好反向。

### 不要给 `GetComponent<AreaLightSource>()` 做「查过没有」的缓存（连 Scene 里挂都会中招）
`RenderPipelineBase` 是 `protected Lighting lighting = new Lighting();`，而 `DefferPipelineAsset`
**只创建一次 pipeline**（`defferPipeline != null` 就复用）⇒ `lighting` 实例**跨帧、跨 Play 持久**。
所以「这盏灯没有 AreaLightSource」这条缓存从**第一帧**就记死了，之后无论是在 Scene 还是 Play 里
挂组件，都不会重新查 ⇒ 表现为「挂上完全没反应，必须重进 Play / 重开场景」。
⇒ 直接每帧 `GetComponent`，不缓存（灯只有几十盏，开销可忽略）。
另外编辑器**不会因为多了一个不认识的组件就重绘 Scene 视图** ⇒ `OnValidate`/`OnEnable` 里补
`UnityEditor.SceneView.RepaintAll()`，才能做到「一挂就有反馈」。

### 面光源阴影的视锥：near 面贴到发光面（已实现）
Unity 的 Spot 阴影 = 一个**透视**视锥，三要素：
`near = light.shadowNearPlane`、`far = light.range`、半张角 = `spotAngle/2`。
⇒ 「far = 灯的射程」本来就是这样，缺的只有 near（默认 0.2，锥在 0.2 处的截面仍≈一点 ⇒ 影子从中心往外扇）。

**透视下「near 面 = 面片」的真实含义**：near 面大小 = near·tan(θ/2)，与 near 耦合，所以要让
`near · tan(θ/2) = 半对角线` ⇒ **`shadowNearPlane = 半对角线 / tan(spotAngle/2)`**。
已落地在 `AreaLightSource.autoMatchShadowCone`（默认开）+ `shadowConeAngle`（默认 120°）：
`spotAngle = shadowConeAngle`、`shadowNearPlane = hd/tan(θ/2)`（1.61×1.66 + 120° ⇒ near≈0.67）。
- 面光源着色**不看** spotAngle（`lightSpotAngles=(0,1,10)` ⇒ `spotAttenuation` 恒 1 = 半球），
  所以 spotAngle 对面光源是**纯阴影参数**，改它不影响亮度。
- Gizmo 改成画 near 环 + far 环 + 4 母线：near 环应≈面片大小，肉眼即可确认对齐。
- 代价：near 之内物体不投影。灯贴着的天花板/墙正好落进去（通常反而是好事，少自遮挡 acne）。

**为什么不做真正交（near 面字面等于矩形、无发散）**：
`RenderSpotShadows` 只能靠 `cullingResults.ComputeSpotShadowMatricesAndCullingPrimitives()` 出矩阵，
`ShadowDrawingSettings.splitData` 只读、由 Unity 算 ⇒ **没有 API 能喂自定义 view/proj**。
要正交必须自建 shadow map：自建 RT/tile + 自算 ortho + 自剔除（`DrawRenderers` 不按你的矩阵做视锥剔除）
+ 自绘制 + 采样侧 bias 口径从 `1/d²` 改常数，且 SRP / Cluster 两条模式都要通。
正交唯一的硬优势：受光点 P 投影落在矩形内时，代表点 R = P 的投影，P→R 正好沿光轴
⇒ 正交深度图在该 (u,v) 的比较**严格等价**于 P→R 的遮挡判定（与 MRP 着色几何自洽）。
面片很大且离受光面很近时才看得出来，暂不做。

### 灯光剔除 ≠ 阴影视锥（别混用）
- 灯光的 tile/cluster 剔除要用**光照影响体积**（面光源 ≈ 半径 `range` 的半球）；阴影锥是它的子集。
  拿阴影锥去掉灯会把「照亮了但锥外」的灯剔掉 ⇒ 直接丢光。
- 现在 `ClusterLight.compute` 用球（center, radius=range）对半球是**保守正确**的，不用改。
- 阴影 caster 剔除**已经免费**：`DrawShadows` + `splitData` 内部按灯视锥剔。收窄锥 = 剔得更狠但覆盖变小。
- 更紧的灯剔除只有「半球测试」/3D 簇有意义，但每 tile 32 盏都不紧张，收益≈0。

### 面光源的两个体积（必须分清）+ 半球剔除 + 90° 是最优锥角
**① 照亮体积 = 半球**（朝发射方向、半径 range、平面过灯中心）：
照明模型 `sideAttenuation = saturate(dot(emitDir, normalize(P-中心))*3)` ⇒ 发光面背后恒 0；
`rangeAttenuation` 用代表点距离，支撑集 ⊂ 球(中心, range)（因 |P-rep| ≤ |P-中心|，球外必然衰减=0）。
**半球就是这个模型精确的支撑集** ⇒ 用它做剔除不会漏灯。
**② 阴影视锥 = 透视锥**（near≈面片、far=range）⇒ 只是①的子集，只能用于 caster 剔除。

**为什么锥角 90° 是最优（不是随手选的）**：
透视锥在 z=range 处的半径 = `range·tan(θ/2)`。
- θ>90° ⇒ 远平面比半球还大，多出的一圈 texel 全浪费（影子变糊）；
- θ<90° ⇒ 半球外侧那圈「有光」的地方没影子（锥外有光无影）；
- **θ=90° ⇒ 远平面半径正好 = range = 半球半径，near 面正好 = 面片半对角线**。
  于是「near 面=面片、far=range」在你这段描述里**字面成立**，且零浪费。
⇒ `AreaLightSource.shadowConeAngle` 默认 90°。

**ClusterLight.compute 新增面光半球剔除**（`Intersect` 尾部）：
球测试通过后，若 `lightAreaRight.w > 0`，再用 AABB 对「前向半空间」切一刀：
取 AABB 沿 n 最远的角，`dot(n, farthest - center) <= 0` ⇒ 整块剔掉。
- 空间约定：tile AABB 的 xy 与 `_CameraMatrixV` 同口径（右·上），但深度侧用「+z 朝前」
  （见 `-lightCamPos.z` / minZ·maxZ）⇒ **法线要 `n.z = -n.z`**，忘了就剔错方向。
- 用被灯深度 slab 裁剪后的 AABB 判定是**安全**的：slab 外的点本身就不受该灯影响。
- 点光/聚光的 `lightAreaRight/Up` 已显式清零 ⇒ 不会被误判成面光（否则会错误剔灯）。

**Gizmo 改动**：绿=照亮半球（剔除用的体积），蓝=阴影视锥（caster 剔除用的体积），
未选中也画淡锥体（面光源在场景里应是「一个体积」不是「一片纸」）。
θ=90° 时蓝色远环正好与绿色赤道重合 ⇒ 肉眼看得出「没有无影区」。

### Gizmo 与 Unity 自带 Light gizmo 抢线的问题
Unity 的 Light 自带锥/范围球是**原生绘制**，没有 API 能关；它只在**选中**时出现。
⇒ 反过来处理：`AreaLightSource.hideOwnConeWhenSelected`（默认 true）
　**选中时我们的蓝锥让位给 Unity 的锥**，未选中时（Unity 什么都不画）才画自己的淡锥补体积感。
**顺带修的真 bug**：选中物体时 `OnDrawGizmos` 与 `OnDrawGizmosSelected` **都会调用**，
导致「未选中也要画」的部分（面片轮廓、淡锥）被画两遍 ⇒ 线更粗更糊。
现在 `OnDrawGizmos` 里先 `UnityEditor.Selection.Contains(gameObject)` 拦一下，选中时只走 Selected 分支。
（通用经验：自定义 gizmo 想区分选中状态，别指望 OnDrawGizmos 不跑，要用 Selection 判断。）
