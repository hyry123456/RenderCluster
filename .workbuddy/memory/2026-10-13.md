## 项目架构理解（供后续会话使用）
- 双管线：默认走 DefferPipeline（延迟渲染：GBuffer×4 + Depth，cluster 光照 isUse=1，SSR/AO 关，postFXSetting=null，CopyDepth/CopyColor=1），MyPipeline 是回退管线（Unity 自带 DrawRenderers + DrawMesh 批绘制，编辑器非运行模式用）。
- 渲染提交模型：各系统实现 IDrawXxx 接口 → DrawNode.Submit() → GPUDravinSystem 单例的 PreorderLinkList 按 queue 排序，DefferPipeline 在对应阶段遍历调用。
- 簇渲染（用户说的"一次渲染所有模型"）：MyRenderObject 单例集中存储 StaticCPUObjects（CPU 端持久列表），MyPipeline.DrawGBuffer 用 StaticObjectViewJob（Unity Jobs）做视锥剔除后逐 DrawMesh，buffer 放不下就分多次。
- 环境光：SceneSH9（ExecuteAlways）把 Cubemap 投影成 9 个 Vector4 经 GPUDravinSystem.SetSceneLighting 上传；Inspector 上有 Bake 按钮（SceneSH9Editor）。未烘焙时 _sh9 为空。
- 活动资产链：RenderPipeAsset.asset → DefferPipeline.asset（cameraShader = CustomRP/Defferer/DefferCamera）。
- Viking Village 的 self-intersecting polygon 警告来自 PhysX 烘焙 MeshCollider（FBX 导入器 addColliders: 0，是运行时/预览实例化时烘焙的），无害。
- 项目原本有 14 个 .cs 是 UTF-16 编码，已全部转为 UTF-8 with BOM（内容无损）。

## 追加3：Releasing render texture that is set as Camera.targetTexture 警告修复

- 根因（用户要求分析流程后发现）：ShadowsPipeline 的 SetupDirectionalLight/SetupSpotLight/SetupPointLight 都是「先 ReleaseTemporary(旧 RT) 再 camera.targetTexture = 新 RT」，释放时相机还指着旧 RT → Unity 打该警告；每切换一个体积光灯触发一次。Dispose() 同样在相机仍指向 shadowTarget 时释放，且释放后不置 null → double-release + Setup 里对已归还池子的 RT 重复 ReleaseTemporary。
- 时间线吻合用户观察：BulkLightNode（Bake 模式）Awake → LightMap3D → ShadowPipelineRegister.Enroll 激活隐藏 DepthPipelineCamera → 每帧烤一个灯 → 切换灯时警告；烤完 nodes 空 → Dispose 警告。即「运行前后」。
- 触发链路仅此一处：全项目只有 ShadowsPipeline(3处) 和 PlaneReflect(1处) 会给 camera.targetTexture 赋值；场景/预制体里 m_TargetTexture 全是 {fileID: 0}。
- 修复（用户选「只修 ShadowsPipeline」）：3 个 Setup* 释放前 camera.targetTexture = null；Dispose 先解绑再释放并置 shadowTarget = null。camera.targetTexture 仅作阴影相机 rect/投影参照，真正渲染目标由 buffer.SetRenderTarget 指定，行为零影响。
- 未修（用户明确不修）：PlaneReflect.cs 是死代码（不在任何场景/预制体），但有两处判反的条件 `if (renderTarget == null) ReleaseTemporary(renderTarget)`（应为 != null，导致尺寸变化/销毁时旧 RT 泄漏且一直挂在 reflectCamera.targetTexture 上，将来池子回收时报同样警告），reflectCamera GO 在 OnDestroy 也不销毁。以后要用这个组件时先修这两处。
- 纠正：上一轮误判 assemble.asset 不存在——实际在 Assets/CustomRenderPipeline/Resources/Cluster/assemble.asset（合法 Resources 路径，Resources.Load("Cluster/assemble") 可加载），当时只搜了 Assets/Resources/**。

## 追加4：虚拟贴图(RVT)流程全面分析（用户第三轮反馈：批数没降、性能反降）

### 现状硬数据（The_Viking_Village 场景）
- 1058 个预制体实例；约 1072/1078 个 MeshRenderer 走 RVT（ClusterObject+ClusterPBR），几乎全场景 RVT
- 每个物体 1-3 个 submesh = 独立 draw call → 每遍全场景绘制约 1500-2500 draw call
- 每帧几何绘制遍数：GBuffer(1) + Feedback(~每2-3帧1遍全分辨率) + 阴影(directional 4 cascade = 4遍) + 透明 → Stats Batches 实际是场景 draw call 的 3-6 倍
- assemble.asset 实际配置：TexturesCount=100, CellCount=1, CellSize=1024, paddingSize=0, mipsLevel=3, FeedbackScale=1(全分辨率!), FeedbackZoomScale=4, UseRVT=1
- 虚拟贴图实体：3072×3072 RGBA8 ×5 张 ≈ 188MB 显存；物理页仅 63 个（mip0 只有 3 个，mip1 12 个，mip2 48 个）→ 近处大表面>3 种即剧烈颠换页
- 34 个 ClusterRenderDataAsset（Viking Village/RenderAsset）+ 每种一个独立 Material 实例；_MapId 是 per-material 属性 → 不同贴图集不可能合并 batch；同贴图集不同 mesh 也不能合（GPU instancing 要求同 mesh）

### 核心诊断
1. RVT 只换了贴图来源，完全没碰绘制路径——所有物体仍逐物体 context.DrawRenderers → 批数量一分没降，Feedback 还让 Stats 里的 Batches 翻倍
2. 用户记忆中"一次渲染所有模型"的簇机制从未接进主管线：
   - ClusterInclude.hlsl 的 geom/geomShadow（_AppendBuffer+_ClustersBuffer+几何着色器）无任何 shader 引用（仅 RVTShader 为 GetMaxFeedback include 该文件）→ 死代码
   - MyRenderObject/MyMeshRender 不在任何场景/预制体 → 回退管线 CPU 剔除列表实际为空
   - MyPipeline 是回退管线，活动资产 RenderPipeAsset.asset→DefferPipeline.asset 不用它
3. 性能下降来源（每帧新增）：全分辨率 Feedback 重绘全场景 + AsyncGPUReadback(1/4分辨率≈13万像素) + Task 逐像素解析(GC) + 页面提交(每帧最多 50 mins+15 wait 页，每页 5 MRT；mins 页还被画两遍=bug) + 主 pass 无条件 5 采样 3072² 大图集(缓存不友好，原来小图+keyword 跳过)

### 已确认的 bug
- ClusterCore.cs:171-172 DrawTile 重复调用（mins 页画两遍）
- ClusterObject.OnDisable：renderAssets[i] 为 null 时 indexs[i]=0 仍会 RemoveTextureId(0)，误减 texture slot 0 引用计数（潜在）
- paddingSize=0 → 低 mip 页无边缘扩展，线性采样跨页取到邻居像素（漏缝）

### 优化路线（已向用户提出，待选）
- 第1级止血：删重复 DrawTile；FeedbackScale 1→2；相机静止且无页请求时跳过 feedback；SetData 合并每帧一次；padding 0→2~4；页容量重组（如 CellSize=512,CellCount=1,mipsLevel=4 → 84MB/340页，或 CellSize=256,CellCount=2 → 50MB/252页）
- 第2级降批数：路线A=静态物体合并烘焙+compute 剔除+DrawProceduralIndirect+激活 geom 几何着色器（对接原设计，GBuffer/阴影/feedback 三 pass 各 1 draw call）；路线B=共享材质+MaterialPropertyBlock 传 _MapId（同 mesh 可 instancing，不同 mesh 无解）
- 第3级：ClusterPBR 加 keyword 跳过未使用的 emission/detail 采样

## 追加6：降批方案结论——推荐 BatchRendererGroup（BRG）
- 项目已装 com.unity.render-pipelines.core 14.0.12，含 UnityDOTSInstancing.hlsl，BRG 完全可用（2022.1+ API）。
- BRG 覆盖用户觉得麻烦的全部环节：不用合并 mesh（RegisterMesh/RegisterMaterial+AddBatch，同 mesh 实例自动合 1 draw call）、不用自己写 compute 剔除框架（OnPerformCulling 回调+BatchCullingContext/Output+Burst）、不用管 AppendBuffer/间接提交（引擎自动）、每实例数据走 metadata+unity_DOTSInstanceData（_MapId 变 per-instance，所有物体共享一个材质）、阴影自动（SetEnabledViewTypes 含 Shadow cascade）。
- 预期：Viking Village 87 个唯一 mesh → 每 pass ~87-150 draw call（现 ~2000），GBuffer/阴影×4/Feedback 全受益。
- Nanite 式"物理 1 draw call 画完所有不同网格"Unity 无现成 API，需自研 mesh 合并+簇+GPU 剔除+几何着色器展开（用户已有一半：ClusterInclude.hlsl 的 geom）；实务上 BRG ~100 draw call 已不是瓶颈，不值得自研。
- 迁移步骤已向用户说明：BRGContainer（按 mesh 注册 batch+实例数据）→ shader 加 DOTS instancing（include UnityDOTSInstancing.hlsl + #pragma multi_compile _ DOTS_INSTANCING_ON + _MapId 改 UNITY_ACCESS_DOTS_INSTANCED_PROP，与现有 UNITY_INSTANCING_BUFFER 二选一）→ PerformCulling Burst 视锥剔除（可搬 MyRenderObject.StaticObjectViewJob）→ 禁用原 MeshRenderer → 动态物体继续走 DrawRenderers。

## 追加8：RVT 参数回退——CellSize/FeedbackScale 耦合错误导致贴图回归（用户第四轮反馈：远处贴图丢失+近处发糊）

- 用户现象：远处部分贴图不加载（白色+杂色斑点）、近处清晰度明显下降；虚拟贴图集大量页槽空着（排除容量问题，用户截图确认）。
- 根因（可数学证明）：主Pass与反馈Pass共用 mip 公式 `mipRadio = mipsChangeSpeed*log2(max(dx²,dy²)) + 1.0 - mipsChangeSpeed + mipsOffset`，dx 基于 `uv = baseUV * CellSize`（_VTFeedbackParam.y = CellSize）。
  - 主Pass全屏渲染：dx_main = CellSize/P；反馈Pass按 1/FeedbackScale 分辨率渲染：dx_fb = CellSize/(P*FeedbackScale)。
  - 原配置 CellSize=1024 + FeedbackScale=Full(1)：dx_main == dx_fb，两级 mip 一致，系统正常。
  - 我改成的 CellSize=512 + FeedbackScale=Half(2)：dx_main 减半 → 主Pass mip 整体细一级；dx_fb 恰好不变 → 反馈仍按原分布分配页。主Pass读取的页表层级从未被反馈更新，条目停留在 InitialTextureNode 写入的最粗 mins 页（或被 SetAllLevelInEmpty 回收后的陈旧页）→ 近/中距表面取到 1/4 分辨率 mins 页（糊）或游离页（白+杂色斑点）。
  - 结论：**FeedbackScale 必须是 Full**，除非给反馈Pass单独传 CellSize*FeedbackScale 做补偿——用户当年把资产设为 Full 不是疏忽，是必需。任何非 Full 的 FeedbackScale 都会造成两级 mip 错位。
- 次要因素：FeedbackScale=Half 使回读分辨率降至屏幕 1/8，远处/细长物体可能覆盖不到反馈像素→页面永不申请（用户猜测方向正确）；CellSize=512 使 mins 页分辨率 256→128。
- 处置：assemble.asset 四参数回退原值（CellCount 1 / CellSize 1024 / paddingSize 0 / FeedbackScale 1；mipsOffset 0.74、mipsChangeSpeed 0.277 是用户手调值，未动）；ClusterAssembleAsset.cs 默认值同步回退并在 CellSize 处加中文注释说明耦合。保留删重复 DrawTile 的 bug 修复与 Feedback 节流（15帧安全网）。需重启 Play 生效（TileTable/LevelCache 仅启动时创建一次）。
- 教训：改 RVT 参数前必须先推演 mip 公式的参数耦合，不能只算显存/页数收益。

### 架构对照结论（用户记忆基本正确）
- 骨架=业界标准：Feedback pass 每像素编码(texId=r*256+g, mip=b)就是"标记区域"，GetMaxFeedback(最小b选择,背景白色b=255永远竞争不过真实表面)的4x降采样设计正确，小表面不会被淹
- 与UE4/UE5 SVT的差距：①全屏AsyncGPUReadback(13万~200万像素/帧)+CPU Task逐像素扫 vs 业界GPU compute压成唯一请求列表只回读几百条；②后台Task与主线程并发改链表(数据竞争)；③最低级48页固定池只增不减 vs 全级别LRU；④无可见性预pass

### 漏页失败模式（按嫌疑排序，均已修）
1. 线程数据竞争(头号)：ExecuteFeedback后台Task调 levelCache.MoveNodeToUse/GetEmptyNode/SetAllLevelInEmpty，主线程RequestMinsMap同时调GetEmptyNode/SetMinNodeInEmpty；0/1级仅3+12=15页，超限即升级到最低级→碰主线程mins链表→结点双分配(错页/黑块)或丢失(永久缺页)
2. 反馈升级偷mins页→页池泄漏：escalation到最低级GetEmptyNode(2)分页，贴图自己的mins页调入后前页孤立在use链表(SetAllLevelInEmpty只重置0~1级)→48页越玩越少
3. 越界异常级联：池满时finalMipLevel无上限→allMipsCacheNode越界→catch吞掉→该帧剩余请求全丢
4. TileTable第一页画空目标：SetRenderTarget(rvtBuffersId)在数组赋值之前入队，首次DrawTile时数组全0(None)→每局一个黑块
5. mins容量不足时原代码直接continue丢弃texId→页表项停留全零→采样(0,0)槽位(错贴图/黑块)

## 追加12：RVT 架构对标业界（用户第七轮：确认设计逻辑+要业界方案）

### 用户设计逻辑评估结论
- 「图片组(texture set)共享 + 材质参数 per-material」= UE SVT 标准模型，逻辑正确，无问题。texture set 是共享单位，多 material 引用同一 set，tint/roughness/normal scale 是普通 per-material uniform。
- 唯一检查点：34 套 ClusterRenderDataAsset 需查内容重复（同贴图被多 asset 各存一份→各自占页表条目+物理页，纯浪费，合并可缓解最低级48页压力）。可写扫描脚本（用户未定）。

### 业界事实（已搜索核实）
- **Granite**（微软，SIGGRAPH 2021）：GPU 端请求压缩——feedback 每像素一条请求，compute 用 AppendStructuredBuffer+InterlockedCompareExchange 原子去重压成唯一列表，只回读几百~几千条。**关键事实：Unity 2021-2022 官方 SVT 实验包底层就是 Granite SDK runtime**（docs.unity3d.com 2021.1/2022.2 手册确认），后废弃。
- UE4 SVT 请求处理实际也是 CPU gather（用户不孤独）；UE5 物理池文档原话 "acts as a least recently used cache"：固定大小、按格式分池、全级别 LRU 淘汰；Hillside 案例 22GB 磁盘→500MB 运行时。
- UE 材质侧：sampler 类型需改 virtual（virtual color/normal/grayscale），material 与 virtual texture 绑定。
- Nanite：几何 cluster 一次提交 + 材质参数 per-instance；Unity 对应物 = BRG + unity_DOTSInstanceData（_MapId 可 per-instance metadata）。

### 用户三处断层（结论）
1. 请求处理走 CPU 全屏回读+Task逐像素扫（13万~200万像素/帧+GC）→ 改 GPU 压缩（Granite 式）
2. 页池最低级48页固定池只增不减 → 改全级别 LRU
3. _MapId 是 material property → 材质爆炸（34套）→ 同 mesh 不同材质不能 instancing → ~2000 draw call/pass → BRG 共享材质+per-instance 参数（~87-150/pass）；轻量过渡=keyword 分化建 4-8 个共享材质
4.（可选）场景静态→页表预初始化（开机黑块根因）

### 落地路线（已提给用户，待选起点）
1. GPU 请求压缩（确定性收益，中等工作量）→ 2. 全级别 LRU 页池（小改）→ 3. BRG 迁移（最大收益最大工作量）→ 4. 可选 keyword 过渡/静态预初始化
- 本轮未改代码，纯分析+两张架构图（SVT 数据流对比、材质参数位置对比）

## 追加13：LRU 页池改造完成（用户批准路线第1步，标准 LRU 替换阉割版）

### 原实现的问题（用户自称"阉割版"）
- GetEmptyNode 无空闲即返回 null → 请求被丢弃/升级，无淘汰机制
- ExecuteFeedback 每帧结尾 SetAllLevelInEmpty() 把 0..N-2 级全部 use 页一次性清回 empty（"每帧全清、按需找回"，O(n) 整表挪动，语义粗暴）
- 最低级 48 页只增不减：SetAllLevelInEmpty 不含最低级，只靠 needRemoveNode（贴图销毁）回收 → 满后新贴图永远进不来（报"最低级页池已满"）
- 非最低级孤立页（贴图移除时）全靠全清兜底回收

### 改造内容（3 文件，全部验证：代码括号平衡、引用一致）
LevelCache.cs：
- GetEmptyNode→AllocateNode（LRU 分配）：empty 优先；无空闲→EvictLRUHead 从 use 链表头部淘汰最久未使用页；淘汰记 pendingEvict(结点,旧texId) 且 node.texId 立即置-1让本帧分配检查通过
- +TakePendingEvict（锁内交换，主线程取）
- +PerLevel.EvictLRUHead
- +ReleaseNode（泛化回收任何级别，SetMinNodeInEmpty 转发兼容）
- Dispose 清 pendingEvict
TextureNodesMap.cs：
- SetCacheNodeToLowMips 加重载(node, texId)：淘汰时结点可能已被新贴图重用(node.texId 已变)，必须按旧 texId 降级
- +EvictTextureNodes(texId)：最低级 evict 清 CPU 映射（GPU 页表不清，shader 无无效页回退，最多错一帧后重画恢复）
- RemoveTextureId：所有级别占用的页都入 needRemoveNode（原来只收最低级，其余靠全清——全清已删，不显式回收会泄漏）；QueueRemoveNode 带去重（同一 node 可被多 mip 级共享，重复回收破坏链表）
- +QueueMinsMap/DequeueMinsMap（minsMapQueued 去重，防重复入队重复分配页）；AllocateTextureId 3 处入队改用
ClusterCore.cs：
- RequestMinsMap 开头 +ProcessPendingEvict：非最低级 evict→SetCacheNodeToLowMips 降级（变糊）；最低级 evict→EvictTextureNodes+QueueMinsMap 重画（运行时溢出兜底，静态场景 34<48 不触发）
- ExecuteFeedback：移除每帧 SetAllLevelInEmpty（LRU 淘汰替代：不可见页沉到 LRU 端被淘汰，语义等价无整表扫描）
- needRemoveNode 回收循环移到 WaitSetList 应用之后 + texId!=-1 跳过（防 LRU 重用结点被双分配）
- Cleanup 清 pendingEvictList；防御分支日志消息更新

### 设计要点/风险（已告知用户）
- use 链表本身即时间序（头旧尾新），MoveNodeToUse 每帧被 feedback 调用 = 天然 LRU touch，原骨架是对的只缺淘汰
- LRU 降级必须主线程做（ComputeBuffer.SetData 线程限制）→ pendingEvict 记录+主线程统一处理，顺带修正了原异步结构里"Task 中间接碰页表"的隐患
- Task 异步导致 evict 降级最晚一帧生效，过渡帧内旧贴图可能采样到已重用页（可接受，仅页池压力大时发生）
- 最低级 evict 的 thrash 风险：A 淘汰 B→B 重画淘汰 A…不会崩（lodCount<50 限流），表现为交替模糊；正解仍是减少贴图套数（后续共享材质/BRG）
- 待用户 Unity 重编译+运行验证
