
## 阴影 cull/draw 定量：2.75 倍重复是共同乘数；静态索引段直通

### 算账（31856 簇 / 4,077,568 三角形 / 4 级联）
- 一份全量索引 = 4,077,568 × 3 × 4B = **48.9MB**
- pad 日志的 x/y 命中率：级联0=0% / 级联1=76.5% / 级联2=98.9% / 级联3=100%
  ⇒ **同一批簇平均被画 2.75 遍**
- `BuildIndices`：读 `_CornerGvid` 48.9 + 读 `_SlotOf` ≈48.9 + **写 `_DrawIdx` 134.5** ≈ **232MB**
  ⇒ 232MB / 0.49ms = **473 GB/s**（2080Ti HBM 峰值 616）⇒ **带宽墙，不是算力问题**
- `DrawProcedural` 1.068ms 画 4.077M × 2.75 = **11.2M 三角形** ⇒ 10.5 Gtri/s ⇒ **贴着三角形吞吐上限**

**结论：cull 和 draw 共用一个乘数（重复倍数）。削它两个一起降。**

### 为什么 Unity 不用重排索引
Unity 每个 renderer 用 **mesh 自带的静态索引**，剔除只决定"这个 draw 发不发"，不改索引内容 ⇒ 索引**只读**（~49MB/帧）、零写入。
我们要重排是因为把全场景压成 **1 个 draw**（SRP 是 41 个）；要在一个 draw 里只画可见簇，就必须有人把索引压实。
⇒ 重排是"1 draw 换 41 draw"的代价，不是浪费。**但可见率 99~100% 的级联，压实等于白做。**

### 已实现：静态索引段直通
- `_DrawIdx` 从 4 段扩到 **5 段**（+48.9MB 显存）：段 0 = 静态全量副本（Rebuild 后 `CopyStatic` 填一次），段 (k+1) = 级联 k 的压实段。
- **dispatch 顺序改为 Reset → CullAll → BuildArgs → BuildIndices**：BuildArgs 先算出 `_Args[k*5+2]`（本段起点），0 表示走静态段。
- `BuildArgs`：`cnt*100 >= clusterCount*FullSkipPercent(90)` ⇒ indexCount=全量、startIndex=0（静态段）；否则压实段。
- `BuildIndices`：读 `_Args[k*5+2]`，为 0 就整级联跳过（不写索引）。
- **正确性**：被视锥剔掉的簇 x/y 落不进本级联盒 ⇒ 影子也落不进 ⇒ 多画它视觉无害，只是多走几何。
- 可见率低时（未来大场景）自动落回压实，因为那时压实是真的在省几何。`FullSkipPercent=101` 可完全禁用。

预期：2.75 → 只压实级联 1（0.765），写入 134.5 → 37MB，`BuildIndices` 约 0.49 → 0.18。

### 诊断埋点（已加，未验证）
- 4 个 dispatch 各自 sample：`CCull.Reset/CullAll/BuildArgs/BuildIndices`（+`CCull.CopyStatic`）
- `RequestVisibilityStats()`：每 120 帧 AsyncGPUReadback 读 `_Counter`，打「倍数 X.XX×（索引每帧写 NMB）」
- **关键实验**：`clusterShadowMaxDepthPad = 1` ⇒ pad 恒 1 = Unity 原生 z 范围。
  若阴影仍正常，说明 pad 从一开始就是多余的（当年缺块真凶可能是 `PadOrthoDepth` 第一版的单侧平移 bug）。

## ★ 关键：阴影 pass 从来没剔过 z 方向 —— 补上第 7/8 个平面（零视觉变化）

### 实测（pad=1，静态索引段已生效）
```
ClusterCull            0.342   (原 0.490)
  CCull.Reset          0.000
  CCull.CullAll        0.004   ← 剔除本身几乎免费！原子竞争不是问题
  CCull.BuildArgs      0.004
  CCull.BuildIndices   0.227   ← 仍有：读 _CornerGvid/_SlotOf + 写压实段
Graphics.DrawProcedural 4 draws 1.055   ← 最大单块，仍没降
```

### 为什么 DrawProcedural 降不下来
atlas 是 **1024**，`split=2` ⇒ 每级联 **512×512**，4 级联合计 **1.05M 像素**。
2080Ti 填充 ~116 Gpix/s ⇒ **填充 ≈0.01ms**。所以那 1.055ms 是 **纯三角形 setup**。

### 根因：z 方向完全没剔
`GeometryUtility.CalculateFrustumPlanes` 在 **reversed-Z 下近/远两个平面几乎恒真**
（代码注释早有记录），所以剔除实际只按 **x/y** 判。于是：
- 「x/y 在盒内、沿光轴远在板外」的簇全被提交；
- 它们在光栅化阶段被投影矩阵的 z 范围**整块裁掉**，一个像素都写不进阴影图；
- ⇒ **纯浪费顶点 + 三角形 setup**。而 pad>1 还会把更多这种簇拉进来（所以 pad 越大越慢）。

这也解释了 Unity 为什么"不 pad 也不缺点"：Unity 按**级联包容球（半径 R）**剔除，
球外物体本来就不画 —— 而球外物体恰好也在 ±R 的 z 板外，两者等价。

### 修法
- `PlanesPerCascade` 6 → **8**：多出的两个是**光轴 z 的两个边界平面**，写成统一形式
  `z_view >= zMin ⟺ dot(row2.xyz, p) + (row2.w − zMin) >= −r`。
- z 范围从 **`GL.GetGPUProjectionMatrix`** 反解（`ndc_z = m22·z_view + m23`，ndc∈[0,1]），
  **不能用裸 `projectionMatrix`**（GL 风格 [-1,1]，反解会得到一半厚度）。
  取 1% 板厚作保守余量，防浮点边界误剔跨板的簇。
- `cullZ=false`（矩阵退化）时写两个恒真平面 `(0,0,0,1e9)`，kernel 不用分支。
- **正确性**：整簇在板外 ⇒ 光栅化器整块裁掉 ⇒ 对阴影图零贡献 ⇒ 剔掉无任何视觉变化。

### 顺带定案
- `clusterShadowMaxDepthPad` **默认 16 → 1**。当年"缺块"真凶是 `PadOrthoDepth` 第一版
  `m22/=pad; m23/=pad` 把板整体往一侧平移了半个板；改成围绕板中心对称扩张后 pad=1 退化为原矩阵。
- `maxPad <= 1` 时**直接跳过** `ComputeDepthPad` 的 O(簇数) CPU 推导（也不再刷诊断日志）。

### 验证要点
`CCull.CullAll` 会从 0.004 涨一点（多 2 个平面判断），**关键看 `DrawProcedural` 是否下降**
和 `倍数` 那行是否变小。若出现阴影缺块 ⇒ z 反解/符号有错，把 `clusterShadowMaxDepthPad`
调回 16 可立即回退（那时 z 剔除范围也跟着变宽，不会缺）。

## Hi-Z 遮挡剔除（GBuffer 侧，默认关）+ Scene 视图三态

### 深度来源改方案（比原计划的 blit 更稳）
原计划：blit 深度到 R32 → 建链。**改成：本帧 GBuffer 画完后直接用本帧深度建金字塔，供下一帧用。**
理由：这就是"上一帧深度"语义，**不需要跨帧保存深度图**，也不需要 depth→color 的格式拷贝。
失败模式安全：深度读不到 ⇒ 金字塔全 0（= 无穷远）⇒ 判据 `tileMin > nearestZ` 永不成立 ⇒ 不剔除、画面不变。

### 数学（reversed-Z：值越大越近，0 = 无穷远）
- 金字塔每级取 2×2 的 **min**（= 最远的点）。
- 判据：`tileMinZ > clusterNearestZ` ⇒ 整簇被挡 ⇒ 剔除。
  含义「矩形内最远的像素都比簇最近的点更近」。取 min 比较 ⇒ 只漏剔不误剔。
- 簇 AABB 8 角点 × `_ViewProj` 求屏幕 AABB + `nearestZ`；**任一角点在相机后方就跳过测试**（保守）。
- 屏幕跨度大就走 1/16 级，小就走 1/4 级；单簇最多 16 次采样，超出就不测（保守）。

### 实现
- `ClusterGBufferCull.compute`：新增 `BuildOccluder0`（深度→1/4 级，4×4 min）/ `BuildOccluder1`（1/4→1/16 级）；
  `CullAll` 在视锥剔除之后插遮挡测试。新增 `_SrcDepth / _HiZ0 / _HiZ1 / _ViewProj / _PicSize / _HiZEnable / _HiZBias`。
  ⚠️ 尺寸用**标量** `_HiZ0SizeX/_HiZ0SizeY/...`（`int2` 用 SetInt 传不进去）；`_PicSize` 声明成 float4 用 SetVector 传。
- `ClusterGBufferRenderer.cs`：`hiZEnable`、`BuildHiZ(cmd,w,h)`、`EnsureHiZ`、`ReleaseHiZ`（Release 里调）；
  两张自建 RT（RFloat / enableRandomWrite / Point / Clamp），1/4 与 1/16 屏。
- `DefferPipeline.cs`：`gbuf.hiZEnable = clusterAsset.clusterHiZOcclusion`；`Cull(buffer,width,height)`；
  `DrawGBuffer` 之后 `BuildHiZ + ExecuteBuffer`（profile 名 `Cluster.HiZBuild`）。
- `ClusterAssembleAsset.cs`：`clusterHiZOcclusion`（默认 **false**）。

### Scene 视图三态（`sceneViewCluster`）
`Srp` / `ReuseMainCulling`（默认，复用主相机剔除结果，只更矩阵）/ `IndependentCull`（独立视锥剔除）。
`ClusterGBufferRenderer.PrepareViewOnly` 只更 `m_w2c`，不动剔除缓冲。
⚠️ Reuse 下可见性跟随主相机，转视角会"没画"，是预期；材质疑似（RVT 页按主相机请求）就切 `Srp`。

### 阴影 Hi-Z 是另一件事（未做）
阴影的遮挡物是**从光源看**的深度，即阴影图本身，不是相机深度。要做需要：
① 阴影 atlas 从 `GetTemporaryRT` 改成**持久 RT**（否则跳过/复用重画时内容是未初始化的）；
② 每级联单独建金字塔（512² 很小，建链几乎免费）；
③ 在 `ClusterShadowCull.CullAll` 里按光空间投影做同样的判据。
收益预期比相机 Hi-Z 大（村庄场景从太阳看遮挡率很高），但要先解决 atlas 持久化。

## 修正：Hi-Z 未绑定时报 "Property (_HiZ0) ... is not set"；Scene 开关简化为 bool

### 1 号 bug：compute 全局纹理必须【每个 dispatch 都绑定】
`_HiZ0 / _HiZ1 / _SrcDepth` 在 `ClusterGBufferCull.compute` 里是**全局声明**，
Unity 的 kernel 反射要求它们在每个被 dispatch 的 kernel 上都有绑定 ——
`_HiZEnable=0` 只是让 branch 不执行，**不解除绑定要求**。
原来 `if (m_hiz0 != null)` 才绑 ⇒ Hi-Z 关闭 / 首帧还没建金字塔时直接报错。

修法：加 `m_hizDummy`（1×1 RFloat、enableRandomWrite、HideAndDontSave），
  - `Cull()` 里 `hz0 = (hiZEnable && m_hizValid && m_hiz0!=null) ? m_hiz0 : DummyHiZ()`，`hz1` 同理；
  - 三个纹理在 `CullAll` / `BuildOccluder0` / `BuildOccluder1` **每个 kernel 都绑一遍**；
  - `Release()` 里释放 dummy。
  - dummy 内容永不被读（`_HiZEnable=0` 时整段跳过）。

### 2 Scene 视图三态 → 单个 bool
用户反馈「三态参数太绕，我只要看 cluster 剔除 / 不看」。

## ★ Hi-Z 「近的被剔、远的还在、一堆穿孔」的两个真因（已修）

### 因 1：`_GBufferDepthTex` 是 MSAA 深度，当 SRV `Load` 读到未 resolve 的样本
`CreateGBuffer` 里 `GetTemporaryRT(GBufferDepthId, ..., RenderTextureFormat.Depth, ...,
(int)renderSetting.antiAiasing)` —— 最后一个参数就是 MSAA 级别。
MSAA 深度**不能直接当 Texture2D<float> 采样**，必须 resolve；`Load` 出来是垃圾值
⇒ 归约出的"最远深度"随机 ⇒ 逐簇随机穿孔，症状正是「近的没了、远的还在」。

**修法（按用户建议，复用管线已有的深度拷贝，零额外 blit）**：
- `BuildHiZ(cmd, RenderTargetIdentifier srcDepth, w, h)` 改为接收深度源。
- 调用点从 `DrawGBuffer`（GBuffer 刚画完）挪到 **`DrawGBufferFinal` 里 `CopyDepth` 之后**，
  源 = `ShaderProperty.CameraDepthTexId`（`_CameraDepthTexture`，`antiAliasing` 未传 = 1，非 MSAA）。
  这份拷贝本来就要为后处理/粒子准备，等于白捡。
- `renderSetting.CopyDepth` 关掉 ⇒ 不建金字塔 ⇒ `_HiZEnable=0` ⇒ 自动失效（安全失败）。

### 因 2：深度方向被硬编码成 reversed-Z
`nearestZ = max(...)`（取最近）、金字塔 `min`（取最远）都写死了 reversed-Z 的语义。
一旦实际不是 reversed-Z，判据整个反过来 ⇒ 近的被剔、远的留下。
- compute 新增 `_ZReversed`（C# 从 `SystemInfo.usesReversedZBuffer` 传，D3D 恒 1），
  并加宏 `ZFAR/ZNEAR` 统一"取更远 / 取更近"；
- 判据改为 `_ZReversed ? (tileFar > nearestZ + bias) : (tileFar < nearestZ - bias)`；
- 用 `bool tested` 代替哨兵值（reversed-Z 下深度 0 是合法值，用 -1 当哨兵会被 min 吃掉）。

### 因 3（顺带修的错位）：金字塔与 VP 矩阵必须同源
金字塔是**上一帧**深度建的，剔除却在**当前帧**用当前 VP 投影簇 ⇒ 相机一动就系统性错位。
- 新增 `m_prevVP`，`BuildHiZ` 末尾记下建金字塔时的 `m_w2c`；
- `Cull` 里 `_ViewProj` 改用 `m_prevVP`。

### 其他
- `DefferPipeline` 每次进相机时一并复位 `gbuf.hiZEnable = false`，
  否则切回 SRP 模式后 `DrawGBufferFinal` 会继续白建金字塔。
- 阴影侧仍未接 Hi-Z（用户确认先只做相机侧）。

**待验证**：开 `clusterHiZOcclusion` 后应无穿孔、无物体消失；`Main Camera` 的
`DrawProcedural` 应下降。若完全没变化 ⇒ 检查 `RenderSetting.CopyDepth` 是否开着。

## Hi-Z 远处穿孔：金字塔最细 1/4 级对远处小簇太粗（已加保守门槛）

修完 MSAA + 方向后：**近的正确、远处仍穿孔**。

### 不是"深度不是 0-1"的问题
深度确实在 [0,1]，只是**非线性**（透视除法）。但簇投影用的是 `cp.z/cp.w`，
和 `_SrcDepth` 读出来的是**同一个空间**，所以比较方向本来就是对的 —— 这点排除。
（若真是空间不匹配，连近处也会错，不会"近的对、远的错"。）

### 真因：金字塔最细一级是 1/4 屏，一个 texel = 4×4 屏幕像素
- 近处簇在屏幕上占几十上百像素 ⇒ 块里几乎全是它自己 ⇒ 判定准（用户实测"近的很正确"）；
- 远处簇可能只占 2~4 像素 ⇒ 4×4 块里 15/16 是旁边的屋顶/树/地面
  ⇒ 「块内最远深度」把邻居算进来 ⇒ 判成被遮挡 ⇒ **远处一堆穿孔**。

### 修法：两条都往「宁可不剔」方向拉
1. `_HiZMinSize = 8`（像素）：簇的屏幕跨度小于 8 就不做遮挡测试。
   宁可漏剔 —— 远处小簇的遮挡剔除收益本来就低，误剔的视觉代价却是"物体凭空消失"。
2. `_HiZRelBias = 0.03`：余量改成 `max(_HiZBias, nearestZ * _HiZRelBias)`。
   远处 nearestZ 趋近 0（reversed-Z），绝对 bias=0 等于没加；相对量才能兜住浮点误差。

### 若还要远处剔除收益（下一步才做）
把金字塔加深一级：现在只有 1/4 与 1/16，缺 1/2。
小簇用 1/2 级（1 texel = 2×2 像素）就能测到 8~16 像素的簇而不过度混入邻居。
代价：多一张 RT + 一个 kernel + CullAll 里多一路分支。
**先看这次两条保守化够不够，不够再上。**

## Hi-Z 按业界 HZB 重做：四级金字塔 1/2 → 1/16 + 选级匹配

前一版（最细 1/4 级 + 8 像素门槛）仍会漏。原因是最细一级就是 1/4 屏
（1 texel = 4×4 像素），对远处 4~8 像素的簇来说**块比簇本身还大**
⇒ 块内的「最远深度」必然来自邻居 ⇒ 逐簇误剔。

### 标准 HZB 的三个要素（这次都补上了）
1. **金字塔从尽量细的级别开始**：改成 1/2 → 1/4 → 1/8 → 1/16 四级，每级 2×2 归约取最远。
2. **选级让块大小匹配簇尺寸**：从最细一级往上找，直到簇的屏幕矩形在该级上
   ≤ 4×4 个 texel。此时块大小 ≈ 簇尺寸的 1/4 ⇒ 块内几乎全是簇自己。
3. **采样数封顶**：每簇最多 16 个 texel（`n.x*n.y <= 16`），CullAll 的预算本来就极宽裕
   （实测 0.004ms）。

### 各级覆盖能力（跨度→级别）
| 簇屏幕跨度 | 选中级别 | 覆盖 texel |
|---|---|---|
| 8 px | 1/2 | 4×4 |
| 16 px | 1/4 | 4×4 |
| 32 px | 1/8 | 4×4 |
| 64 px | 1/16 | 4×4 |
| > 64 px | **不测** | — |

> 64 px 以上的簇不测：它们在近处，极少被完全遮挡，而误剔最刺眼。
> 要恢复这部分收益再加一级 1/32 即可。

### 改动
- `compute`：`_HiZ2/_HiZ3` + `BuildOccluder2/3` kernel；`CullAll` 里四级 if/else 链。
- `ClusterGBufferRenderer`：四张 RT（合计 < 1MB / 相机）、`EnsureHiZ` 四级尺寸、
  `ReleaseHiZ` 全释放、`Cull` 里四个纹理都绑（全局声明必须每个 kernel 都绑）。
- `_HiZMinSize` 保持 8 像素（有了 1/2 级，8 px 的簇走 L0 精度足够）。

## Hi-Z 调试设施：统计回读 + 日志门控 + 金字塔尺寸核对

### Frame Debugger 核对（用户截图）
`BuildOccluder3`：Thread Groups 10×4×1、Group Size 8×8 ⇒ 覆盖 80×32，
`_HiZ3` = 75×30（1200×490 的 1/16）✓；`_HiZ2` = 151×61（1/8）✓。
**金字塔构建链路本身没问题**，四级尺寸都对。

### 新增
- `_HiZStat`（`RWStructuredBuffer<uint>`，C# 侧 `ComputeBuffer(8,4,Structured)`）：
  0=测了且保留 / 1=判遮挡剔除 / 3=太小或太大跳过 / 4=矩形不可靠（角点在相机后）。
  `_HiZDebug` 非 0 才累加（避免平时付原子开销）。
- `RequestHiZStats()`：每 120 帧 `AsyncGPUReadback`（不 stall），打印
  `[Cluster Hi-Z] 本帧：测了 X 保留 / 剔 Y / 跳过 Z / 矩形不可靠 W`。
- `ClusterGBufferRenderer.debugStats`（由 `DefferPipeline` 按 `clusterMode == ClusterDebug` 置位），
  控制统计与日志。
- `ClusterShadowRenderer.Rebuild` 的「重建：N 簇 / …」日志改为 `if (debugStats)` 才输出
  —— 用户反馈每次重建都刷太吵。

### ⚠️ 行为变更：`_DebugForceAll` 不再跳过 Hi-Z
原来 `_DebugForceAll != 0` 时连 Hi-Z 一起跳过 ⇒ ClusterDebug 下永远测不到遮挡剔除、统计恒为 0。
现在只有【视锥剔除】受它控制，Hi-Z 独立执行。Debug 模式的语义变成
「忽略视锥剔除、单独看遮挡剔除对不对」，这才有用。

### 排查提示（重要）
Scene 视图现在**复用主相机的可见集**（不自己剔除），所以「Scene 里转到别的方向、物体消失」
是**预期行为**，不是 Hi-Z 误剔。要判断 Hi-Z 有没有问题，必须看 **Game 视图**，
或者看 `[Cluster Hi-Z]` 那行统计的剔除比例是否异常。

## Hi-Z 遮挡剔除：远处缺块 = 屏幕矩形 Y 轴镜像（已修）
- 症状：Game 视图近处都对，远处房子/房屋簇整块消失（像被挖掉一块）。
- 根因：`ClusterGBufferCull.compute` 的 `ClusterScreenRect` 把 NDC 映射到深度图 texel 时
  写成 `s = (ndc*0.5+0.5)*_PicSize`，**漏了 Y 翻转**。`_ViewProj` 来自
  `GL.GetGPUProjectionMatrix(proj,true)`（D3D 上 y 已翻，Unity 自己用 `_ProjectionParams.x = -1`
  翻回来，见 `DefaultPassVertex`），而深度拷贝纹理行序是「屏幕自上而下」。
  于是矩形上下镜像：近处物体映到天空（深度 0 ⇒ 永不判遮挡 ⇒ "近的都是对的"），
  远处小物体映到房前近处地面（深度大 ⇒ 整簇误剔）。已改为 `s.y = (0.5 - ndc.y*0.5)*picH`。
- 顺手：`nearestZ = saturate(nz)`（角点被近平面切时 z 可能 <0，会让 tol 变负）。
- 统计口径修正：`AsyncGPUReadback` 在 Cull 里（ExecuteBuffer 之前）发起 ⇒ 读到的是 C# 清零值，
  恒为 0（看起来像 Hi-Z 没跑）。改为 `m_hizStatDue` 标记 + 管线 `ExecuteBuffer()` 之后调
  `gbuf.FlushDebugStats()`。日志带 启用/金字塔有效/剔选屏宽 三个自证字段。
- 教训：任何「NDC → 屏幕纹理 texel」的映射，必须和 `_ProjectionParams.x` 同口径，否则整屏镜像。

## Hi-Z 调激进（Y 翻转修好之后）
- 用户反馈"剔除成功了，但看不到的还经常出现" ⇒ 三个保守旋钮一起放开：
  1. `HiZRelBias` 0.03 → **0.01**（200m 处余量从 ~15m 收到 ~1.6m）；
  2. `HiZMinScreenSize` 8 → **4** px（最细一级是 1/2 屏，2 texel 起步）；
  3. 金字塔 4 级 → **6 级**（1/2…1/64）：以前屏幕跨度 >64px 的簇（1/16 上就超 4×4 texel）
     整类"太大跳过"= 永远画出来；现在 256px 以内都能测。
- 实现：compute 里把嵌套 if 链换成 `for lvl<6` + `HiZSize()/HiZSample()` 两个 if 链小函数
  （RWTexture2D 不能当形参传）；C# 侧 m_hiz4/m_hiz5 + 各自 size uniform + Bind() 全绑。
- 判据方向没变：tileFar(块内最远) 仍要比 nearestZ + tol 更近才剔 ⇒ 只会漏剔不会穿孔。
- ⚠️ 踩坑：`ClusterGBufferCull.compute` 每个 kernel 都必须有显式 `#pragma kernel XXX`
  （这个文件不是"有 numthreads 就自动算 kernel"）。加了 BuildOccluder4/5 函数但漏了 pragma
  ⇒ 运行期 `Kernel 'BuildOccluder4' not found`、每帧抛 ArgumentException。已补。
- 顺手加防线：C# 用 `m_cull.HasKernel(...)` 探级数（`m_hizLevels` 4 或 6）+ compute 里
  `for lvl < _HiZLevels`，以后 kernel 缺失只会退回 4 级，不再每帧抛异常。
- ❌ **D3D11.0 一个 kernel 最多 8 个 UAV**。CullAll 的 UAV = `_HiZ0..3`(4) + `_HiZStat` +
  `_SlotOf` + `_Visible` + `_Counter` = **正好 8**。再加两级金字塔 ⇒ 10 ⇒
  "Compute Shader: dispatching a compute shader with 10 UAVs ... Skipping dispatch"，
  整个剔除静默失效（不报错、画面只是不变快）。所以 **Hi-Z 级数被锁死在 4 级**。
- 大簇的替代做法：不加级，改**texel 预算**——最粗一级（1/16）允许 8×8=64 texel，
  覆盖到屏幕 128px（原 64px）。零额外 UAV、零额外显存。

## 簇路径反射读到「陈旧 unity_SpecCube0」（反光随相机位置/距离剧变）
- 症状：木桶远处/相机在阳光下时反光暴亮（像镜面反射天空盒），靠近或进阴影就"反光消失"，剧变。
- 根因：`ClusterPass.hlsl` 的 `ClusterGBufferShade` 用 `ComputeIndirectSpecular()` → 读
  `unity_SpecCube0` / `_HDR` / `_ProbePosition` / `_BoxMin` / `_BoxMax`。这些是 Unity
  **逐 Renderer** 绑定的全局量；簇走 `DrawProceduralIndirect` **没有 Renderer** ⇒ 读到的是
  上一个 SRP 物体残留的值 ⇒ 强度/方向随「相机附近画了什么」乱跳。
  且原写法**没有 reflIntensity 衰减**（非金属也全强度反射）+ 用了盒投影（陈旧的盒）。
- 修复：与 `PBR/Input/GBufferPass.hlsl`（DefferStandard / BRG）逐字一致：
  `reflMip = clamp(roughness*7,0,8)` → `SamplerReflectProbe(reflect_dir, reflMip)`（= 采样
  工程自己的天空盒 `_MySkybox`，GPUDravinSystem 每帧 SetGlobalTexture，与 `_Sh9` 同源）
  → `refl *= lerp(saturate(0.05+(1-roughness)*0.6), 1, metallic)`。
- 影响面：`ClusterPass.hlsl` 被 ClusterGBuffer.shader（簇）和 ClusterPBR.shader（SRP 材质，
  第 100/258 行）共用 ⇒ 两条路径现在反射来源一致，也和 DefferStandard/BRG 一致。
- 铁律：**过程化绘制（Draw/DrawProcedural*）不要读 `unity_SpecCube0` / `unity_SH*` /
  `unity_Lightmap` 这类逐 Renderer 的全局量**，要读管线自己 SetGlobal 的量（`_MySkybox`、`_Sh9`）。

## 阴影侧 Hi-Z（灯光空间遮挡剔除）—— 与 GBuffer 共用 clusterHiZOcclusion 开关
- 需求：只在 Game 视图做（Scene 不做），开关就是资产上那一个（开了 = 视锥 + 遮挡一起开）。
- 数据流（与 GBuffer 同款）：本帧阴影图集画完 → `ClusterShadowRenderer.BuildHiZ` 用【本帧图集深度】
  建 4 级金字塔 → 【下一帧】CullAll 用它剔除。图集是 GetTemporaryRT，所以只在【同一帧内】读它，
  金字塔是自己的持久 RFloat，不需要把 atlas 改成持久 RT。
- 关键矩阵两份：
  · `_ClipMtx[k]` = `GL.GetGPUProjectionMatrix(proj,true)*view` —— 它的 ndc.z **就是**阴影图里存的深度；
  · `_AtlasMtx[k]` = `ConvertToAtlasMatrix(proj*view, offset, scale)` —— 与
    `SAMPLE_TEXTURE2D_SHADOW` 采样口径逐位一致 ⇒ `uv * atlasSize` 直接就是 texel 坐标，**不用翻 Y**
    （和 GBuffer 那次相反：那次 NDC→像素是手动映射，才需要翻）。
  ⚠️ 千万别用 atlas 矩阵的 z 去比深度：它被映射成 0.5*(1-ndc_z)（0=近 0.5=远），和存的深度差一个仿射。
- UAV：CullAll = `_SlotOf`+`_Visible`+`_Counter`+`_HiZ0..3` = **7**（上限 8）⇒ 阴影侧也不能加级、
  也不加统计缓冲。改看现有 `[Cluster阴影] 可见簇 级联k=…` 日志判断效果。
- 相机口径：`ClusterShadowRenderer.HiZGameCamera`（static，DefferPipeline 每相机在 lighting.Setup
  【之前】置位）⇒ Scene 视图 hiZEnable=false，纯视锥剔除。
- BuildHiZ 调用点：`RenderDirectionalShadows(index,split,tileSize)` 末尾（所有级联 + cutout SRP pass
  画完之后、ReleaseTemporaryRT 之前）。
