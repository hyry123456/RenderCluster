## 移除「簇渲染路径」（useClusterBuild / useClusterRender）—— 架构定案
- 用户决定：保留 BRG + Tile-VT，彻底放弃簇。已从 Inspector 移除两个开关，代码分支全部删除。
- **概念澄清（重要，别再混淆）**：Tile-VT 不是「Unity 版的簇」，两者是**正交维度**：
  - 簇（Nanite 式）= 几何 LOD + 逐簇剔除，解决"三角形太多"；
  - Tile-VT = 贴图虚拟内存 + 逐 tile mip，解决"贴图太多太大 / texel 密度"。
  - 移除的真正理由不是"Tile-VT 取代了簇"，而是**原来那套簇没实现簇的核心价值**：没有 LOD 层级选择，只是把 submesh 再切碎后逐个 `DrawMesh` —— 有簇的开销、没有簇的收益，实测把帧率打到个位数。
- **当前方案准确说法**：整网格 BRG 实例批处理 + tile 粒度虚拟贴图按页流式驻留（GPU 驱动实例化 + 虚拟贴图），不是虚拟几何。
- **代价**：失去几何 LOD / 逐簇遮挡剔除。Viking Village 场景量级不需要。

## Tile-VT 画面糊的定量根因（2026-10-19，已改配置 + 修公式）
用户对比「T=4 的 RVT」与「不用 RVT」，发现 RVT 明显糊，怀疑 Tile 实现或桶材质有问题。逐项定量后结论：**既不是材质问题，也不是采样/编码问题，是页池容量按 T² 缩水 + mip 公式没乘 T 导致的 LRU 抖动**。

- **素材真实尺寸（实测 TIFF 头）**：`prop_barrel_01_a/_n.tif = 1024²`，`_m.tif = 512²`；`terrain_far_01_a2.tif = 4096²`，`terrain_01_n.tif = 2048²`。
  用户「4 个 512 = 2048 和原图一致」的前提不成立——桶本来就是 1024。
- **虚拟贴图总分辨率 = CellSize × T**（不是 CellSize）。RVT 一张贴图能到多少分辨率只看这个乘积。
- **图集/页池容量公式**（`TileTable` + `LevelCache`）：
  - 图集边长 `= (padding * 2^(mips-1) * 2 + CellSize) * CellCount * mips`（正方形，`texSizeX = texSizeY * mips`）。
  - 每个 mip 级别的物理格数 `= CellCount·2^i × (CellCount·2^i · mips)`；level0 `= CellCount² × mips`。
  - 每张贴图每级占用 `T²` 格 → **level0 能容纳的贴图数 = CellCount² · mips / T²**。
  - 旧配置 CellSize512 / CellCount4 / mips3 / T=4 → level0 = 48 格 ÷ 16 = **只放得下 3 张贴图**；而场景正好 3 个 texId（Barrel_01 / 鱼桶 / Terrain_far_01）→ 池子**零余量** → 每帧分配必先淘汰，LRU 抖动，大量 tile 停在 mip2（128px/格 = 整张 512）→ 全场景糊。
  - 对照：T=1 时 level0 能放 48 张。**开 T 会把缓存容量按 T² 打折，这是最容易忽略的代价。**
- **mip 公式缺陷**：`FeedbackPass.hlsl` / `ClusterPass.hlsl` / `ClusterPBR_BRG.shader`(GBuffer+Feedback 两处) 里
  `uv = baseUV * _VTFeedbackParam.y`（= CellSize），**没乘 T** → texel 密度低估 T 倍 → 少算 log2(T) 级 mip（T=4 少 2 级）
  → 每帧都替中远距离像素申请最高分辨率页 → 把本就缩水的池子打爆。
  已全部改为 `_VTFeedbackParam.y * (float)max(1, _TilesPerAxis)`（T=1 时与旧式等价，零回归）。
- **配置已改**：`CellSize 512→1024`，`TilesPerAxis 4→2`（虚拟分辨率仍是 2048，但页数 16→4，level0 容量 3→12 张贴图）；
  图集 6336²→12480²，单张 RT 160MB→623MB，5 张共 ~803MB→~3.1GB。
- **遗留限制（下次别当 bug 查）**：
  1. `mipsLevel` 是全局级数，图集边长 ∝ `mips`（且 padding 项 ∝ `2^(mips-1)`），级数多了显存吃不消。
     **更正（上一轮写错）**：本布局每个 mip 级虚拟分辨率【相同】= CellSize × T，级别只提供「tile 粒度」选择，
     level i 的采样率 = `V / (SourceSize · 2^i)`。级数少 → 最粗级别不够粗 → 远处只能硬用较细级别（费页、易闪），不是"分辨率上限"。
  2. 单一全局 T 无法同时适配 1024 的桶和 4096 的地形；真正的解是**逐贴图 T**（按 `ceil(texSize/CellSize)` 取），当前架构没做。
  3. `CellCount` 才是容量旋钮，但它是平方级吃显存；要装几十张贴图必须换「扁平统一页池」布局，不是调参数能解决的。
- **一行 A/B 验证法**：把 `Mips Level` 改 1（只剩 mip0，反馈全被 `_MaxMipIndex=0` 挡掉）→ 若画面立刻变清晰，即证明是"页池抖动回退到低 mip"，而非采样/材质问题。
- **将来真要做虚拟几何**：在 compute 里做逐簇视锥/遮挡剔除 + indirect draw（`Graphics.RenderPrimitivesIndexedIndirect` / BRG indirect），**绝不要回到 CPU 逐簇 DrawMesh**（已证伪）。
- **代码改动**：`ClusterAssembleAsset` 删 2 个字段；`ClusterObject` 删簇材质缓存/`GetOrCreateClusterMaterial`/两个 branch/`m_clusterRenderDisabledRenderer`/OnDisable 里的 `ClusterRenderManager.Unregister`；`DefferPipeline` 删 `RenderLoop.DrawCluster` 块；`assemble.asset` 删对应 YAML key。
- **归档（未删除，工程无 git）**：`_Deprecated/ClusterPath/` 下 4 个文件 —— `ClusterMeshBuilder.cs`、`ClusterRenderManager.cs`、`ClusterPBR_Cluster.shader`、`ClusterPBR.shader.bak`（含 .meta，移动保留 GUID）。`ClusterStruct.cs` 保留（`ClusterData.hlsl` 仍被 `ClusterInclude.hlsl`→`RVTShader.shader` 使用，C# 镜像留着无害）。
- **必须保留、容易误删**：`ClusterPBR.shader`（`ClusterRenderDataAsset` 用它 `Shader.Find("Unlit/ClusterPBR")` 建 AssetMat）、`ClusterInput.hlsl`（ClusterPBR 的 include）、`ClusterInclude.hlsl`（RVTShader.shader 的 include）。

## 「分辨率算够了还是糊」的真凶：mip 公式多出一个常数项（2026-10-19，已修）
用户把 CellSize 调到 1024、mipsOffset 手动调到 -1.41 仍糊 → 说明还有容量之外的因素。逐行核对后找到：

- **原公式**（4 处：`ClusterPass.hlsl`、`FeedbackPass.hlsl`、`ClusterPBR_BRG.shader` 的 GBuffer + Feedback 两处）：
  `mip = clamp(speed * log2(max(dot(dx,dx),dot(dy,dy))) + 1.0 - speed + offset, 0, mips-1)`
  末尾那个 **`+ 1.0 - speed` 是多余常数**。代入默认 speed=0.277/offset=0.15：
  屏幕 1 像素 = 1 虚拟 texel（1:1，本该 mip=0）时算出 **0.873** → 三线性 `smoothstep(0,1,0.873)=0.956`
  → **95.6% 权重落在半分辨率的 level1** → 虚拟分辨率明明够，画面永远比不用 RVT 糊整整一级。
- **已修**：删掉 `+ 1.0 - _VTFeedbackParam.x`，改为 `clamp(speed * log2(...) + offset, 0, mips-1)`。
  1:1 → mip=0（纯 level0），与硬件 mipmap 约定一致。`mipsChangeSpeed` 0.277→**0.25**（log2 内是 `dot(dx,dx)=|dx|²`，故 0.25 等效标准斜率 0.5）；`mipsOffset` 默认 **0**（想更清晰可调负值，如 -0.5）。
- **四份副本必须逐字一致**，否则「请求的页 ≠ 采样的页」。

## RVT 图集缺各向异性过滤（2026-10-19 定位并修复）
用户对比「RVT 运行时 / 不开 RVT 运行时 / 不运行」三张截图，认为运行时精度都不够。逐项排查结论：

- **先排除的**：`QualitySettings` 在 Fantastic 档 `textureQuality=0`（全分辨率）、`streamingMipmapsActive=0`、
  `renderScale=1`（GBuffer 与屏幕同分辨率）、GBuffer RT0=ARGBFloat —— 都不是降质来源。
- **真实差异（已修）**：桶的 `prop_barrel_01_a.tif` / `_n.tif` 导入设置是 **`aniso: 9`**（各向异性过滤等级很高），
  标准路径 `PBRInput.hlsl` 用 `sampler_MainTex`（材质属性纹理的采样器）→ 吃到 aniso；
  而 RVT 图集采样用的是**全局** `sampler_linear_repeat`，**aniso 恒为 1**。
  圆柱侧面、地面这类掠射角表面因此显著更糊 —— 这是「RVT 比不用 RVT 糊」的真实技术来源之一。
- **修法（关键机制）**：Unity 只有在采样器对应「**材质属性纹理**」时才会沿用该纹理自己的 `anisoLevel`。
  所以把 5 张图集从「纯全局纹理」改成「材质属性」：
  1. `UnityInput.hlsl` 加 `SAMPLER(sampler_VirtualAlbedo/Normal/Mask/Emission/Detail)`
  2. `ClusterInput.hlsl` + `ClusterPBR_BRG.shader` 的 GetColor 全部改用 `sampler_Virtual*`（不再用 `sampler_linear_repeat`）
  3. `ClusterPBR.shader` / `ClusterPBR_BRG.shader` 的 Properties 加 5 个 `[HideInInspector] _Virtual*` 2D 属性
  4. `TileTable.CreateAtlasRT()`：`anisoLevel = 8`
  5. `ClusterObject.ApplyAtlasTextures()` + `BindAtlas()`：运行时把图集 `SetTexture` 到所有材质
     （`AssetMat` 与 BRG 克隆材质）。**时序陷阱**：`ClusterObject.OnEnable`（场景加载）早于
     `ClusterCore.Initialize`（首次 Render），所以必须「静态字段暂存 + Initialize 回填已存在材质 +
     新克隆材质时立即绑定」三处配合。

## Unity 2022 报 "State comes from an incompatible keyword space" 的成因与修法（2026-10-19）
- **现象**：`ScriptableRenderContext.Submit()` 处刷 `Incompatible keyword states`，
  Expected 是 `CustomRP/Defferer/DefferCamera`（15 个 keyword），Actual 是 `Hidden/Internal-Loading`（4 个）。
- **根因**：`Shadows.SetKeywords` / `Lighting.ReadyClusterLight` / `ClusterLight` 用
  `buffer.EnableShaderKeyword(...)` 设的是**全局 keyword**（_DIRECTIONAL_PCF3/5/7、_OTHER_PCF3/5/7、
  _CASCADE_BLEND_SOFT/DITHER、_USE_CLUSTER、VISABLE_LIGHT_COUNT）。全局 keyword 一旦 Enable 就持续，
  会跟着 CommandBuffer 的**后续所有命令**走。而**无材质的 `buffer.Blit`** 内部用 Unity 内置的
  `Hidden/Internal-Loading`（keyword 空间只有 4 个 stereo），Unity 做 `LocalKeywordState::Union` 对不上 → 断言。
- **触发点**：`DefferPipeline.cs` 的两处无材质 Blit —— 一处是 CopyColor
  （`ColorAttachmentId → CameraColorTexId`，对应 Game 视图堆栈），一处是 `cameraType != Game`
  分支（对应 Scene 视图堆栈）。用户给的两段堆栈正好各对应一处。
- **修法**：改走管线自己的材质。基类已有 `Draw(from, to, pass)`（设 `_SourceTexture` +
  `SetRenderTarget` + `DrawProcedural(material, pass)`），两处都换成
  `Draw(ShaderProperty.ColorAttachmentId, target, (int)DefferRenderPass._CopyColor)`（_CopyColor=0）。
  这样用的是 DefferCamera 材质，keyword 空间一致，行为与 Blit 等价。
- **同类隐患（未改，开启后会同样报错）**：`AmbientOcclusion.cs:61` 和
  `StochasticScreenSpaceReflection.cs:356/409` 也有无材质 `buffer.Blit`；
  那两个类没有 DefferCamera 材质，改造需另找拷贝 pass，等真正开 AO/SSR 报错时再处理。
- **不是本轮 aniso 改动引入的**：那批改动只碰 Cluster 的 shader/C#，与 DefferCamera 无关；
  只是 shader 重编译后 Unity 重新做了这项严格校验才暴露出来。

    `assetMat:0`，**没有 occlusion 槽**，detail 语义（打包 R/G/B/A）也与 Standard 两张图不同。
  - `ApplyStandardMaterials()` 手工 new Material + 逐属性拷贝，**从不 SetTexture("_DetailMap")、
    从不 EnableKeyword("_DETAIL_MAP")**（注释明写"detail 默认不开"）→ 6× 平铺 4096 的高频细节层
    与 AO 整层消失。基础贴图只有 prop_barrel_01_a（2048），撑不起来。
- **结论**："糊"不是采样精度问题，是**整层细节被丢掉**。此前 aniso / 页池容量 / mip 常数项
  都是在补一个根本不存在的差距（只有次要贡献）。
- **已修**：`ApplyStandardMaterials()` 加前置判断——若 `original[i].shader == DefferStandard`
  则**原样沿用不重建**（工程 40 个材质里 38 个命中）。这样 Play(UseRVT=0) 与 Edit 走完全相同的
  材质与 keyword，可直接作为精度基准。
- **未修 / 下一步**：RVT 路径仍结构性追不上，因为 BRG 材质源是 `AssetMat
  = new Material("Unlit/ClusterPBR")`（由稀疏 ClusterRenderDataAsset 填充），不是场景材质。
  且 detail 是平铺纹理，**不该虚拟化**（图集按 baseUV 分页，6× detailUV 会越页）。
  正解：基础层走 RVT，detail/occlusion 直采（照 `PBRInput.hlsl` 的 `_DETAIL_MAP` 分支实现，
  带 NaN 安全混合）。需先与用户确认再动 shader。
- 另外确认：**RVT 反馈只在 `cameraType == Game` 执行** → Scene 视图下页表永不更新，
  用 Scene 视图比较 RVT 开关本身无效。

## 采纳业界「detail 直采」方案并落地（RVT 路径）

- **用户提问**：听说过"有 Detail 的可以直接写进 Albedo，同一个 Detail+参数的全部烘进 Albedo，不额外占空间"，是否可行。
- **结论：说法部分正确，但对本工程是错的选择**（分析要点，已写进 MEMORY.md）：
  - 合成进 VT/Albedo 后，**清晰度上限 = 承载它的那张图的分辨率**。
    本项目 VT 虚拟分辨率 = CellSize×T = 2048；detail 有效密度 = 4096×6 = 24576 texels/UV，**差 12 倍**。
    烘进去 = 把高频细节砍到 1/12，正是用户嫌糊的那一层。
  - 显存不省：detail 信息没消失，只是换地方；要么 albedo 涨到合成后分辨率，要么保留 detail 原图用于烘焙。
  - 还会丢掉硬件 mip + 硬件 aniso（图集无 mipmap），且运行时改 detail 参数要重烘。
  - 业界确实有这做法（UE RVT 合成、megatexture、离线 detail 烘 base），但它解决的是
    **运行时采样开销 / 贴图槽位**，不是清晰度。
- **已实现「detail 直采」**（业界对平铺纹理的标准做法）：
  1. `ClusterPBR_BRG.shader`：
     - Properties 新增 `_DetailNormalMap`（与 DefferStandard 同名，克隆时按名带过来）。
     - 新增 `TEXTURE2D(_DetailMap)` / `TEXTURE2D(_DetailNormalMap)` / `SAMPLER(sampler_DetailMap)`。
       （已确认 `ShaderLibrary/Common.hlsl` 只 include UnityInput + Core CommonMaterial，不含 PBRInput，无重复声明。）
     - `GetBase(colors, detailMap)` / `GetNormalTS(colors, detailNormalMap)` / `GetRoughness(colors, detailMap)`
       三处改为**直采**，公式与 `PBRInput.hlsl`（Standard）逐字对齐
       （albedo 用 detail.r、roughness 用 detail.b + mask.g，均为 `map*2-1`）。
     - detail 法线**重新启用**，三重安全：① C# 无贴图时 `_DetailNormal=0`；② `detail.z` 下限 0.05 防
       BlendNormalRNM 除零；③ `!(dot(b,b) < 1e6)` 非有限值回退基础法线。
     - frag 里先按强度闸门采样 detail（最多 2 次额外采样），再传给三个函数。
  2. `ClusterObject.cs`：
     - `OnEnable` 在 `meshRender.materials` 覆盖前抓取 `sceneMats`。
     - BRG 材质源从 `AssetMat` 改为 **场景原始材质**（`GetOrCreateBRGMaterial(brgSrc, ...)`），
       这样才能带过 `_DetailMap`/`_DetailNormalMap`/`_DetailMap_ST`(6,6)；AssetMat 只有五槽且 detail 是打包语义。
     - `GetOrCreateBRGMaterial` 内加 detail 安全门控：无 `_DetailMap` → `_DetailAlbedo/_DetailRoughness=0`；
       无 `_DetailNormalMap` → `_DetailNormal=0`；并把 DefferStandard 的 `_DetailNormalScale`
       搬到 BRG 的 `_DetailNormal`（属性名不同，切 shader 不会自动带过来）。
- **未做 / 下一步**：occlusion（`_OcclusionMap` strength 0.8）仍未接入 RVT 路径；
  `_VirtualDetail` 图集采样现在已无人使用（每次 tap 多一次纹理取样 + 占 1/5 图集显存），可后续清理。

## 修「Property (_LevelData) exceeds previous array size (4 vs 3)」+「什么都没渲染」

- **报错**：`Shader.SetGlobalVectorArray` 报 `_LevelData` / `_LevelPadding` "exceeds previous array size (4 vs 3). Cap to previous size."
- **根因**：`TileTable` 构造函数里 `new Vector4[mipLevel]` —— 数组长度**跟着 mipsLevel 变**。
  Unity 的全局数组尺寸在**首次 SetGlobalVectorArray 注册时锁死**（native 侧，跨 domain reload 存活），
  之后用更长的数组去设会被**静默截断**。用户 mips 3→4 → 第 4 级 levelData/levelPadding 恒为 0
  → 该 mip 级所有页映射到图集原点 → 整屏黑/什么都不渲染。
- **已修**：`TileTable` 新增 `public const int MaxShaderMips = 7`，数组固定分配 7 个
  （与 `UnityInput.hlsl` 的 `float4 _LevelData[7] / _LevelPadding[7]` 对齐），只填前 mipLevel 个。
  多出来的槽位保持 0，永远访问不到（mip clamp 到 mipsLevel-1 ≤ 6）。
  **注意：当前 Unity 会话已把尺寸锁成 3，必须重启一次 Unity 才会重新注册成 7。**
- **同时修掉一个致命编译错误**：`ClusterPBR_BRG.shader` 法线诊断分支里还引用 `pageIdMin`，
  但上一轮做「手动各向异性」重构时把它删了 → **未定义标识符 → 整个 GBuffer Pass 编译失败 → 什么都不渲染**。
  这才是「什么都没渲染」的主因，数组截断是次因。
  修法：抽出 `int GetPageId(baseUV, index, mip)` 作为 pageId 编码的**唯一出处**
  （必须与 Feedback Pass / RVTFeedbackCompact.compute 逐字一致），`SampleRVTAt` 与诊断模式 2 都复用它。
- **教训**：改 shader 内取数结构时，**诊断/调试分支里引用的局部变量最容易漏改**，而 HLSL 编译失败
  在 Unity 里表现为「物体整体消失」而不是半截画面，很容易被误判成运行时逻辑问题。

## 结论：平铺 detail 不该做「独立的 Detail VT」（用户问过，已答复）

- detail 是 **6× 平铺**，没有唯一 UV 参数化 → VT 的核心价值（大贴图按需驻留）对它无效。
- 一个 tile period 就是整张 4096 图，做 VT 等于原样塞进图集；虚拟分辨率必须 ≥4096 才不比原图糊，
  图集要从现在的 3.4GB（13056²×5）涨到 4 倍以上，收益为零。
- 图集 `mipCount=0` 无 mip 链 → 放进 VT 会**丢掉硬件 mip + 各向异性**，掠射角反而更糊。
- detail 常驻成本极小：4096² BC7 ≈ 21MB（未压缩 67MB），根本没有"装不下"的问题，不需要虚拟化。
- 业界（UE RVT / Decima / Far Cry）确实会把 tiled layer **烘进 VT 页**，但那是为了
  **省 shading 时的多次采样**（地形 8 层混合），代价是清晰度受限于 VT 分辨率。
- 所以本工程走 **detail 直采**（上一轮已实现）= 业界对平铺纹理的标准做法。
- 用户当时的理解「细节写进 Albedo 导致不清晰」需纠正：实际是 `Barrel_01.asset` 的 `detail: 0`，
  槽位是**空的**（`_VirtualDetail` 走默认灰图），不是被烘进 albedo。

## 遗留
- `_OcclusionMap`（strength 0.8）仍未接入 RVT 路径。
- `_VirtualDetail` 图集现已无人使用（每次 tap 白采一次 + 占 1/5 图集显存），待清理。
- 手动各向异性最坏情况：4 taps × 2 mips × 5 图集 = 40 次纹理取样/像素，掠射角开销大，可下调 taps。

## 修「管线自带 Debug Mode 在 Scene 视图无效」

- **现象**：detail 效果正确后，RenderPipeline 资产上的 `DefferDebugMode`（Color/Normal/Albedo/PBRData）切换没反应。
- **根因**：`DefferPipeline.DrawFinal()` 里 `camera.cameraType != CameraType.Game`（即 Scene 视图）那条分支
  被硬编码成 `_CopyColor`。这是上一轮修 `State comes from an incompatible keyword space` 时，
  把无材质 `buffer.Blit` 换成 `Draw(...)` 顺手写死的 —— **Game 视图正常，Scene 视图永久显示最终颜色**，
  而用户主要就在 Scene 视图看效果，所以表现为「Debug Mode 显示不出来」。
- **已修**：把 pass 选择（normalDebugMode 优先级最高，其次 switch(defferSetting.debugMode)）提到分支之前，
  Game / Scene 两条分支共用同一个 pass。`Draw(from,to,pass)` 在 RenderPipelineBase 里是通用的
  （SetRenderTarget + DrawProcedural），任意 pass 都能走。
- **教训**：为绕开一个 bug 写死参数时，务必确认没有顺手关掉别的既有功能；Scene/Game 双分支最容易顾此失彼。

## 「近处普通 SRP / 远处 RVT」方案评估（用户提议，已答复，未实现）

- 用户方案方向**正确**，但收益来源要摆对：
  1. **Draw call**：远处物体数量最多，正是 BRG 批处理收益最大处；近处改回 DrawRenderers 损失有限
     （SRP Batcher 下同类材质切换便宜）。所以「远 BRG / 近普通」把 BRG 用在了刀刃上。
  2. **Per-pixel（大头）**：近处物体占屏幕 50~80% 像素，正是 per-pixel 最敏感处。
     RVT 路径要页表随机读 + 最多 4 taps × 2 mips × 5 图集 = 40 次取样，且图集 13056²/3.4GB
     **纹理 cache 命中率极差**；直采 2048² 小贴图 + 硬件 mip/aniso 只要 5~8 次、cache 友好。
- **更优的等价实现（推荐）**：**保留 BRG 做批处理**，只在 shader 里按距离分支（近=直采 _MainTex，远=RVT）。
  BRG 材质现在已经是从场景材质克隆的，`_MainTex`/`_NormalMap` 都在，直采分支直接有数据。
  避免在 C# 侧运行时反复启停 MeshRenderer / 注册注销 BRG（有抖动和 pop 风险）。
  阈值建议**逐实例**（按包围盒中心距离）而非逐像素，否则同一表面跨阈值会闪。
- **必须提醒的反直觉点**：RVT 的真正立身之本是**显存/流式**，不是性能。
  Viking Village 仅 ~40 材质、贴图 2048/4096，全常驻几百 MB；而 RVT 图集自己就 3.4GB → **显存净亏**。
  纯为性能的最优解其实是「全部直采 + BRG 只做批处理」，RVT 只留给将来超大/需流式的贴图（UE 的实际做法）。
- 「近处 RVT 也够清晰」是有条件的：base albedo 源图就是 2048，VT 虚拟分辨率也 2048，1:1 刚好够；
  相机再拉近超过 1:1 像素密度就会开始糊。detail 现在看起来清晰是因为它走直采分担了高频。
- 动工前先让用户在 GPU Profiler / Frame Debugger 里量 GBuffer pass 占比，别盲改。

## 修「非 Cutout 材质被误裁剪」——clip 没有 _CLIPPING 门控（用户指出）

- **用户反馈**：Game 视图地面上出现几块莫名其妙的黑洞/缺块，怀疑"把不是 CullOff 的 Mask 读成了 CullOff"。
- **根因（确实是 bug）**：`ClusterPBR_BRG.shader` 的 GBuffer frag 里写的是
  `clip(albedo.w - _CullOff);` —— **无条件裁剪**。
  而 Standard（`Renderer/DefferPipeline/PBR/Input/GBufferPass.hlsl:75`）是：
  ```hlsl
  #if defined(_CLIPPING)
      clip(base.a - GetCutoff());   // GetCutoff() = INPUT_PROP(_CullOff)
  #endif
  ```
  `_CullOff` 在每个材质上都恒有值（本工程全部 `_CullOff: 0.5`），
  但 `_CLIPPING`（DefferStandard 的 `[SubToggle(ClipSetting,_CLIPPING)]`）**全工程只有 3 个材质开**：
  `mat_strawroof_cutout_01` / `mat_fish_01` / `LitDefferer`。其余 37 个材质根本不该裁剪。
  于是只要 albedo 的 alpha（= 贴图 alpha × `_Color.a`，本工程 `_Color.a` 恒 1）落到 0.5 以下，
  该像素直接被 discard。多 tap 各向异性求平均时，1/4 的 tap 落到空页/邻页就可能把均值拉到 0.5 以下
  → **地面凭空出现黑洞/缺块**，且 Edit 模式（走原材质、无 `_CLIPPING`）完全正常。
- **已修**（3 处）：
  1. `ClusterPBR_BRG.shader` GBuffer pass 加 `#pragma multi_compile _ _CLIPPING`
     （**用 multi_compile 不用 shader_feature**：BRG 材质是运行时 `new Material(src)` 克隆的，
     构建时没有任何材质资产引用本 shader 的这一变体，shader_feature 会被整条剥离）。
  2. frag 里 `#if defined(_CLIPPING) clip(albedo.w - _CullOff); #else clip(_CullOff + 1.0); #endif`
     —— else 分支恒真，只为把 `_CullOff` 留在编译产物里（DOTS/BRG 的 cbuffer 布局校验要求成员不被优化掉，
     与 ShadowCaster 里 `clip(INPUT_PROP(_CullOff)+1.0)` 同一用途）。
  3. `ClusterObject.GetOrCreateBRGMaterial` 显式搬运 keyword：
     `if (src.IsKeywordEnabled("_CLIPPING")) m.EnableKeyword("_CLIPPING"); else Disable`。
     不搬的话真镂空材质（草屋顶/鱼）在 BRG 下会变实心。
- **口径核对（其余 mask 通道都对得上，不用改）**：
  Standard `_MaskMap` = r:metallic / g:AO / b:detailMask / a:roughness，与 BRG 的
  `mask.x→metallic`、`mask.y→AO`、`mask.z→detail`、`mask.w→roughness` 完全一致。
- **遗留（死代码，未改）**：`Input/ClusterPass.hlsl:118` 也有同样的无条件 `clip`，
  但只有 `Unlit/ClusterPBR`（`ClusterRenderDataAsset.AssetMat`）用它，而 BRG 接管后
  那些 MeshRenderer 全被 `enabled=false`，该 pass 不参与绘制。若将来重新启用那条路径需同样加门控。

## 「RVT 低精度下仍然慢 100 帧」分析（360 → 260 fps）

- **用户配置**（screenshot / assemble.asset）：CellCount=2, CellSize=256, mips=4, T=4（asset 文件里实际存的是 T=1）。
- **结论：低精度 ≠ 低开销。** CellSize / T 只改变「虚拟分辨率 V = CellSize×T」和「图集边长」，
  **完全不改变每像素的采样次数**。所以把精度调低只是画质变差，per-pixel 成本一分不少。
- **成本三块（按量级排序）**：
  1. **Feedback 是第二遍全场景几何**：`ClusterCore.RenderFeedback` 在 `isFinish` 时用
     `DrawRenderers(feedbackTagId)` 把整个不透明场景再画一遍到全屏 `feedbackTex`（fbScale=1 → 全分辨率，
     depth 32）。重绘节奏被 `AsyncGPUReadback` 卡住 → 大约每 2~3 帧一次，折合 +1/3 个场景 pass。
     这就是「加了 RVT 就掉 1ms」里最大的一块。
  2. **per-pixel 采样**：每个 tap = 1 次 `_TextureNodesBuffer` 结构化读 + 最多 5 张图集采样，
     且要做 mip 三线性 → 实际 2 次 SampleRVTAt（minMip/maxMip）。最坏 4 taps × 2 = **40 次取样/像素**，
     典型也要 10~20 次；直采路径只要 6 次（albedo/normal/mask/emission + 2 张 detail）。
  3. **抖动重绘**：每帧最多消费 15 条新页，每条 `tileTable.DrawTile` 都是一次 5 渲染目标、CellSize² 的绘制。
     容量不够时页会被反复淘汰 → 每帧固定烧这块。
- **容量算式复述**：level0 可容纳贴图数 = `CellCount² × mipsLevel / T²`。
  - CellCount=2, mips=4, T=4 → **1 张**（场景 ~40 材质 ⇒ 每帧疯狂抖动，这是"低精度反而更慢"的主因之一）
  - CellCount=2, mips=4, T=1 → 16 张（asset 当前存的值，虚拟分辨率只有 256 → 糊到不可用）
  - CellCount=6, mips=4, T=4 → 9 张；CellCount=4, mips=4, T=4 → 4 张
  - **CellCount 是平方关系，1 个数的变化等于 4~9 倍容量**，调参优先动它，别动 CellSize。
- **本轮改动（纯收益，零风险）**：`ClusterPBR_BRG.shader` 的 `SampleRVT` 里删掉
  `colors.detail = SAMPLE_TEXTURE2D_LOD(_VirtualDetail,...)` → 填 0。
  detail 改直采后该通道**没有任何读取者**，但每个 tap 仍在白采一次图集 → 占 RVT 采样量 1/5。
  （结构体字段与 AddColors/ScaleColors 保留，保证与 ClusterInput.hlsl 的逐字副本一致；
  第 5 张图集 `_VirtualDetails` 仍被 DrawTile 写入，暂不删，等链路稳定再一起清理。）
- **其他可选优化（未做，等用户决定）**：
  - taps 阈值抬到 `>12 才 4 taps`、`>4 才 2 taps`（现在是 6 / 2）→ 掠射角采样数减半。
  - Feedback 降频：`isFinish` 上加一个帧计数，静止或页表稳定时降到每 6~8 帧一次
    （不能完全跳过：LRU 与丢页补帧依赖它，见 `RenderFeedback` 里的注释）。
  - Feedback 半分辨率（`FeedbackScale=2`）：几何光栅减半，tile 粒度远大于 1px，请求基本不丢。
  - 根本解法仍是「近处直采 / 远处 RVT」的距离分层。
- **测量方法**：`RenderFeedback` 全程包在 `buffer.BeginSample("Cluster")` 里，Profiler 里直接看这个标记；
  再对比 Turn On/Off `UseRVT` 时 GBuffer pass 的时间差，就能把「Feedback」与「per-pixel」两块拆开。
- 附注：Inspector 里 `Debug Feedback / Debug Feedback Zoom / Rvt Debug Tex` 显示 "Type mismatch"，
  是资产里这几个调试字段的序列化类型与现在的 C# 字段类型对不上（纯显示问题，不影响渲染）。

## 修 Profiler "Non-matching / Missing EndSample"（采样失衡）

- **报错**：`Non-matching Profiler.EndSample: Cluster` / `RenderLoop.DrawBRG`，连带冒出一堆 `RenderLoop.DrawBRG` 失衡。
  用户误以为是设置问题，**实为代码 bug**：`CommandBuffer.BeginSample/EndSample` 配对失衡。
- **根因（系统性）**：`RenderPiplineBase.ExecuteBuffer()` 内部是
  `context.ExecuteCommandBuffer(buffer); buffer.Clear();` —— **每次都清掉 buffer**。
  而工程里大量写成 `buffer.BeginSample(X)` → … → `ExecuteBuffer()`（清 buffer）→ `buffer.EndSample(X)`，
  Begin 已被清掉并执行、End 却留在新 buffer 里 → 失衡。样本栈错乱后，把 Unity 内部的
  `RenderLoop.DrawBRG` marker 也带崩 → 才出现那一串 DrawBRG 报错。
- **共 4 处**：`DefferPipeline.cs:106/115`（SampleName）、`:265/611`（SampleName）、
  `ClusterCore.cs:692/730`（"Cluster"）、`DefferPipeline.cs:365-368`（`"RenderLoop.DrawBRG"`）。
- **修法**：把这种**跨多次命令缓冲提交**的标记，从 `CommandBuffer.BeginSample/EndSample` 换成
  C# 的 `UnityEngine.Profiling.Profiler.BeginSample/EndSample`（不受 `buffer.Clear()` 影响，专门用于
  包裹多次 ExecuteBuffer 的 C# 作用域）。两个文件加了 `using UnityEngine.Profiling;`。
- **`RenderLoop.DrawBRG` 这个名是坑中坑**：它和 Unity 内部同名 GPU marker 冲突，所以单独改名
  `"BRG.Draw"`；原注释里说"EndSample 在下次 Submit 闭合"——那是错的，`buffer` 早已被 Clear。
  现在改成 `ExecuteBuffer(); Profiler.BeginSample("BRG.Draw"); context.Submit(); Profiler.EndSample();`。
- **已确认未受影响**：`Core/Shadows.cs:245/262`、`Core/Lighting.cs:78/82` 等是 `Begin→End→ExecuteBuffer`
  顺序（End 在 ExecuteBuffer 之前），本来就平衡，不动。
- **代价说明**：C# Profiler 样本是 CPU 作用域标记，BRG/GPU 命令真正在 `context.Submit()` 才上屏，
  所以 "Cluster"/"BRG.Draw" 在 Profiler CPU 时间线里有，但 GPU 时间线不会挂这个名。
  要看 RVT 的真实 GPU 开销，仍用 Frame Debugger 看各 pass，或看 Profiler 里 GPU 模块的 "RenderLoop" 子树。

## 「Asset 的 Debug Mode 显示不出来 / Rvt Debug Tex 变 Missing」——两套 Debug 划清边界

**先分清两套，别再混（用户反复踩）**：
- `assemble.asset` 的 `Debug Mode`（`RVTDebugMode`）= **选哪张图集挂到 `Rvt Debug Tex` 槽做 Inspector 预览**，
  **不影响画面**。`Albedo=0 / Normal=1 / Mask=2 / Emission=3 / Detail=4`。
- 管线资产（`DefferPipeline.asset`）里的 `debugMode`（`DefferDebugMode`）= **真正影响画面**的 Debug Mode
  （`Color=0 / Normal=1 / Albedo=2 / PBRData=3`），由 `DefferPipeline.DrawFinal` 选 pass。
- 当前磁盘状态：三个管线资产的 `debugMode` 全是 0（Color）；`assemble.asset` 是 `debugMode: 0`（=Albedo 预览）。

**`Rvt Debug Tex` 为什么是 "Missing (Render Texture)"**：
- 图集 RT 是运行时 `new RenderTexture()`，**不是资产**，`assemble.asset` 里恒为 `fileID: 0`。
- 它只在 `ClusterCore.RequestMinsMap` 里被赋值，而那一帧来自 `RenderFeedback`，
  前置条件：`cameraType==Game` + `Application.isPlaying` + `!EditorApplication.isPaused` + `UseRVT=1`。
  ⇒ **Edit 模式永远是空**；退出 Play / 域重载时这些 RT 被 Unity 销毁，字段还捏着旧引用 → 显示 "Missing"。
- 顺带的含义：**若 Play 中仍然 Missing，说明 RVT 反馈那一帧根本没跑**（UseRVT 关 / 暂停 / 非 Game 相机），
  此时图集也永远不被绘制 → 石头/地面直接采到全黑 albedo。这两个现象是同一个开关，别分开查。

**真 bug（用户说"Normal Debug 关掉了，Debug 核心还是不生效"）**：
`ClusterProverty.NormalDebugModeValue` 原来是 `static { get; set; }` 缓存，只在
`ClusterCore.UpdateRequest`（上面那串前置条件下）同步。一旦设过非 0 值、之后关掉 UseRVT / 退出 Play / 暂停，
缓存就永久停在旧值 → `DefferPipeline.DrawFinal` 永远走 `_DebugAlbedo`，把管线自己的 Debug Mode 钉死。

**已修（4 处 + 1 顺手）**：
1. `ClusterControl.cs`：`NormalDebugModeValue` 改成**实时读资产**的属性 getter（`ClusterControl.Instance.ClusterAssembleAsset.normalDebugMode`），
   Off 时对渲染零干预；缓存语义连同注释一起删掉。
2. `DefferPipeline.Render` 开头每帧 `Shader.SetGlobalFloat(_NormalDebugMode, NormalDebugModeValue)`——
   不再依赖反馈帧，关 RVT / 暂停也能立即生效/失效；与 `DrawFinal` 的 pass 判定同源。
3. `ClusterCore`：把 `RequestMinsMap` 末尾那个 `switch(asset.debugMode)` 抽成 `SyncDebugTex(asset, table)`，
   并在 `Initialize` 建完图集后先绑一次（Play 头几帧不再 Missing）。
4. `ClusterCore.Cleanup`：显式把 `rvtDebugTex / debugFeedback / debugFeedbackZoom` 置 null
   → 退出 Play 后 Inspector 显示 **None** 而不是 Missing。
5. 顺手：`RenderFeedback` 里的 `Profiler.EndSample("Cluster")` 原来写在 `if (...) { ... }` 外面，
   条件不成立的帧必报 `Non-matching Profiler.EndSample: Cluster` → 已移进 if 内（与 BeginSample 同作用域）。
