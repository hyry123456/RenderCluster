## 「Play 里石头/巨石/鱼/木堆变纯黑，Edit 正常」——根因：RVT 无条件吃 mask，Standard 有白 mask 回退

- **现象**：Geometry/法线都对（Normal Debug 各模式看着正常），但 `pf_boulder_01_*` 这类物体在 Play 里是**纯黑**，
  Edit（场景原材质）完全正常。截图里 Normal Debug Mode=15（图集法线原始字节）呈粉红色 ⇒
  **RVT 页表与图集采样本身是好的**（法线页有数据），所以不是"页没分配/图集没画"那类问题。
- **根因（结构性缺陷 + 数据错配，两者叠加）**：
  - Standard（`PBRInput.hlsl:82`）的 `GetMask(c)` 是
    `if(c.useMask) return SAMPLE(_MaskMap); return 1.0;`，而 `useMask` 只在 `#if defined(_MASK_MAP)` 时为真
    （`GBufferPass.hlsl:66`）⇒ **材质没有 mask map 时 mask 恒为白**：metallic=`_Metallic`、roughness=`_Roughness`、**AO=1**。
  - `ClusterPBR_BRG.shader` 原来**无条件**用图集 mask：`metallic = mask.x*_Metallic`、`roughness *= mask.w`、**`AO = mask.y`**。
    图集 mask 来自 `ClusterRenderDataAsset.pbrData`。
  - **数据错配**：全工程交叉核对（37 个 RVT 资产 × 84 个材质，按 albedo+normal 配对）后发现 **5 个资产的 pbrData
    被填成高光/光泽图而不是 mask**，而对应场景材质的 `_MaskMap` 是空的、`_MASK_MAP` keyword 也没开：
    | 资产 | pbrData 实际内容 |
    |---|---|
    | Boulder_01 / Menhir_01 / Rune_01 | `prop_boulderrunemenhirskull_01_sg.tif`（**骷髅**高光图） |
    | Fish_01 | `prop_fish_01_sg.tif` |
    | Logpile_01 | `prop_barrelbucketboardlogpile_01_m.tif` |
  - **判据**：全工程 37 个 `_MaskMap` 引用**一律是 `*_Mask.png` / `*_MaskMap.tif` / `*_o.tif`，从没有 `_sg`**。
    → `_sg` 图确定不是 mask，是数据填错。
  - **为什么表现是"纯黑"而不是"偏暗"**：高光/光泽图 g 通道普遍接近 0 ⇒ `AO≈0` ⇒
    `DefferCameraPass.hlsl:139/150` 把**间接漫反射与反射整体乘 0**（direct sun 不乘 AO，所以受光面还亮）。
    太阳很低时相机看到的是背光面 ⇒ 只剩被 AO 清零的间接光 ⇒ **纯黑**。Edit 路径 AO=1 所以正常。
- **已修**：
  1. `ClusterPBR_BRG.shader`：新增 `_UseMask`（Properties + 两个 pass 的 `UnityPerMaterial` /
     `MaterialPropertyMetadata` / `#define` 四处齐全），并在 frag 里 `ScaleColors` 之后立刻
     `colors.mask = lerp(float4(1,1,1,1), colors.mask, saturate(_UseMask));`
     —— 放在所有消费者（`GetBase`/`GetNormalTS`/`GetRoughness`/`metallic`/`AO`）之前，一行覆盖全部通道。
  2. `ClusterObject.GetOrCreateBRGMaterial`：`m.SetFloat("_UseMask", src.IsKeywordEnabled("_MASK_MAP") ? 1f : 0f)`
     —— 与 Standard 的 `#if defined(_MASK_MAP)` 判定口径完全一致（和 `_CLIPPING` 同一套思路：看 keyword 真值）。
  3. `ClusterObject`：把 `OnValidate` 里的同步逻辑抽成 `SyncRenderAssetsFromMaterials()` 并加
     `[ContextMenu]`（组件右键即可执行），顺带补了 `i >= mats.Length` 越界保护。
- **待办**：5 个资产的 `pbrData` 仍是脏数据（渲染上已被 `_UseMask` 屏蔽，但会影响图集内容与将来的非 BRG 路径）。
  正确做法是让 Unity 自己写：在场景里选中这 5 类物体 → 组件右键「从场景材质同步 RVT 资产」，
  `pbrData` 会被写成 `Texture2D.whiteTexture`。**不要手改 YAML 填内建白图**（`0000000000000000f000000000000000`
  的 fileID 是 1030x 号段，没先例可抄，写错就是 Missing 纹理）。
- **遗留**：`Input/ClusterPass.hlsl`（`Unlit/ClusterPBR` 那条**已废弃**的 AssetMat 路径）有同样的
  `metallic = colors.mask.x * _Metallic` / `AO = colors.mask.y`，将来若重新启用需同样加白回退。

## 「RVT+BRG 反而更慢（380 → 280 fps）」——归因框架 + 采样点补齐

### 用户给的两张 Profiler 图里【没有 GPU 数据】（两图右上角都是 `GPU: -- ms`）
- 不开 RVT+BRG：CPU 累计 **7.75ms**，380 fps（2.63ms/帧）
- 开 RVT+BRG：CPU 累计 **4.33ms**，280 fps（3.57ms/帧）
- **CPU 反而更便宜、帧率却更差 ⇒ 瓶颈在 GPU**。CPU Profiler 时间线看不到 GPU，
  所以这两张图在结构上就无法回答「谁慢」。

### 归因上的致命坑：用户的 A/B 一次改了两个变量
- `ClusterObject.OnEnable` 里 **BRG 注册写在 `UseRVT` 分支内部**；
  `Use RVT = 0` 时走 `else if (Application.isPlaying) ApplyStandardMaterials()`，
  **BRG 完全不注册**。
- 于是「380 帧」= MeshRenderer + DrawRenderers + 直采；「280 帧」= BRG + RVT 图集采样。
  **缺「BRG + 直采」这一档**，无法区分是 BRG 慢还是 RVT 慢。
  （要做第三档，得给 BRG shader 加 `_UseRVT` 分支：BRG 材质是从场景材质克隆的，
  `_MainTex`/`_NormalMap` 都在，可直接采样。）

### BRG 剔除逻辑核对结论（逐行看过 `BatchRenderManager.OnPerformCulling`）
- **Camera 视图：剔除是对的** —— 逐实例用世界 AABB 对 `cullingContext.cullingPlanes` 测试，
  同 (mesh,材质,submesh) 一条 batch、visibleCount=可见实例数 → 一次 draw。
- **Light（阴影）视图：故意不剔除**，全部实例参与 —— 这是 2026-10-17 修「远处没阴影」的代价。
  工程有 4 个级联 ⇒ **每个级联都画全部实例**（150+ 石头 ×4），这是 BRG 阴影侧的隐藏 GPU 成本。
- **帧中 `context.Submit()`**（`DefferPipeline.DrawGBuffer`）是为了让 BRG 的 GBuffer 绘制赶在光照 pass 之前落地，
  代价是每帧两次提交。（`BRG.Draw` 这个 marker 量到的是 Submit 的 CPU 成本，不是 GPU 成本。）
- 结论：**BRG 本身没有"错误的剔除"**，它的 CPU 开销很小；慢的是 RVT 的 GPU 采样 + 反馈 pass。

### 优化清单（按预期收益排序，等用户定）
1. **Feedback 降频 + 半分辨率**（`FeedbackScale=2`）：整个不透明场景每 2~3 帧重画一遍到全屏 RT，摊薄后 ≈ +1/3 场景 pass。
2. **aniso taps 阈值抬高**：现在 `>6 → 4 taps`、`>2 → 2 taps`；改 `>12 / >4` → 掠射角取样数减半。
3. **emission 图集可以不采**：全工程 `asset.emission` 都是 null（图集里是黑的），白采一次。
4. **近距离直采 / 远距离 RVT**（真正的大杀器）：BRG 材质是从场景材质克隆的，shader 内按距离分支即可。
5. **阴影视图做剔除**：不要全量提交 4 个级联。
6. 场景量级只有 ~40 材质，SRP Batcher 已经让 draw call 很便宜 ⇒ **BRG 的 CPU 收益很小**；
   而 RVT 的立身之本是显存/流式，不是性能 ⇒ 这个场景 RVT 大概率是净亏（图集本身 3.4GB）。

## 修「UnityPerMaterial CBuffer inconsistent size inside a SubShader」（我引入的回归）

- **报错**：BRG 刷 `A BatchDrawCommand is using a pass from the shader "Unlit/ClusterPBR_BRG"
  that is not SRP Batcher compatible. Reason: "UnityPerMaterial CBuffer inconsistent size inside a SubShader" (<Unnamed Pass 2>)`，
  连带船 / 栈桥 / 木板这些物体的**阴影缺失**。
- **根因**：`Unlit/ClusterPBR_BRG` 有 **3 个 pass**（OutGBuffer / Feedback / ShadowCaster），
  但 `UnityPerMaterial` cbuffer 只在前两个里各自声明了一份；
  **ShadowCaster pass 走的是 `Input/ClusterDOTSMaterial.hlsl` 里的第三份**（原本 11 个成员）。
  我加 `_UseMask` / `_UseEmission` 时只改了前两处 → 三处尺寸不一致 → Unity 直接不画该 pass。
- **已修**：`ClusterDOTSMaterial.hlsl` 的 cbuffer + `MaterialPropertyMetadata` 补上两个成员，
  并在文件头写死规则：**同一 SubShader 内所有 pass 的 UnityPerMaterial 成员必须完全一致，
  新增材质属性要同时改 3 处**（GBuffer pass / Feedback pass / ClusterDOTSMaterial.hlsl）。
  ⚠️ 这与「法线链路 5 处」「mip 公式 4 处」是同一类"逐字副本"陷阱。

## BRG 为什么不能比 SRP Batcher 快（结论，已向用户说明）

- **SRP Batcher 不合并 draw call**，它降低的是**每个 draw 的 CPU 成本**（材质常量缓冲一次绑定，
  后续 draw 只更新少量数据）—— 这是 Unity 的"零额外 CPU 开销"路径。
- **BRG 要额外付出**：每帧 `OnPerformCulling`（Unity 调度 + 我们的逐实例测试）、每帧
  `UpdateMatrices` + instance buffer 上传、BRG draw 的 metadata 校验与绑定；
  而且 **BRG 批次不能再走 SRP Batcher**（"not SRP Batcher compatible" 报错就是这个意思）。
- **BRG 的真正价值是 draw call 数量**：上万同 mesh 实例 → 1 个 draw。本场景 1159 实例 → 134 批
  → 267 draw/帧，draw call 本来就不是瓶颈。
- **本场景 BRG 必然更慢的根因**：BRG 接管后 MeshRenderer 被禁用，阴影从
  「Unity 逐级联 per-caster 剔除（1×）」退化成「BRG 每级联全量提交（**4×**）」。
  日志实测：`Shadows.ExecuteDrawShadows` 4.29ms（BRG 开）vs 0.559ms（BRG 关）。

## BRG 无法做 per-cascade 剔除（这是阴影 4× 冗余的根本原因）

- Unity 普通路径：`context.DrawShadows` 对**每个级联各调一次**，每次带不同的
  `shadowSettings.splitData` → 逐 renderer 剔掉不在该级联范围的投射物 → 总工作量 ≈ 1×。
- BRG 路径：`OnPerformCulling` 对**整个光源只调一次**（日志证实：Light 视图提交 1159/帧 = 一次），
  产出**一份** `visibleInstances`；4 个级联全部复用这一份 → 每级联都画全部 1159 个 → **4× 冗余**。
- 所以「级联球剔除」在本工程**必然无效**：阴影距离 `maxDistance=300` > 场景尺度，
  4 个级联的范围并集 ≈ 整个可见区域，任何"相机看得见"的物体必然落在某个级联球里
  ⇒ 实测 Light 视图仍是 1155/帧，与之前 1159/帧无差别。**该剔除不是写错，是剔了也没用。**

## ★★ 终极解法：BRG 原生支持按阴影级联剔除（splitVisibilityMask）

**用户提问**：「BRG 也可以对阴影做逐视锥剔除吧，还是说 BRG 做不到，一定要自己写簇+indirect draw？」

**答案：BRG 就能做到，Unity 有专门 API。之前我们一直用错了。**

- **官方文档**（`BatchDrawCommand.splitVisibilityMask`，2022.1+ 就有，本工程 2022.3 可用）：
  > "Indicates which splits that the draw command is visible in. Unity uses this when it culls
  > shadow map splits simultaneously. **A split refers to a shadow cascade in a directional
  > light shadow map or a cube map face in a point light shadow map.** This is an 8-bit bitfield
  > where a value of 1 indicates that Unity should render the draw command in the split..."
  > 位序：最低位 = 第一个 culling split，最多 6 个 split。
- **我们之前的代码写死 `splitVisibilityMask = 0xff`**（= 所有 split 都画）
  ⇒ 每个实例都被画进**全部 4 个级联** ⇒ **4 倍几何冗余**。
  这就是「BRG 阴影 4.29ms vs 普通 MeshRenderer 0.56ms」的真正根因。
- **改造后的做法**（已实现）：
  1. `Shadows.cs` 收集每个光源每个 split 的剔除球
     （方向光=4 个级联的 `splitData.cullingSphere`、聚光=1 个、点光=6 个 cube 面），
     键 = `light.visibleLightIndex`。
  2. `BatchRenderManager.OnPerformCulling`（Light 视图）：
     Pass A 算每个实例命中哪些 split（mask 的第 i 位 = 命中第 i 个 split），
     按 mask 分组 → Pass B 每组生成一条 draw command，`splitVisibilityMask = 该组的 mask`。
     ⇒ Unity 渲染第 i 个级联时只画掩码含 bit i 的命令，**冗余从 4× 降到 ~1.x×**。
  3. 相机视图不变（一条 batch 一条命令，mask=0xff）。
- **为什么以前"用级联球剔"无效**（2026-10-20 实测）：那版是把「落在**任意**级联球内」的实例
  整批提交（Light 视图仍是 1155/帧，与原来无差别）—— 因为级联球的**并集**≈整个可见区域，
  剔了等于没剔。**split mask 才是对的粒度：按"命中哪几个级联"分组。**
- **并发安全**：剔除回调跑在渲染线程，阴影数据是主线程算的 ⇒ 不能共用可变容器。
  做法：主线程每帧构造**不可变快照**（`ShadowSplitSnapshot`），
  `Interlocked.Exchange` 原子发布；剔除线程 `Volatile.Read` 读快照（拿到的是上一帧或这一帧的完整快照）。
  注意：BRG 剔除在 `context.Cull` 阶段，早于 `lighting.Setup()`→`shadows.Render()` ⇒ 实际用的是**上一帧**的球。
- **踩过的坑**：① 各 batch 的不同 mask 不能共用一份 `s_distinctMasks`（Pass A 会被后面的 batch 覆盖，
  Pass B 再读全错）⇒ 改成按 batch 平铺的 `s_batchMasks`。② draw command 数量不再是「batch 数」，
  必须**先算 mask 再分配**（`UnsafeUtility.Malloc` 的内存 Unity 会自动释放，**不能手动 Free**）。
- **⚠️ 2022.3 没有 `BatchCullingContext.visibleLightIndex`**（编译报错 CS1061，实测确认）。
  ⇒ 剔除侧**认不出当前 Light 视图对应哪一盏光** ⇒ 只能用安全判据：
  **全场只有一盏阴影光源时**才启用 split 掩码（快照里只有 1 个 light 就直接用它的 splits）；
  多盏光 → 退回旧行为（掩码 0xff）。
  另外必须限定 `cullingContext.viewType == BatchCullingViewType.Light`
  —— ReflectionProbe 等视图没有 split 概念，套掩码会画错。
  （若将来要支持多光，需另找识别光源的办法，例如用 `cullingContext.cullingMask` 反查。）
- **新增统计**：`StatShadowSplitDraws` = Σ(实例 × 命中级联数) —— 这才是阴影 pass 的真实负载。
  改造前 = 实例数 × 4，改造后应接近实例数 × 1.x。日志里输出为「阴影实际绘制量(实例x级联)」。

## ★ 实施「BRG 只画 GBuffer，阴影交给 MeshRenderer」（用户要求）

**做法（layer 排除法）**：
1. BRG 物体挪到专用 layer（默认 31，工程 15~31 全空；相机/灯光 cullingMask 实测都是 Everything ✓）。
2. `DefferPipeline` 的 **GBuffer pass** 与 `RenderPipelineBase.DrawUnsupportedShaders` 的
   `FilteringSettings.layerMask` 排除该 layer ⇒ 这些 MeshRenderer 只画阴影、不画 GBuffer（不双重绘制）。
   （`DrawUnsupportedShaders` 必须排除：它用 `overrideMaterial = errorMaterial` + "Always" 标签，
   Unity 会无视材质自己的 pass 直接画 ⇒ 没有 OutGBuffer pass 的物体会变**洋红色**。）
3. BRG 批次的 `filterSettings.shadowCastingMode = Off`（新增 `s_brgCastsShadows` 开关）。
4. `ClusterObject.ApplyShadowOnlyMode(excludeLayer)`：切 layer + MeshRenderer enabled 状态；
   `OnDisable` 里还原 layer（否则退出 Play 后物体永久留在 layer 31）。
5. BRG 模式**不再覆盖** `meshRender.materials`（保留场景原材质给阴影用）；
   AssetMat 只在非 BRG 路径赋值。
6. 时序：模式决定必须在 `context.Cull()` **之前**（剔除在 cull 阶段，layer 换了才进得了投射物集合）⇒
   放在 `DefferPipeline.Render` 顶部。
7. 安全兜底：
   - 相机 cullingMask 不含该 layer ⇒ 不启用该模式（否则物体直接消失）；
   - 灯光 cullingMask 不含该 layer ⇒ `Shadows.ReserveDirectionalShadows` 检测到就
     `BRGShadowExcludeDisabled = true` 自动回退到「BRG 自己投阴影」并打日志；
   - `ClusterControl.TryGetAssembleAsset()`：安全取资产，不触发懒加载单例的
     `AssetDatabase.CreateAsset`（编辑器导入期间会抛 UnityException）。

## ★★ 为什么 BRG 比 SRP Batcher 慢（回答用户提问，核心认知）

**BRG 确实做了逐实例剔除，慢的不是「画了多少几何」，而是「提交了多少条 draw command」。**

- **Unity 的 SRP Batcher：按【材质】合批**。场景 1219 个投射物只用 4 种材质 → **4 个 SRP Batch**（4 条 draw）。
  它不合并 draw call，而是让**每个 draw 的 CPU 成本极低**（材质常量缓冲一次绑定，后续 draw 只更新少量数据）。
- **BRG：只能按【(mesh, 材质, submesh)】合批** —— 一次 draw 只能一个 mesh。
  本场景有 **134 个不同的 (mesh,材质) 组合 → 至少 134 条 draw command**，
  每条还要带自己的 instance buffer 绑定 / metadata 校验 / per-instance 常量更新。
- 实测：134~334 条命令 × ~14µs ≈ 4.8ms，与观测吻合。
- ⇒ **BRG 的合批粒度比 SRP Batcher 粗得多**（多一个 mesh 维度就无法合并）：
  在这个场景里它把 4 条 draw 变成 134 条。
- BRG 的真正价值是「**上万个相同 mesh 的实例**合成 1 条 draw」（10 万棵树那种场景）。
  1159 实例 / 134 组合 ⇒ draw call 本来就不是瓶颈，BRG 反而是负收益。
- 「BRG 把所有物体都扔进去画」这个直觉**部分对**：每条 BRG draw command 确实是
  一次 instanced draw，把该组所有实例一次画完（几何不浪费）；但**命令条数**被放大了。

### 罪魁祸首确认：阴影，而且和「自己写的视锥剔除被改成 Unity」无关
- 用户的阴影管线**一直是** Unity 的 `context.DrawShadows` 画的：
  工程的 `Shadows.cs` 负责的是「算级联 / 分配图集 tile / 设置 `ShadowDrawingSettings.splitData` / 设全局量」，
  **真正画投射物的一直是 Unity**，那个「自己写的视锥体裁剪」就是 `splitData.cullingSphere`
  ——Unity 用它逐 renderer 剔投射物（0.964ms 画 1219 个投射物，很快）。
- BRG 接管后 MeshRenderer 被禁用 ⇒ 投射物不再进 Unity 的 renderer 列表 ⇒ 只能走 BRG 批次路径 ⇒ ~4.8ms。
- ⇒ **"完全用 Unity 的"没错，但那恰恰是快的那条路。**

### B 档「阴影反而更贵」的原因（已修）
`Unlit/ClusterPBR`（AssetMat）**不是 SRP Batcher 兼容材质** ⇒ 阴影投射物不能走 `DrawSRP Batcher`，
1219 个逐个 draw ⇒ ExecuteDrawShadows 0.964ms → 2.391ms。
根因：`ClusterPBR.shader` 的 ShadowCaster / WriteDeep pass 只 include `ClusterDOTSMaterial.hlsl`，
而它的**非 DOTS 分支根本没声明 UnityPerMaterial cbuffer** ⇒ 同一 SubShader 内各 pass 的
UnityPerMaterial 不一致 ⇒ 整个 shader 不是 batch 兼容材质。
**修法**：把 cbuffer 声明统一到 `ClusterDOTSMaterial.hlsl`（DOTS / 非 DOTS 两个分支都声明，
14 个成员**完全一致**），`ClusterInput.hlsl` 不再单独声明。
（`PBRInput.hlsl` 即 DefferStandard 用的就是 `UNITY_INSTANCING_BUFFER_START(UnityPerMaterial)`，已验证兼容。）

### B 档「太亮」的原因（已修）
`ClusterPass.hlsl` 把 SH9 间接光**烘焙进 emissive**（`emissive = sh * diffColor + colors.emission.xyz`），
而延迟最终合成阶段（`DefferCameraPass.hlsl:138`）又用 `_Sh9` 算一次间接漫反射叠加 ⇒ **双重叠加**。
DefferStandard / BRG 路径都不烘焙（见 GBufferPass.hlsl 的注释）。
**修法**：`emissive = colors.emission.xyz`（`sh` 变量保留但不再用）。

## 修好 `Unlit/ClusterPBR`（AssetMat）路径 —— 打开「RVT + 不开 BRG」这一档

之前 AssetMat 路径是死路（两个已知 bug），修好后就能做**三档公平对比**：
- **A** 关 RVT + 关 BRG → 基线（380fps）
- **B** 开 RVT + **关 BRG** → **RVT 的净成本**（几何走普通 DrawRenderers，阴影走 Unity 常规路径，没有 BRG 阴影开销）

## 砍 GPU 的三刀（已实现，2026-10-20）

RVT 的 GPU 增量 ≈ 2.11ms（5.41 vs 3.30），来源：per-pixel 图集采样 + 反馈 pass。
本轮针对 **per-pixel 采样**动刀：

1. **单 mip 取代 min/max 三线性混合**（最大的一刀）
   - 原来每个 tap = 2 次 `SampleRVTAt` = **2 次页表随机读 + 2×N 张图集取样**；
     单 mip 直接取最近一级 ⇒ 全部减半。业界（UE RVT）同样是每页一个 mip、不做 mip 间混合。
   - 开关：`assemble.asset` 的 `rvtTrilinearBlend`（默认 0=单 mip，1=原实现），
     经 `ClusterProverty.RVTTrilinearBlend` 全局下发，shader 里 `_RVTTrilinearBlend`。
   - 代价：远处 mip 跳变（高频闪烁）更明显。
2. **按材质跳过用不到的图集**
   - `_UseMask`（早先已有，但只是把 mask 置白、**采样照做**）→ 现在真的不采；
     新增 `_UseNormal`（源材质无 `_NORMAL_MAP` keyword ⇒ 不采法线图集，直接给 (0.5,0.5,1)）。
   - 一次 tap 原本采 4 张图集（albedo/normal/mask/emission），现在典型材质只采 1~2 张。
   - ⚠️ `_UseNormal` 必须同时改**三处**（BRG shader 的 GBuffer pass、Feedback pass、
     `ClusterDOTSMaterial.hlsl` 的 cbuffer + metadata）—— 少一处就报
     "UnityPerMaterial CBuffer inconsistent size"。
3. **aniso taps 阈值抬高**：`>6 → 4 taps` 改成 `>12 → 4 taps`，`>2 → 2 taps` 改成 `>4 → 2 taps`。

**待用户实测的下一个纯配置项**：`assemble.asset` 的 `Feedback Scale` 1 → 2
（反馈 RT 降到 1/4 像素；反馈 pass = 整个不透明场景每 2~3 帧重画一遍，是 GPU 上的大头）。
没替他改，因为会轻微影响反馈精度。

**仍然缺的关键数据**：Frame Debugger / RenderDoc 的分 pass GPU 时间 ——
它决定「反馈 pass vs GBuffer 采样」各占多少，也就是下一步该砍哪个。

- `[剔除对照] 相机视锥内 MeshRenderer = 1472 / 场景总数 1473 (99.9%)`
  ⇒ **相机确实看得见几乎全部物体**（场景 MeshRenderer 1473 个，BRG 实例 1159 个）。
- `[BRG剔除统计] 判定不一致=0`、`Unity内置测试可见` 与 `Camera视图可见实例` 完全相同
  ⇒ **我们的 `IsVisible` 与 Unity 内置 `GeometryUtility.TestPlanesAABB` 逐实例完全一致，剔除没写错。**
- 结论：「一个都没剔掉」是**正确行为**，不是 bug。剔除这条路在本场景本来就没有收益。

## 架构讨论：indirect / cluster 能否打败 SRP Batcher？（结论）
- **关键前提**：本场景 SRP Batcher 只要 **2 个 draw call** 画 1450 个物体。
  ⇒ 「减少 draw call」这条路**根本没有空间**（2 已接近下限，indirect 撑死到 1）。
- **indirect 本身不快**：它只是把"剔除 + 提交"从 CPU 搬到 GPU，省的是 **CPU**，不是 GPU。
  本机 CPU 剔除 1450 个物体本来就便宜（2.74ms 里那部分很小），所以搬过去没收益。
- **BRG 结构性劣势**：SRP Batcher 按【材质】合批，能跨 mesh；BRG 按 (mesh,材质,submesh)，
  一条命令只能一个 mesh ⇒ 134 条 vs 2 条。BRG 赢的场景是「10 万个同 mesh 实例」，
  本场景每个 mesh 只有 1~8 个实例，摊不平固定开销。
- **真正能赢的三件事（按顺序）**：
  1. **Cluster LOD**：逐簇按屏幕投影面积选 LOD ⇒ 减少的是【三角形】，不是 draw call。
     阴影 pass 现在 4 级联 × 全量几何（~20M tri），这是最大目标。
  2. **Hi-Z 遮挡剔除**：两遍，被房子挡住的簇不画。
  3. 单次 `DrawProceduralIndirect`：把上面可见簇合并成 1 条命令（收益最小）。
- 之前几次 indirect 实验失败的原因：是**CPU 端逐簇 DrawMesh**（几万次 C# 调用 → 4FPS），
  不是 GPU 端 indirect 慢。两码事。
- **验证顺序建议**：先只改 `maxDistance 300→120` + `cascadeCount 4→2`，
  看阴影 0.82 掉多少：掉一半 ⇒ 几何量确实是瓶颈 ⇒ cluster LOD 值得做；几乎不变 ⇒ 瓶颈在别处。

## 第十轮：开工「真正的 cluster 管线」——阴影先行（全新代码，未编译验证）
新增文件：

- `Runtime/ClusterRender/ClusterShadowRenderer.cs` —— 运行时：Rebuild 摊平到【世界空间】

                                                  → 一次 DrawProceduralIndirect
- `Resources/Cluster/ClusterShadowCull.compute` —— 逐簇视锥剔除(用 Unity 的 ShadowSplitData 平面)

接入点：`Shadows.Render()` 里 Rebuild；`RenderDirectionalShadows` 里分岔（Cluster 时跳过 context.DrawShadows）。
设计要点（别改坏）：
- LOD 判据是「每级簇半径按 2 倍递增 ⇒ 任意区域恰好只有一级落在 (T/2,T]」；
  两个极端（比目标粗→只选 level0，比目标细→只选 maxLod）必须保留，否则会破洞。
- 剔除平面直接用 `splitData.GetCullingPlane()`，与 Unity 口径一致，不会出现"远处没阴影"。
- DrawCascade 必须写在 ExecuteBuffer【之前】（它是命令），context.DrawShadows 则在其后。
