# 2026-10-17 工作日志

## BRG 三问题（光滑 / 颜色 / 阴影）根因与修复收尾

### 关键架构澄清：哪套 Shadow/Lighting 是活动实现
- 工程存在**两套平行** Shadow/Lighting 实现：
  - `Runtime/Core/Shadows.cs` + `Runtime/Core/Lighting.cs`（被 `RenderPipelineBase` 的 `lighting = new Lighting()` 使用）
  - `Runtime/MyRenderPipeline/Lighting/MyShadow.cs` + `MyLighting.cs`（被 `MyPipeline` 使用，含 `MyShadow`、无 `GetShadowCasterBounds` 调用）
- **活动管线是 `DefferPipeline`**（BRG + 延迟路径），它继承自 `RenderPipelineBase`，故实际使用 **`Core/Shadows.cs`（Shadows 类）**，不是 `MyShadow.cs`。`MyShadow.cs` 是遗留/死代码路径。
- 结论：上一轮对 `Core/Shadows.cs` 的 `GetShadowCasterBounds` 闸门修复**落在活动路径上**，不是死代码。

### 阴影仍"全无"的真正根因（双层修复，均已落地）
1. **`Shadows.cs` 的 Reserve 闸门**：`ReserveDirectionalShadows` / `ReserveOtherShadows` 内，当 `GetShadowCasterBounds` 返回 false 时，若 `BatchRenderManager.Instance.HasBatches`（即 BRG 接管绘制）则**不能跳过该光**。原因：BRG 物体 MeshRenderer 被禁用 → 不在 `cullingResults` 的 shadow caster 集合 → `GetShadowCasterBounds` 对本应投影的光返回 false → 否则该光被"无投射物"跳过 → `context.DrawShadows` 永不调用 → 阴影图全空。
2. **`BatchRenderManager.OnPerformCulling` 的 `filterSettings.shadowCastingMode = On`**：BRG 批次默认被所有阴影流程静默排除（默认 Off），主画面却正常 → 表现即"画面正常但没阴影"。
- 这两处都在活动路径上，配合使用才完整：闸门保证光被登记并触发 `context.DrawShadows`；`shadowCastingMode=On` 保证 BRG 批次在 `OnPerformCulling` 中被画进阴影图。
- 旁注：`GPUDravinSystem.DrawShadows` 遍历 `node.shadowEvent`，但全工程**从未给任何节点赋值 `shadowEvent`** → 该调用是 no-op。BRG 阴影实际完全靠 `context.DrawShadows` → `OnPerformCulling`，无需手动注册 shadowEvent。

### 光滑 + 颜色错位的根因：BRG 从不提交 RVT 反馈
- `GPUDravinSystem.DrawFeedback` 只遍历注册了 `feedbackEvent` 的节点，而 BRG 从未注册 → BRG 物体的 `(texId,mip)` 永不进反馈 → `TextureNodesMap` 永不分配/流式载入它的图集页 → `GetColor` 采到未初始化页（width/height/mipsLevel=0）。
- 后果：法线/粗糙度(mask.w)通道错乱 → roughness≈0 → **异常光滑**；albedo 取错页 → **颜色不对应**。二者同源（缺反馈）。
- **修复**：给 `ClusterPBR_BRG.shader` 加 `LightMode="Feedback"` Pass（pageId 编码与 `FeedbackPass.hlsl` / GBuffer Pass 逐字一致：
  `pageId = mip*_SumTextureCount + texId*T*T + tileIndex`）。`RenderFeedback` 里的 `context.DrawRenderers(cullingResults,"Feedback")` 会回调 BRG 的 `OnPerformCulling` 用本 pass 提交反馈，MeshRenderer 是否启用无影响。

### 反射公式修正（上一轮引入、本轮订正）
- `ComputeIndirectSpecular`（GI.hlsl:284）内部**仅把 mip 用作 `SAMPLE_TEXTURECUBE_LOD` 的 lod 参数，返回值就是解码后的反射探针颜色，不会乘 mip**。
- 上一轮误信"第3参 mip 被当乘子"，在 BRG 写了 `skyRefl *= reflMip`（最多放大 6×），与 BRG 关路径严重不符。
- **订正**：`reflMip = roughness*(1.7-0.7*roughness)*6.0` 仅作 LOD 层级；`skyRefl = SAMPLE_TEXTURECUBE_LOD(_MySkybox, reflMip).rgb`，**去掉 `skyRefl *= reflMip`**。菲涅尔/AO 仍由合成阶段统一乘。
- 注：`_MySkybox` 与 `unity_SpecCube0` 同源（场景天空盒），BRG 路径不便 include GI.hlsl，故直接用 `_MySkybox` 采样（与 BRG 关的 `ComputeIndirectSpecular` 锐度一致）。

### 待用户验证（本环境无法跑 Unity 编译）
- 三处改动均需进 Play 模式确认：① BRG 物体颜色/粗糙度恢复正常（RVT 反馈生效）；② 反射不再过亮/过光滑；③ 开启 BRG 后阴影重新出现（Frame Debugger 的 Shadows 段应出现 "Hybrid Batch Group"）。

## 续：用户图1（RT1 法线）反馈 —— "同朝向桶面法线差异太大 + 仍过光滑 + 远无阴影"

### 1) 法线 GBuffer 公式与 Standard 逐字一致 —— "抄 Standard" 不需要
- 逐行比对 `ClusterPBR_BRG.shader` frag(:318-323) 与 `GBufferPass.hlsl` LitPassFragment(:74-82)：
  - TtoW 构造（vert 端）两者完全相同；TS→WS 点积 `normalize(float3(dot(TtoW0,n),dot(TtoW1,n),dot(TtoW2,n)))`、`PackNormal(normal)` 逐字一致。
  - BRG 的 `normal` 来源是 RVT `GetNormalTS(colors)`（移植自 ClusterInput.hlsl），Standard 是 `GetNormalTS(config)`（PBRInput.hlsl）；逻辑等价，差异只在取数源（都是 RVT）。
  - 结论：**公式没错**，问题在喂入公式的 RVT 法线贴图数据本身。用户怀疑"GBuffer 写公式错"不成立。

### 2) 反射漏乘 reflIntensity —— 本轮已修（"仍过光滑"主因之一）
- 旧 BRG 反射：`reflMip=roughness*(1.7-0.7*roughness)*6; skyRefl=SAMPLE_CUBE_LOD(_MySkybox,reflMip)`，**无任何强度衰减**。
- Standard（`GBufferPass.hlsl:99-104）：`reflMip=clamp(roughness*7,0,8); refl=SamplerReflectProbe(...); reflIntensity=lerp(saturate(0.05+(1-roughness)*0.6),1,metallic); refl*=reflIntensity;`
- **修复**：BRG 反射改为与 Standard 逐字对齐 —— `reflMip=clamp(roughness*7,0,8)`，补 `reflIntensity` 并 `skyRefl*=reflIntensity`。非金属/粗糙面反射大幅衰减，消除"像镜子一样过光滑"。文件 `ClusterPBR_BRG.shader`。

### 3) 同朝向桶面法线差异大 = RVT 页未流进 BRG（核心未解项）
- 症状：同朝向（应同世界法线→同 RT1 色）却青/品红/蓝各异。RT1 色只取决于世界法线，**与摄像机位置无关**，故"因摄像机位置不同"不成立；只能是**逐物体采到不同（垃圾）法线**。
- 机制链路：GBuffer 用 `pageId=mip*_SumTextureCount+_MapId*T*T+tileIndex` 取 `_TextureNodesBuffer[pageId]`；若 Feedback 没为该 BRG 物体分配/流式载入页 → 节点 width/height/mipsLevel=0 → 采图集随机位 → 逐物体各异；且 `mask.w`(roughness)≈0 → 镜面光滑。
- mip 由屏幕导数(`ddx/ddy(uv)`)算，逐物体在屏上位置/大小不同 → 取不同 mip → 不同（未初始化的）页 → **不同颜色**，完美解释"差异大"。
- 关键观察：`AllocateTextureId` 按 `TextureMapNode` 去重(:196) → 同贴图同 `_MapId`，故 BRG 材质按源材质缓存(`GetOrCreateBRGMaterial`)在常见同 prefab 场景下安全；_MapId 共享覆盖不是主因。最低级页由 `QueueMinsMap`+`InitialTextureNode` 无条件分配(:295)→ 近处(mip0)应正常、远处(mip>0 需反馈升级)才爆 → 与"远/差异大"吻合。
- **待验证根因**：`RenderFeedback` 的 `context.DrawRenderers(cullingResults,"Feedback")` 是否真的让 BRG 批次走 `OnPerformCulling` 提交 Feedback pass 进 `feedbackTex`。若 BRG 批次未在此 DrawRenderers 内被包含（Unity 版本/剔除细节），则 BRG 的 (texId,mip) 永不反馈 → 页永不升级 → 远处垃圾。
- **验证手段（用户进 Play + Frame Debugger）**：展开 "Cluster" → Feedback 采样，看是否有 "Hybrid Batch Group"（BRG）绘制；同时看 `ReveryCluster/asset` 的 RVT debug 图集是否含 BRG 贴图的 tile。若无 BRG 绘制 → 确认 feedback 未覆盖 BRG → 需在 `BatchRenderManager`/管线侧强制 BRG 批次参与 Feedback 的 DrawRenderers（例如显式在 Feedback 阶段提交 BRG 批次，或确认 DrawRenderers 的 filtering/instance 设置允许 BRG）。

### 4) 远无阴影
- `shadowCastingMode=On` + 全局 bounds 已加（`BatchRenderManager`）。近处应有阴影；远处无 = 阴影视锥/距离受限（`Cull` 里 `shadowDistance=min(maxShadowDistance,farClip)`）→ 超出阴影距离的物体本就不在阴影图中。先排查 `ShadowSetting.maxDistance` 是否过小；若近处也无，再回查 `OnPerformCulling` 在阴影视图下的 `cullingPlanes`/`IsVisible` 与 `splitVisibilityMask=0xff` 是否把远处实例错误剔除。

## 续三：编译/运行期两个错误修复

### 1) MenuItem 报错 "is not static and cannot be used for menu commands"
- 根因：`ClusterAssembleAsset.ApplyNormalYFlipMenu` 写成**实例**方法，但 `[UnityEditor.MenuItem("CONTEXT/...")]` 要求方法 `static` 且首参为 `MenuCommand`。
- 修复：`private static void ApplyNormalYFlipMenu(UnityEditor.MenuCommand command){ var asset = command.context as ClusterAssembleAsset; asset?.ApplyNormalYFlip(); }`。

### 2) "State comes from an incompatible keyword space" + Hidden/Internal-Loading 断言崩溃
- 堆栈：`DefferPipeline.Submit()` → `context.Submit()` → `ExecuteCommandBuffer` → `ImageFilters::Blit` → `Shader::ResolveLocalState` → `LocalKeywordState::Union` 失败。
- 根因：`StochasticScreenSpaceReflection.cs` 把 `SSR_HierarchicalDepth_RT` 设为 `useMipMap=true; autoGenerateMips=true`（每帧 `GetTemporary` 重建）。该 RT 是 HiZ 缓冲，其 mip 链由 `SeparateRender/CombineRender` 里的 `for` 循环**手工**用 `DrawProcedural + CopyTexture` 逐 mip 构建。
  `autoGenerateMips=true` 会让 Unity 在该 RT 被采样时额外用内部 shader `Hidden/Internal-Loading`（4 个 stereo keyword 的关键字空间）做自动 mip 生成；而该 blit 与 `DefferCamera`（15 个 local keyword 空间）处在**同一个** `buffer` 命令缓冲（`spaceReflect.BeginRender(buffer,...)` 共用主 buffer），`Shader::ResolveLocalState` 在合并两套关键字空间时断言失败。
- 修复：改为 `autoGenerateMips=false`（保留 `useMipMap=true` 以容纳 mip 链）。手工 HiZ 循环已覆盖全部 mip，关闭自动生成既消除断言，也避免 Unity 用错误（模糊而非 min-depth）的 mip 覆盖手工 HiZ 结果。
- 旁注：全工程 grep 仅 `SSR_HierarchicalDepth_RT` 一处 `autoGenerateMips=true`，RVT 图集/feedback/GBuffer/AO 等 RT 均为 mip 数 0 或 `autoGenerateMips=false`，故这是唯一触发点（前提：SSR 功能开启；若未开启则不会触发本断言）。

## 续四：法线方向问题的两个"假阴性"根因 + TBN 正交化修复

用户反馈：`flipNormalY` 勾/不勾**画面几乎完全一样**，法线仍然不对；阴影 bug 已解决。

### 1) `flipNormalY` 从来没生效过（本轮最重要发现）
- `ClusterAssembleAsset` 只挂了 `OnEnable()` + `[MenuItem("CONTEXT/...")]`，**没有 `OnValidate()`**。
  在 Inspector 勾选复选框只会写序列化字段，**不会调用任何代码** → `_NormalYFlip` 全局量恒为 0
  → 两张截图其实逐像素相同。**上一轮"Y 翻转无效"的结论是假阴性，不是翻转真的无效。**
- 修复：加 `private void OnValidate() => ApplyNormalYFlip();`（Inspector 改字段即生效）。

### 2) `DebugNormal` 调试视图本身不可读（假阴性的另一半）
- `DefferCameraPass.hlsl` 的 `DebugNormal` 直接 `return float4(normalWS, 1)`。
  渲染目标把**负分量硬截成 0** → 画面只能是纯红/纯绿/纯品红的死色块，人眼根本无法判断方向对错。
- 修复：改为 `float4(normalWS * 0.5 + 0.5, 1)`（标准法线可视化）。
  判据：正对相机平面 = (0.5,0.5,1) 淡蓝紫；地面法线朝上 = (0.5,1,0.5) 淡绿；分量为 0 时通道值 0.5。

### 3) 新修：非等比缩放下的 TBN 剪切（最可能的真正根因）
- `ClusterPBR_BRG.shader` vert 与 `GBufferPass.hlsl` `LitPassVertex` 均为：
  `tangentWS = TransformObjectToWorldDir(...)`（只做了 normalize），随后 `cross(normalWS, tangentWS)`。
- **非等比缩放**（场景 prefab 常带）会让变换后的切线与法线**不再正交**，此时 cross 出的 TBN 基是"剪切"的，
  法线贴图所有方向整体偏斜 —— 症状正是"起伏在、方向歪"，且 **Y 翻转对它无效**。
- 修复：加 Gram-Schmidt 正交化 + 退化保护：
  ```hlsl
  float3 orthoT = tangentWS - normalWS * dot(normalWS, tangentWS);
  float lenSq = dot(orthoT, orthoT);
  tangentWS = lenSq > 1e-8 ? orthoT * rsqrt(lenSq) : tangentWS;
  ```

### 4) 新增诊断开关 `useVertexNormalOnly`（assemble.asset）
- `GetNormalTS` 开头 `if (_VertexNormalOnly > 0.5) return float3(0,0,1);` → TS 中值经 TBN 变换后**恰好等于顶点法线**。
- 判据：勾上后法线正常 → 世界法线链(TBN/GBuffer/调试)没问题，问题在"法线贴图数据/解码"；勾上后依旧歪 → 问题在顶点法线/TBN/GBuffer 打包。
- 三处 `GetNormalTS` 同步：`ClusterPBR_BRG.shader`、`ClusterInput.hlsl`、`PBRInput.hlsl`；`_VertexNormalOnly` 声明在 `Common.hlsl` 的 `_NORMAL_Y_FLIP_GLOBAL` 守卫块内。

### 本轮已排除的假设
- 法线贴图导入设置：查了 `Ground_Normal.tif.meta` / `Ferns_Normal.tif.meta`，均 `textureType: 1`(NormalMap) + `sRGBTexture: 0` ✓ 正常。
- DOTS 矩阵：`BatchRenderManager` 的 metadata 同时注册 `unity_ObjectToWorld` 与 `unity_WorldToObject`，
  且 `worldToObject[i] = new PackedMatrix(m.inverse)` ✓ 是真逆矩阵，不是误用 O2W。
- BRG `SampleRVT` 与 `ClusterInput.GetColor` 逐行比对一致（含 `UNITY_UV_STARTS_AT_TOP` 的 y 翻转、pageId 公式）。
- RVT 图集 5 张 RT 共用同一 `node`（`GetColor(uv, texId, mip, detailUV)` 单 texId 设计）→ 布局一致，非错位来源。

## 续五：法线诊断开关的"全局量名不匹配"死穴 + 模式化诊断落地

用户反馈：开/关 `flipNormalY` 差别不大；勾 `useVertexNormalOnly`（仅顶点法线）法线看着没问题 → 用户判断"是投影的问题"。

### 1) 关键修复：assemble.asset 写的全局量与 shader 读的不一致（诊断此前完全死掉）
- 上轮把三处 `GetNormalTS` 改成读 `_NormalDebugMode`（0~5 多模式：0正常/1仅顶点/2标准/3强制AG(DXT5nm)/4强制RG(RGB)/5 Tangent轴可视化），并在 `Common.hlsl`/`ClusterInput.hlsl`/`PBRInput.hlsl` 守卫块内 `float _NormalDebugMode;`。
- **但 `ClusterAssembleAsset.cs` 只写了 `_VertexNormalOnly`（一个没有任何 shader 读的死全局量），从未写过 `_NormalDebugMode`** → 运行时 `_NormalDebugMode` 恒为 0（=模式0正常）→ 所有模式切换无效，诊断形同虚设。
- 修复：`useVertexNormalOnly`(bool) 升级为 `normalDebugMode`(int, [Range(0,5)])；`ApplyNormalYFlip()` 改为 `Shader.SetGlobalFloat("_NormalDebugMode", (float)normalDebugMode)`（同时保留 `_NormalYFlip` 写入）。删除对 `_VertexNormalOnly` 的写入。全仓 grep 已确认无残留引用。
- 旁注：模式 3/4/5 仅在**活动 BRG 路径**（`ClusterPBR_BRG.shader` 内联 `GetNormalTS`，含 `DecodeAGOnly`/`DecodeRGOnly` + 黑守卫 `dot(map.rgb)<1e-5 → (0,0,1)` + frag 模式5 Tangent轴）完整实现；`ClusterInput.hlsl`/`PBRInput.hlsl` 仅含模式1+黑守卫（非活动路径，够用）。
