- **视锥剔除只救「屏幕外」那部分**；你正看着的簇仍在画两遍，所以帧率没回来。
- **修复（正常流程：簇渲染作为唯一渲染路径）**：
  - `ClusterObject.cs`：开启 `useClusterRender` 且所有 submesh 簇数据 `isValid` 时，**关闭该物体的 `MeshRenderer`**（`Application.isPlaying` 才关，编辑器保持可见），并在 `OnDisable` 恢复，避免编辑器网格永久消失。

## 剔除后几何全消失 + 帧率仍低：两处真正的根因（用户反馈定位）
用户反馈：①「不是重复绘制，Cluster 本身有问题，剔除了还是很慢」②「裁剪完后面全部不见了，之前 BRG 是成功的」③ 询问 Unity SRP Batcher。截图证据：Frame Debugger `RenderLoop.DrawCluster` 下 34 组「Compute ClusterCull + Draw Procedural Indirect」，Statistics `Tris: 1.0k / Verts: 609 / CPU main 26.1ms`。

### 根因 1（致命 BUG）：DrawProceduralIndirect 的 args 语义 vs shader 取 slot 方式不匹配
- args 设成 `[96(每实例顶点数), 可见簇数, 0, 0]`，但 shader 仍用 `slot = vertexId / 96`。
- **`SV_VertexID` 在间接绘制里每个实例都从 0 重新开始**（不跨实例连续），恒为 0..95 → `slot` 恒等于 0 → 每个实例都画 `_VisibleClusters[0]` 那**同一个簇**，其余几何全部消失。
- **截图数字互证**：34 组 × 1 个簇 × 32 三角 = **1088 ≈ "Tris: 1.0k"**，完全吻合。
- 修复：`ClusterPBR_Cluster.shader` 顶点签名改为 `vert(uint vertexId : SV_VertexID, uint instanceId : SV_InstanceID)`，`slot = instanceId; localVid = vertexId;`。args 保持 `[96, 可见数, 0, 0]`（绝不能改成 `96*簇数`，否则与 instanceId 约定冲突）。
- 结论：**之前「加剔除后画面消失」不是剔除算法错（球 vs 6 视锥面数学正确），是映射错**。

### 根因 2（性能）：每帧 O(总簇数) 的 CPU 矩阵刷新 + 整块上传
- 旧 `Render` 每帧对**每一个簇**执行 `owner.transform.localToWorldMatrix`（一次 native 调用），并把整块矩阵（簇数 × 64B）重新 `SetData` 上传。场景几万簇时 = 每帧几万次 native 调用 + 数 MB 上传 → 这才是 300→40 的主因（剔除只减 GPU 绘制，救不了 CPU；截图里 GPU 只画了 1.0k 三角却仍 26ms CPU，正说明是 CPU 瓶颈）。
- 修复（`ClusterRenderManager.cs` 重写）：
  - 构建时把「簇 → owner」去重成 `ownerList` + `clusterOwnerSlot[]`；
  - 每帧只对**去重后的 owner**（= 物体数，通常几百）取 `localToWorldMatrix` 并与上帧缓存比对；
  - 全部未变化（静态场景）→ 直接 `return`，跳过逐簇展开与整块上传，每帧 CPU≈0；
  - 有变化时做一次「owner 矩阵 → 逐簇数组」纯托管拷贝后上传一次；
  - 计数器重置改用 `cmd.SetBufferCounterValue`（保证与 dispatch 顺序一致，替代原先立即模式的 `SetCounterValue`）；
  - 删除 identity 回退路径：缺 `ClusterCull.compute` 时直接报错并跳过（原回退会往 append 缓冲 `SetData`，行为不可靠；且 compute 实测能正常加载）。

### 关于 SRP Batcher（回答用户问题，纠正概念）
- SRP Batcher **不减少 draw call，也不能把不同材质合并成一次绘制**。它只是让「同一 shader variant」的连续绘制之间**不再重设 shader 状态/常量缓冲**（per-material cbuffer 常驻 GPU），从而降低每次 draw 的 CPU 开销。Frame Debugger 里的 "SRP Batch" 分组只是标记，不是合并。
- 用户描述的「同一个 shader 共同绘制、参数用数组一起存」= **per-instance / per-cluster 数据数组**（GPU instancing、BRG 的 `_PerInstanceData`、我们的 `_ClusterMatricesBuffer`），而不是 SRP Batcher。这正是 Tier2 的方向。
- 我们的簇路径其实已经隐含了 SRP Batcher 的收益（每个材质只设一次、连续 draw）。

### 簇路径相对 BRG 的固有代价（诚实结论，需向用户说明）
- BRG：硬件顶点获取（vertex cache + post-transform cache）+ 索引复用 + 实例化，是 GPU 最快路径；剔除走 job 线程。
- 簇路径：无索引复用（簇各自重取 96 顶点，顶点放大 ~2.2×，实测 124 簇×96=11904 vs mesh 5465 顶点）+ 每顶点 3 次依赖式缓冲读取（无顶点缓存）+ 每顶点矩阵乘 + padding 退化三角形仍走 VS。
- 因此**簇路径在「全场景几乎全可见」时必然慢于 BRG**；只有当可剔除比例很高（Nanite 式海量三角形/遮挡）才划算。建议后续二选一：① 保留 BRG 作为绘制路径，簇只作剔除/LOD 粒度；② 走 Tier2 把材质参数 per-cluster 化，压到 1 次 draw，再在遮挡密集场景对比收益。

## P7 修正（关键）：本 Unity 构建不支持 SetVertexBufferParams / 带索引 DrawProcedural → 改用 DrawMesh 稳健方案
- **编译报错根因**：`GraphicsBuffer.Target.VertexBuffer`/`IndexBuffer` 成员名实际为 `Vertex`/`Index`（已确认官方页）。但更致命的是：本工程 Unity **2022.3.62f3c1** 构建里 **`CommandBuffer.SetVertexBufferParams` 和 9 参数 `DrawProcedural` 根本不存在**（SRP Core 14.0.12 全仓 grep 不到 `SetVertexBufferParams`；SRP Core 自身只用矩阵开头的非索引版 `DrawProcedural(Matrix4x4, Material, int, MeshTopology, int vertexCount, int instanceCount, MaterialPropertyBlock)`）。编译器报"方法不存在"是权威结论，原 P7 meshlet（GraphicsBuffer 顶点/索引缓冲 + DrawProcedural(indexBuffer)）方案不可行，必须换。
- **已淘汰方案**：P7 第一版（GraphicsBuffer Vertex/Index 缓冲 + SetVertexBufferParams + DrawProcedural(indexBuffer)）已弃用。
- **改用稳健方案（已落地）**：
  1. `ClusterMeshBuilder.cs`：每个 (mesh,submesh) 构建**一个真实 Mesh**（`combinedMesh`），顶点 = 源 Mesh 原始属性（pos/normal/tangent/uv，**零放大**），簇 = 该 Mesh 的**逐簇 submesh**（索引区间引用共享顶点，无 padding）。缺失 normal/tangent 时 fallback 到 `RecalculateNormals/RecalculateTangents`。`ClusterMeshData` 结构改为 `{ combinedMesh, clusterBoundsOS[], clusterCount, vtNodeIndex, isValid, ... }`。
  2. `ClusterRenderManager.cs`：注册项经 `RebuildUnits()` 去重为绘制单元；`Render(cmd,camera)` 算视锥平面 → 每 owner 仅在 transform 变化时刷新矩阵并变换世界包围球 → 逐可见簇 `cmd.DrawMesh(combinedMesh, matrix, material, submeshIndex=c, 0)`；`_ClusterVtId` 逐 owner 设置。draw 数 = 可见簇数，同材质相邻调用由 SRP Batcher 合并。
  3. `ClusterPBR_Cluster.shader`：vs 输入标准顶点属性（POSITION float3 / NORMAL float3 / TANGENT float4 / TEXCOORD0 float2，与 combinedMesh 顶点布局严格对应）；object-to-world 用 `unity_ObjectToWorld`（DrawMesh 自动提供，显式 `mul` 计算避免依赖辅助函数）；`_ClusterVtId` 逐 owner 设置；去掉所有 StructuredBuffer / SV_VertexID / `_ClusterObjectToWorld`。
  4. 删除已失效的 `Resources/Cluster/ClusterCull.compute`（GPU 剔除版，已改 CPU 剔除）。
- **本质**：簇渲染现在走与 BRG **完全相同**的硬件顶点管线（DrawMesh = 真实顶点缓冲 + 索引复用 + post-transform 缓存），仅多了"簇级"这层 CPU 视锥剔除粒度。零顶点放大、零逐帧 GPU 上传。
- **诚实边界**：draw 数 = 可见簇数（非单 draw）；全场景全可见时 draw 数可能上千，但每个是廉价硬件 draw 且被 SRP Batcher 合并，远优于之前手动展开。后续 P7c 可把同 owner 可见簇索引打包进动态 IB → 每 owner 仅 1 次绘制。

## DrawMesh 方案失败 + 业界正确做法调研（重要结论）
- **实测反馈**：DrawMesh 逐簇绘制 → 帧率仅 4 FPS（卡死）。根因：`DrawMesh` 每调用一次 = 一次 CPU draw call 提交，130k 簇 = 130k 次 CPU 提交。**性能杀手是 draw call 数量，不是顶点数**。
- **权威实测数据（Medium《100,000 objects, one draw call》，Unity 2022.3 + RTX 3060）**：10 万 Renderer 组件 = 100k draw / 38.2ms CPU；**单次 Indirect + GPU 剔除 = 1 draw / 0.4ms CPU / 3.8ms GPU**。→ 必须用「单次 indirect draw 画全部可见实例」。
- **BRG 澄清（用户误解已纠正）**：BRG（BatchRendererGroup）**不是** SRP Batcher。BRG 在 C++ 侧把同 (mesh,材质) 实例合并成 1 个实例化 draw call + `OnPerformCulling` 剔除，Frame Debugger 显示为 **"Hybrid Batch Group"**（本次截图中 `RenderLoop.DrawSRPBatcher → Hybrid Batch Group` 即 BRG，223 FPS）。SRP Batcher 只减少每次 draw 的 CPU 状态设置，**不减少 draw call**。
- **业界在 Unity 无 mesh shader 时的簇/meshlet 标准做法**（Arx-GPUDriven-Renderer、UnityNanoMesh、Medium 文一致）：几何存 StructuredBuffer → 剔除 compute（视锥/Hi-Z）写可见簇 ID 进 AppendStructuredBuffer + 计数 → `DrawProceduralIndirect` / `DrawMeshInstancedIndirect` 用该计数当 instanceCount，**1 次 draw 画完所有可见簇**；簇在 vs 里靠 `SV_InstanceID` 展开。**手动取顶点是该方案固有成本但实测很快**（3.8ms 那行已含手动取顶点）。
- **结论**：之前 approach-3（DrawProceduralIndirect）方向正确，但被连续搞砸（双绘 / 剔除映射写成 vertexId/96 只画 cluster 0 / 每帧全量上传矩阵 / 最后错改成 130k DrawMesh）。正解 = 单次 indirect draw + 正确 `SV_InstanceID` 映射 + 剔除产可见列表 + 不动不重传。
- **簇粒度 + 硬件顶点管线在 Unity 内置管线不可兼得**（除非 mesh shader）；BRG 的快来自「实例共享几何 → 实例化合并」，簇几何各异 → 强行按簇分实例反而退化。

## RVT 纹理粒度问题（用户新问题：贴图糊）
- **现象**：一个材质/贴图只占 RVT 一个格子 → 清晰度被压扁 → 糊。
- **根因（对着代码）**：`TileTable` 按 mip 分带、每张图每级 mip 占**恰好一个格子**（`maxCellSize`）；`GetColor`（ClusterPass.hlsl/ClusterInput.hlsl）把 UV 直接映射进该格子采样。→ **一张图的最高清晰度 = maxCellSize**，源图更大就被压扁。
- **业界正解**：分块虚拟贴图（Sparse/Unity VirtualTexturing）——把每张图切成固定尺寸 **tile**（如 128²/256²），页表按 `(texId, mip, tileX, tileY)` 寻址物理 tile，反馈按 tile 收集，按需流式载入 + LRU 淘汰。分配单元从「整张图」变为「固定 tile」。
- **与簇的关系**：几何簇（切 mesh 做剔除/LOD）与贴图 tile（切贴图做按需驻留）正交；可耦合为「按簇分配贴图页」（P5，UE5 Nanite+VT 做法）。
- **关键洞察**：**RVT 粒度与绘制路径（BRG / 簇）无关**——两者都采样同一套 `_TextureNodesBuffer` + `_Virtual*`，改进 RVT 对两条路都有益。

## RVT 改造方案：Tile 粒度虚拟贴图（Sparse VT，用户已确认方向）
- **目标**：把每张图从「1 个格子」改为「T×T 个 tile」，让 4K 图可达 `CellSize*T` 分辨率（CellSize=512、T=8 → 4K 满分辨率），不再被 maxCellSize 卡死。
- **页（page）定义**：`pageId = (((texId*mipsLevel + mip)*T + tileY)*T + tileX)`；`RVTTransferNode`/`allMipsCacheNode` 由「每(texId,mip)1 个 CacheNode」改为「每 page 1 个 CacheNode」。`flags` 缓冲长度 = `texCount*mipsLevel*T*T`。
- **反馈编码（关键命门）**：`FeedbackPass.fragSimple` 当前写 `float4(texId/256, texId%256, mip, 1)`（RGBA8，仅 (texId,mip)）。改为写 32-bit `pageId`：`R=(pageId>>0)&255, G=(pageId>>8)&255, B=(pageId>>16)&255, A=(pageId>>24)&255`。`RVTFeedbackCompact` 解码 `pageId = r | g<<8 | b<<16 | a<<24`，再按 `T/mipsLevel` 拆回 (texId,mip,tileX,tileY)；`key=pageId` 直接置位；过滤 `pageId >= texCount*mipsLevel*T*T` 与最低级由 `needCallMinsMap` 仍负责（需扩展为分配 T×T 个最低级 page）。
- **采样（GetColor）**：`ClusterPass.hlsl` 调 `GetColor(input.baseUV, texId, mip, detailUV)`；内部 `tileX=floor(uv.x*T), tileY=floor(uv.y*T), localUV=frac(uv*T)`，查 `_TextureNodesBuffer[pageId]` 得该 tile 的 atlas 格子，用 localUV 采样。
- **绘制（DrawTile + RVTShader）**：`BRDF_Tile.RenderTile` 给 block 传 `_TileOrigin=(tileX/T, tileY/T)`、`_TileScale=1/T`；`Unlit/RVTShader` 的 draw pass frag 改为 `i.uv = (_TileOrigin + i.uv*_TileScale - Padding)/(1-2*Padding)` 后再采样源贴图，实现只画该 tile 子矩形。
- **LRU/淘汰**：CacheNode 已含 (width,height,mipsLevel)；`ProcessTextureEviction` 改为遍历该 texId 的全部 page 结点整组降级（现有 per-texId 遍历逻辑可复用，只需从「遍历 mip」改为「遍历 page」）。
- **安全**：用 `useTileVT` 开关门控（新增 `ClusterAssembleAsset` 字段），BRG/旧路径默认关，验证通过再开。
- **改动文件清单**：`FeedbackPass.hlsl`、`RVTFeedbackCompact.compute`、`TextureNodesMap.cs`、`TileTable.cs`(DrawTile)、`RVTShader.shader`、`Datas/TileUnility.cs`(BRDF_Tile)、`ClusterInput.hlsl`(GetColor)、`ClusterPass.hlsl`(调用)、`ClusterAssembleAsset.cs`(TilesPerAxis/useTileVT)、`ClusterCore.cs`(MinsMap 分配 T×T page)、`ClusterControl.cs`(全局传 T)。
- **显存代价**：每 tex 每 mip 占 T² 格；缓存总格数 = `CellCount² * mipsLevel²`（`LevelCache` 网格）。T=8、100 可见图需 ~6400 格 → CellCount 需随 sqrt(N*T²) 调大，图集显存线性随 CellCount 增长。需与用户确认 T 取值与门控方式后再实现。

## ⚠️ RVT Tile 化的显存真相（重要，推翻上面的"lean 方案"）
- **核心约束**：单张贴图在图集里占据的像素 = 它驻留的页数 × cellSize²。一张 4K 图若 64 页(T=8)全驻留 = 64×512² = 4K² 像素，等于吃满 64 个 cell。若反馈只按 (texId,mip) 粒度（不编码 tileX/tileY），一旦某张图被请求就把它 T² 页全画进图集 → 所有被请求的图都按全分辨率驻留 → 显存 = 所有"被请求图"的像素之和，**无法被图集容量限制**，必然爆显存。这就是上面"lean 方案（反馈不变、分配时 fan-out 到 T² 页）"的致命缺陷。
- **结论**：要真正省显存、支持 4K/8K，tile-VT **必须**走"每页反馈 + 每页 LRU 流式"——即反馈编码 32-bit pageId=(texId,mip,tileX,tileY)，`LevelCache` 改为以"页(cell)"为分配/淘汰单元（每 (texId,mip) 占 T² 个 cell 结点，LRU 逐页淘汰），`flags` 缓冲扩到 `texCount*mips*T*T`。这是一次对 `LevelCache`/`TextureNodesMap`/反馈编码的实质重构，不是小改。
- **立即生效的零风险替代**：当前糊的根因是 `CellSize=512` 把每张图压成 512²。若源图最大 2048，**把 `ClusterAssembleAsset.CellSize` 调到 2048（配合足够 `CellCount`）即可立刻满分辨率、零代码改动**；其显存 = 同 T=4 tiling，但完全不碰 RVT 逻辑。Tiling 的真正价值是"混合大小贴图时按需驻留、未来 4K/8K 不浪费小图显存 + 流式"，不是单纯提清晰度。
- **给用户的最终选项**：A) 立刻调 CellSize 解决当前糊（零风险）；B) 投入真正 tile-VT 重构（per-page 反馈+LRU，分阶段、门控、风险较高）。需与用户确认走哪条。

## ★ BRG 阴影真正根因纠正：不是缺 ShadowCaster pass，是 BatchFilterSettings.shadowCastingMode 默认 Off
- **用户反馈**：补了 ShadowCaster pass 后**仍然没阴影**。Frame Debugger 截图铁证：`Main Camera > Shadows > Shadows.DrawSRPBatcher` 下**只有 4 个 "SRP Batch"（用户的地板，普通 MeshRenderer）**，**完全没有 "Hybrid Batch Group"**；而主画面 `RenderLoop.DrawSRPBatcher` 下有 `Hybrid Batch Group`（= BRG）。→ BRG 批次根本没被阴影流程收集。
- **真正根因（决定性）**：`BatchRenderManager.OnPerformCulling` 里 draw range 的 filterSettings 只写了
  `new BatchFilterSettings { renderingLayerMask = 0xffffffff }`，其余字段取默认值。而
  **`BatchFilterSettings.shadowCastingMode` 默认 = `ShadowCastingMode.Off`(0)**，Unity 据此把整条 draw range
  排除在**所有**阴影流程之外（相机 pass 不看该字段 → 主画面正常，极具迷惑性）。
  Unity 官方 `BRGSetup.cs`（Unity-Technologies/Graphics, Tests/SRPTests/.../BatchRenderGroupRaw）**显式**写了
  `shadowCastingMode = ShadowCastingMode.On, receiveShadows = true, layer = 0, motionMode = ForceNoMotion` 等
  全套 filterSettings —— 这正是官方示例能投影的原因。
  权威依据（Unity 2022.3 CoreModule XML 文档）：`P:BatchFilterSettings.shadowCastingMode` = "Specifies how

## 修复二：远处阴影被剔除 + 画面全黑（无天空盒 SH9 / 反射）
用户反馈：① BRG 近处阴影有、远处没有（怀疑 BRG 视锥剔除）；② 画面全黑、完全没加天空盒 SH9 间接光与反射。

### 修复 1（远处阴影）：BatchRenderManager 补 SetGlobalBounds
- **根因**：`BatchRendererGroup` 从未调用 `SetGlobalBounds(...)`。Unity 在 `OnPerformCulling` 之前用组级 bounds 做整组 broad-phase 剔除（含阴影/光照视图）。缺省 bounds 会让远处/阴影视图下整组被丢弃 → "近有远无"。逐实例 `IsVisible`（box-vs-frustum 保守测试）本身正确，不是元凶。
- **改法**：`BatchRenderManager.cs` 新增 `ComputeGlobalBounds()`（所有实例 `worldBounds` 并集，空时退回官方 BRGSetup.cs 同款超大 bounds `1048576³`）+ `UpdateGlobalBounds()` 调 `brg.SetGlobalBounds(...)`；在构造函数、`Register`、`Unregister`、`UpdateMatrices`（矩阵变化时）均调用。
- **更正（上轮误判）**：阴影距离参数**本就来自 Deffer 管线预制体**，不是 Unity 内置。`DefferPipeline.asset` 的 `shadowSetting.maxDistance=300`（覆盖 `RenderSettingStruct.cs` 的默认 100），经 `DefferPipeline.Cull()` 设 `p.shadowDistance`。**Unity 内置 `m_ShadowDistance`（QualitySettings/场景相机）对本自定义 SRP 不生效**。用户本轮确认参数就在 Deffer 预制体上——Inspector 的 Shadow Setting → Max Distance 可调，无需改代码。

### 修复 2（全黑）：天空盒 SH9 间接漫反射 + BRG 天空盒反射
- **根因 A（全场景缺间接光）**：延迟最终合成 `DefferCameraPass.hlsl::DrawGBufferColorFragment` 从不叠加任何 SH 间接漫反射 → 阴影/背光面纯黑。主份 GBuffer 填充（DefferPipeline 走 `else` 分支 `GetBakeDate` 读 `unity_SHAr`，而该值为 0）也没给间接光。
- **根因 B（BRG 无反射）**：`ClusterPBR_BRG.shader` fragment 写 `RT3.rgb = 0`（反射缺），而最终阶段把 `RT3.rgb` 当反射叠加 → BRG 物体零反射。主份路径此处写 `ComputeIndirectSpecular`。
- **根因 C（`_Sh9` 恒为 0）**：`SceneSH9.OnEnable` 只调 `UpdateSceneSH9()`，此时 `_sh9` 为空 → 传给 shader 的全零。必须点过 Bake 才有非零 SH9。
- **改法**：
  1. `DefferCameraPass.hlsl`：在 `GetGBufferLight` 后加 `indirectDiffuse = max(GetIndirectLight(normalWS),0) * albedo * (1-metallic*0.96) * AO`，叠加到 color（全对象生效，含 BRG）。注意 DefferPipeline 不启用 `_MY_LIGHTING`（仅旧 MyPipeline 启），故无双重叠加。
  2. `ClusterPBR_BRG.shader`：fragment 内新声明 `TEXTURECUBE(_MySkybox)/SAMPLER` + 用 `positionWS/TtoW.w`、`_WorldSpaceCameraPos` 算反射方向，采样 `_MySkybox` 写入 `RT3.rgb`（与最终阶段菲涅尔/AO 调制一致）。仅 include Common.hlsl，未引入 GI.hlsl 重链 → DOTS "wrong cbuffer setup" 复现风险规避。
  3. `SceneSH9.cs`：`OnEnable` 改为「若 `_sh9` 空且挂了 `currentSkybox` 就自动 `Bake()`，否则沿用」。保证延迟管线一开始就拿到正确 `_Sh9`（天空盒间接光）。`_Sh9` 由 `GPUDravinSystem` 每帧设成全局量，`_MySkybox` 同源。
- **待用户进 Play 验证**：① 远处阴影是否出现（必要时调大 Max Distance）；② 阴影/背光面不再全黑（有天空盒 SH9 间接光）；③ BRG 物体有天空盒反射；④ 画面整体不再死黑。
- **前置条件提醒（已放宽）**：原要求 `SceneSH9.currentSkybox` 必须手动挂场景天空盒 Cubemap；本轮已改为**自动从 `RenderSettings.skybox` 解析**，手动引用仅作兜底。

## 修复三：用户五点反馈（阴影距离来源 / 天空盒太亮+颜色错+像默认 / SH9 算错 / 木质反射过强）

### 1) 阴影距离来源（澄清，无需改代码）
- 当前即用 Deffer 管线预制体参数：`DefferPipeline.asset → shadowSetting.maxDistance=300`，经 `DefferPipeline.Cull()` 写入 `p.shadowDistance`。**Unity 内置 `m_ShadowDistance`（QualitySettings 或场景相机 Inspector）对本自定义 SRP 无效**，调它不会改变阴影距离。

### 2) 天空盒来源错配（头号根因，已修）
- **根因**：`SceneSH9.currentSkybox` 一直指向 `ReflectionProbe-0.exr`（guid `d3e628a4…`，一个反射探针 cubemap），而场景真实天空盒是 `SunsetSkyboxHDR.mat`（`Skybox/Cubemap` 着色器，其 `_Tex` = `SunsetSkyboxHDR.hdr` cubemap，guid `162dc31d…`）。两者不是同一个 → SH9 与反射 cubemap 都基于错误来源，表现即「太亮 + 颜色不一致 + 像 Unity 默认天空盒」。
- **改法 `SceneSH9.cs`**：新增 `autoUseSceneSkybox`（默认开）+ `ResolveSceneSkybox()`（`RenderSettings.skybox.GetTexture("_Tex")` 取场景真实 cubemap，兜底 `mainTexture`）；`OnEnable` 自动用场景天空盒覆盖手动引用；新增 `_bakedFromInstanceId` 记录烘焙来源，来源变化（实例 ID 不同）即自动重烤，避免一直沿用旧来源烘焙出的 `_sh9`。新增 `indirectIntensity`（默认 1，0~4）强度倍率，来源修正后仍偏亮/暗可微调。加 `[ContextMenu("Re-Bake Scene SH9")]` 手动重烤入口。

### 3) SH9 数学复查（未改公式，来源修好即正）
- 复查 `SH9ProjectFromCubeMap.compute`：均匀球面采样（theta=acos(1-2x/(N-1)) 等面积分布）+ Monte Carlo 积分 `A=4π/N` 求和；`SH9Project.cs` 跨 ThreadGroup 累加；`GI.hlsl::GetIndirectLight` 用 `_Sh9[0..8]` 与 compute 的 Y00..Y2p2 顺序一一对应。**基函数与重建公式对齐，无算错因子**。之前"算错"实为来源 cubemap 错。若来源修正后仍偏亮，用 `indirectIntensity` 微调。

### 4) 木质高粗糙反射过强（已修）

## 修复四：DefferStandard 与 BRG 材质差距大 + BRG 阴影崩溃（用户两条反馈）
用户原话：①「你是不是把我的延迟渲染的着色代码改了，要把 DefferStandard 改统一，按正确的改，不知道是你错了还是我之前的错了」；②「没跑 BRG 时整场景都有阴影，一跑 BRG 阴影就出错，一定是 BRG 有问题」。

### A. 两材质差距根因（已修，结论：BRG 是对的，DefferStandard 没跟上）
- **诊断**：两条路径都写同一套 MRT，但 GBuffer 填充逻辑分歧巨大：
  1. **反射来源不同**：`GBufferPass.hlsl`(DefferStandard) 旧代码走 `ComputeIndirectSpecular` → 采样 **`unity_SpecCube0`**（内置反射探针）；BRG 走 `SamplerReflectProbe` → 采样 **`_MySkybox`**（场景真实天空盒 cubemap，GPUDravinSystem 每帧设）。来源不同 + 后处理（DecodeHDREnvironment / 投影 box）不同 → 肉眼可见色彩/亮度差。
  2. **mip 公式不同**：DefferStandard 用 `PerceptualRoughnessToMipmapLevel(roughness)`；BRG 用 `clamp(roughness*7,0,8)`。模糊度不一致。
  3. **SH9 双重叠加**：DefferStandard 旧代码把 `GetIndirectLight(perNormal)*ao` 烘焙进 `emissive`(RT2)，而延迟合成 `DefferCameraPass.hlsl` 又用 `_Sh9` 统一加一遍 SH9 → 主份物体间接漫反射被加倍，BRG 物体只加一遍 → 两者背光面亮度差。
- **为什么 BRG 这套是对的**：DOTS/BRG 下不能用 Unity 全套内置链（`unity_SHAr`/`unity_SpecCube0` 在 DOTS 变体里是错的，而且引入会报 `wrong cbuffer setup`），所以 BRG 必须用工程自己的 `_MySkybox`/`_Sh9`。DefferStandard（非 BRG 路径）虽能走内置链，但那样两者就永远对不齐。→ **统一基准 = BRG 那套**，把 DefferStandard 对齐到它。
- **改法 `GBufferPass.hlsl`**：删除 SH 烘焙进 emissive 的逻辑（emissive 现在只 = `GetEmission`，SH9 全交给合成阶段统一加）；反射改为 `SamplerReflectProbe(reflect_dir, clamp(roughness*7,0,8))`（即采样 `_MySkybox`）并乘 `reflIntensity=lerp(saturate(0.05+(1-roughness)*0.6),1,metallic)`。**逐行对照 `ClusterPBR_BRG.shader::frag`(341-352) 确认公式完全一致**（同一 `_MySkybox`、同一 mip、`environment.xyz` == `.rgb`、同一 `reflIntensity`）。RT3 写入两路径现在等价。
- **效果**：主份与 BRG 物体反射来源/模糊度/材质衰减一致；SH9 间接光只由合成阶段统一加一次，无双重。

### B. BRG 一开阴影就出错根因（已修）
- **诊断**：未启用 BRG 时，物体走普通 `MeshRenderer` + 标准 `context.DrawShadows`，整个 `cullingResults` 里有 shadow caster → `GetShadowCasterBounds` 返回 true → 阴影正常。一旦 BRG 接管，`ClusterObject.OnEnable` 把物体的 `MeshRenderer.enabled=false` → 这些物体**不在** `cullingResults` 的 shadow caster 集合里。于是 `Shadows.cs::ReserveDirectionalShadows/ReserveOtherShadows` 里的 `cullingResults.GetShadowCasterBounds(visibleLightIndex, out Bounds)` 对本该投射阴影的光返回 **false**，代码据此判定「该光无投射物」→ `return Vector4(-light.shadowStrength,0,0,maskChannel)` → 整条光的阴影被跳过 → **整片阴影消失**。BRG 本身（ShadowCaster pass + `shadowCastingMode=On` + `SetGlobalBounds`）都正确，锅在 `Shadows.cs` 的剔除闸门。
- **改法 `Shadows.cs`**：新增 `using Cluster;`（引 `BatchRenderManager`）；两处 `GetShadowCasterBounds` 失败闸门改为「仅当 `BatchRenderManager.Instance==null || !BatchRenderManager.Instance.HasBatches`（即确实没有任何 BRG 投射物）时才跳过该光；有 BRG 批次则假定光仍需渲染，BRG 经 `OnPerformCulling` 提供 caster」。之后该光仍照常 `ComputeDirectionalShadowMatricesAndCullingPrimitives` + `context.DrawShadows`，由 Unity 回调 BRG 的 `OnPerformCulling` 把 BRG 物体画进阴影图。
- **安全性**：栅门只在该光「查不到 caster 且确实无 BRG 批次」时跳过；否则保留。不会误伤普通 MeshRenderer 物体的阴影（它们本就进 `cullingResults`，`GetShadowCasterBounds` 返回 true → 正常保留）。
